# GMB-141: a second implementation task, and what it settles

**Date:** 2026-08-25
**Task added:** `tt-implement-split-task-cancelled-release` (task-tracker-mcp), with holdout fixture
`corpora/task-tracker-mcp/fixtures/tt-implement-split-task-cancelled-release/`.
**Variance run:** `results/token-economy/2026-08-24T21-17-07-169Z.json` — 15 records, 5 repetitions ×
3 arms, $7.42.

**Two results, and they point opposite ways.** The task is **noisier** than the incumbent on turns
and tokens, which by this task's own acceptance criteria is a reason to say so rather than adopt it
quietly. But on the measurement it was built for it is far **more consistent** — and it settles the
question GMB-136 could not.

## 1. The bug it poses

Not invented. The corpus's own doc comment on `cancelRelease` states the contract:

> Note what this does *not* do: nothing happens to the release's tasks. A cancelled release keeps its
> membership as the record of what was abandoned, and its still-open tasks **stay claimable**

They stay claimable — but they cannot be **split**. `splitTask` inherits the parent's `release_id`
by passing it to `createTask`, which runs it through `requireAssignableRelease`, which rejects a
cancelled release. Splitting fails with *"Release … is cancelled; cannot assign new tasks to it"*
about work that is already in that release and is not being newly assigned.

**Why it has blast radius.** `createTask` has three callers: `splitTask` (inherits a release),
`createTasks` (takes one from its input) and the MCP tool (takes one from the caller). The fix has to
separate inheritance from assignment across those three, and keep rejecting a *released* release,
which is frozen on purpose. It is not a one-file read: `tasks.ts` and `releases.ts` both matter, and
so does checking the other two callers.

## 2. The holdout discriminates — demonstrated, not assumed

Four tests. One asserts the split works and the subtasks inherit the cancelled release. Three pin the
rules that must survive: a new task still cannot be created into a cancelled release, an existing
task still cannot be moved into one, and a task whose release already shipped still cannot be split.
Without those three, deleting the guard would "pass".

| against | result |
|---|---|
| the corpus at its pinned revision | **1 failed, 3 passed** |
| a reference fix | **4 passed**, and the existing 109 tests in `lifecycle`/`releases`/`tasks`/`split`/`status` still pass |

The reference fix was written in a throwaway `git worktree` of the corpus and reverted; it is not in
the registry and not in the corpus checkout.

It is roughly twice as long a task (27.6 turns against 15.1) and, on the g-mesh arm, noisier in both

**So the acceptance criterion "prefer a tighter task" is not met.** Anyone quoting this task at n=3
will get the same reversals the incumbent produced.

## 4. What it does deliver, which is the point

The incumbent could not answer the post-edit question: one of its three sweeps had zero post-edit
greps, and the registry's other implementation task makes zero calls after its edit at all. This one
produces a real verification phase in **every repetition**:

| arm | rep | pre-edit native/total | post-edit native/total | post-edit greps |
|---|---|---|---|---|
| `gmesh-configured` | 1 | 2/7 | 0/10 | 3 |
| `gmesh-configured` | 2 | 4/8 | 0/7 | 2 |
| `gmesh-configured` | 3 | 3/11 | 0/7 | 2 |
| `gmesh-configured` | 4 | 3/7 | 0/21 | 9 |
| `gmesh-configured` | 5 | 3/8 | 0/19 | 7 |
| **`gmesh-configured`** | **all** | **15/41 (37%)** | **0/64 (0%)** | **23** |
| **`baseline`** | **all** | **0/49** | **0/58** | **24** |

**Zero native calls after the edit, in five repetitions out of five, on a task independent of the
one the pattern was first seen on.** Before the edit the same arm is at 37%.

And it does 23 post-edit greps against baseline's 24 — after its first edit, the g-mesh arm is
behaving indistinguishably from the arm that has no index at all.

## 5. What this changes

GMB-139 downgraded the post-edit collapse to "a real observation about tool choice with, so far, no
demonstrated cost attached", because the grep storm appeared in only two of three sweeps of one
task. That caveat is now too weak in one direction and still correct in the other:

- **The collapse itself is confirmed.** Two independent tasks, eight repetitions between them, and
  the post-edit native share is 0–13% against a pre-edit 29–64%. It is not an artifact of one task.
- **A cost consequence is still not demonstrated.** g-mesh's post-edit call count here (64) is close
  to baseline's (58), and its turn mean is within noise of baseline's (27.6 vs 27.4). The arm stops
  using its index; it does not obviously pay more for doing so on this task.

The experiment GMB-139 could not run — the post-edit cue A/B with a second task to check against —
is now possible. At this task's CV it needs about 8 repetitions a side, not 3.
