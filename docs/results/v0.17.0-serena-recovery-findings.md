# v0.17.0 — serena arm recovered; cheap re-run against 2026-08-14

## What was broken

Since at least 2026-08-14, `serena`/`serena-configured` could not start:

```
uvx --from git+https://github.com/oraios/serena serena --help
  -> Failed to download and build `serena-agent @ git+https://github.com/oraios/serena@93ec043105f5ee4f5ff64ea0158041500d2cdc65`
  -> Git operation failed: `/usr/bin/git reset --hard 93ec043...` exit status 128
  -> error: unable to read sha1 file of src/serena/project_server.py (0debaac...)
  -> error: unable to read sha1 file of test/solidlsp/kotlin/test_kotlin_diagnostics.py (0d0d824...)
```

That is a **corrupted local `uv` git cache entry**, not an upstream serena
problem: `uv` had a checkout of commit `93ec043105f5ee4f5ff64ea0158041500d2cdc65`
cached under `~/.cache/uv/git-v0/{checkouts,db,locks}/42910dfe8296368e/`, and
that checkout was missing objects two of its files needed. `git reset --hard`
against a checkout with missing objects fails exactly this way.

**Fix**: remove that one cache entry (not a full `uv cache clean`) and let `uv`
re-clone and rebuild:

```bash
rm -rf ~/.cache/uv/git-v0/checkouts/42910dfe8296368e \
       ~/.cache/uv/git-v0/db/42910dfe8296368e \
       ~/.cache/uv/git-v0/locks/42910dfe8296368e
uvx --from git+https://github.com/oraios/serena serena --help   # rebuilds cleanly
```

`uv` re-resolved the **same** commit, `93ec043105f5ee4f5ff64ea0158041500d2cdc65`
— confirming the repo itself never moved; only the local cache was bad.

## The re-run: a cheap 4-task subset, not a new sweep

The 2026-08-14 sweep (387 records, $38.75) is **still invalid** as a
g-mesh-vs-serena comparison and is not being redone in full here — that would
cost another ~$38 and hours for a result this fix doesn't require. Its
g-mesh-vs-baseline half stands; its serena column remains what it was
annotated as by `scripts/annotateMcpDeadRuns.ts`: baseline, mislabeled.

Instead, this is a deliberately narrow, cheap re-run of the four tasks the
2026-08-14 investigation's conclusions leaned on, chosen to cover both
corpora and both repetition regimes:

- `tt-deps-incoming-db-connection`, `tt-scenario-impact-requireproject`,
  `ex-references-pointfrom-highfanout` — `G_MESH_BENCH_REPS=low` (1 rep each)
- `ex-multihop-elbowarrow-routing-callees` — `G_MESH_BENCH_REPS=normal`
  (3 reps; this is the task with observed run-to-run variance, hence the
  extra reps here specifically)

Run in the **foreground** (a first, backgrounded attempt died mid-run when the
machine slept and never wrote a result file — no partial numbers from that
attempt are reported anywhere), with `G_MESH_BENCH_SAVE_TRANSCRIPTS=yes` and
`G_MESH_BENCH_WARM_CACHE=yes`. Total cost: **$0.84 + $0.03 narrative** for the
three low-rep tasks, plus the multihop 3-rep run (see raw files for its own
total) — two orders of magnitude below a full sweep.

Result files:
- `results/token-economy/2026-08-15T17-35-38-375Z.json` (9 records: 3 tasks × 3 arms × 1 rep)
- `results/token-economy/2026-08-15T17-43-52-973Z.json` (9 records: 1 task × 3 arms × 3 reps)

Every one of the 18 records has `status: "ok"` and `oraclePassed: true` — no
errors, no budget exceedances, no annotation needed.

- On `tt-deps-incoming-db-connection`, `gmesh-configured` made 1 `mcp__*` call

  harder tasks these arms are meant to differentiate on.

## Pinning serena to a fixed revision

**Recommendation: do not hard-pin.** Keep `uvx --from git+https://github.com/oraios/serena`
resolving the default branch tip, as it does today — but *do* record what
that tip resolved to on every run, which this fix adds
(`TokenEconomyRun.serenaRevision`, `harness/token-economy.ts`, via
`git ls-remote`).

Reasoning:

- **What actually broke here wasn't "the revision changed under us" — it was
  a local cache holding a corrupt copy of one revision.** `uv` re-resolved the
  identical commit (`93ec043105f5ee4f5ff64ea0158041500d2cdc65`) once the bad
  cache entry was removed. A pin would not have prevented this failure or
  made it faster to diagnose; the fix was cache hygiene, not version control.
- **Task #14's guard already closes the failure mode that actually cost real
  money** — an arm whose server never started being silently recorded as a
  passing baseline-shaped result. That guard fires on *any* connection
  failure, pinned or not, so a pin's main remaining value is narrower:
  knowing which serena build a given result reflects.
- **`serenaRevision` gets that same value without the downside of a hard
  pin.** A fixed SHA needs upkeep — someone has to notice when it's worth
  bumping, and a stale pin fails *silently* (numbers keep looking normal,
  just measuring an increasingly old serena) rather than loudly, which is a
  worse failure mode than this incident's loud, obvious breakage.
- **This repo's own stated design goal is to measure serena as a user
  actually installs it** (`uvx --from git+…`, "there is nothing else to
  install" — see README's Getting Started). A pin measures a frozen
  historical serena instead, which is a different, narrower question than
  the one this benchmark exists to answer.

Worth revisiting if: `SERENA_TOOLS`/`SERENA_DENIED_TOOLS` in
`harness/lib/armConfig.ts` (a hand-curated list against serena's *current*
tool surface) drift out of sync with a real upstream change — i.e. if
tracking HEAD starts silently changing what tools the arm exposes rather than
just its internals. That is the concrete trigger for reconsidering a pin, not
this incident.
