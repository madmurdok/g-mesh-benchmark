# GMB-142: it uses the index to find and grep to confirm

**Date:** 2026-08-25
**Data:** 140 `gmesh-configured` runs over 46 tasks — the 2026-08-24 token-economy sweep
(`2026-08-24T09-33-30-824Z-partial.json` + `2026-08-24T12-39-50-277Z.json`) plus the GMB-141
variance run (`2026-08-24T21-17-07-169Z.json`). No new spend; all of it is `toolResults` already on
disk.

**Answer in one line:** the agent reaches for g-mesh first almost every time, and reaches for grep
*after it already has the answer* — not because a lookup failed.

## 1. The opener: it does reach for the index first

| category | runs | opens with a g-mesh call |
|---|---|---|
| semantic-search | 39 | 100% |
| lookup | 45 | 80% |
| multi-hop | 12 | 100% |
| scenario | 15 | 100% |
| implementation | 11 | 100% |
| control | 9 | 89% |
| ambiguous-name | 6 | 100% |
| feature-request | 3 | 100% |

**130 of 140 runs (93%) open with a g-mesh call.** The first call is `search_code` 38% of the time,
`find_definition` 27%, `find_references` 10%. Only 4 runs in 140 open with a grep.

The guidance doc's instruction to make `search_code` the first move on a "find the function that does
X" prompt is being followed. Whatever the tool-choice problem is, it is not the opening.

## 2. What actually precedes a grep

Every grep in the 140 runs, classified by what came before it in the same run:

| what preceded it | greps | share |
|---|---|---|
| a g-mesh call, before any edit | 70 | **60%** |
| an `Edit` | 38 | 33% |
| nothing — first call of the run | 4 | 3% |
| only `Read`/`Glob` | 4 | 3% |

**Grep is almost never where the agent starts. It is where the agent goes next.** 93% of greps
happen in a run that has already made a native call, and a third of them after the run has started
editing.

## 3. It is not a fallback from failure

The obvious explanation — the index returned nothing, so it grepped — does not survive the data.

Across 229 native calls the result sizes are: min 59 chars, p10 684, p25 1,153, **median 3,761**,
max 18,826. **Four results in 229 are under 400 characters and one is under 200.** Empty and
near-empty answers are rare enough that they cannot be driving 116 greps.

The tool is answering. The agent greps anyway.

## 4. A quarter of greps re-ask a question already answered

Of the 93 greps whose `pattern` argument parses, **23 (25%) contain a symbol the same run had
already resolved with a native call.** Verbatim, from the runs:

| already resolved by a native call | the grep that followed |
|---|---|
| `requireTask` | `grep requireTask` |
| `requireProject` | `grep requireProject` (twice in one run) |
| `releaseTask` | `grep releaseTask\|release_task` |
| `mutateElement` | `grep mutateElement` (twice in one run) |

This is the behaviour the guidance document spends several paragraphs on — it states when a
`find_references` result is complete, says not to re-verify it with grep, and cites a measured ~38%
mean cost drop from an agent that stops. A quarter of greps do it anyway.

Cost unit is the turn, not the grep: a turn costs roughly 15,100 tokens in the isolated experiment,
and the static prefix (8,762) is charged on every one of them. Greps can share a turn when issued in
parallel, so 23 redundant greps is an upper bound on 23 wasted turns, not an equality.

**Method, and where it is weak.** This is a substring test of the resolved `symbol_name` against the
grep's `pattern` string — a heuristic, not a parse. It over-counts where a re-grep was legitimate
(hunting a different usage form, or a string that merely contains the symbol) and under-counts
greps whose pattern does not carry the literal symbol. The 47 greps with no parseable pattern and
the ones searching for something never resolved natively are excluded rather than bucketed.

## 5. The two most expensive tools are the two least used

| tool | calls | runs using it | share of runs | share of `tools/list` payload |
|---|---|---|---|---|
| `search_code` | 71 | 53 | 37.9% | 10.7% |
| `find_definition` | 57 | 40 | 28.6% | 14.6% |
| `find_references` | 42 | 39 | 27.9% | 11.5% |
| `find_callers` | 18 | 17 | 12.1% | 10.0% |
| `get_file_outline` | 17 | 8 | 5.7% | 7.1% |
| **`find_implementations`** | **12** | 12 | 8.6% | **21.2%** |
| `find_callees` | 9 | 9 | 6.4% | 10.0% |
| **`get_dependencies`** | **3** | 3 | 2.1% | **14.8%** |

Payload shares from `v0.22.0-gm188-where-the-schema-tax-goes.md`.

`find_implementations` and `get_dependencies` together are **36% of the schema every run carries on
every turn**, for 15 calls across 140 runs. `find_implementations` alone is the single most
expensive tool in the payload and the second-least used.

**This is the one directly actionable number here, and it comes with a real caveat.** Usage is a
function of the task mix: the registry has 2 `ambiguous-name` tasks and 2 that are about the import
graph, so `get_dependencies` having little to do is partly the registry's shape, not the tool's
worth. A tool that is rarely needed but decisive when it is needed can be worth its schema. What the
number does establish is where to look if the schema tax is ever trimmed — and GM-188 already
measured that the recoverable prose there is ~2% of the payload, so trimming means shipping thinner
contracts, not tidier ones.

## 6. So: when does it get it right

**Right, consistently:** the opening. 93% of runs, 100% in every category except `lookup` and
`control` — and in those two the guidance doc explicitly says grep is the cheaper choice, so an
80–89% native opening there is arguably too *high*, not too low.

**Wrong, consistently:** the confirmation step. Having resolved a symbol with a tool whose contract
states the result is complete, the agent re-checks it with text search in a quarter of its greps —
and after its first edit it stops using the index entirely (0/64 native calls across five
repetitions on `tt-implement-split-task-cancelled-release`, and 0–13% on
`tt-implement-release-cancelled-task-bug`; see GMB-141).

Both failures are the same failure in two places: **the agent trusts the index to find things and
does not trust it to have finished.**

## 7. What this does not establish

That the confirmation habit costs anything measurable. On the task where it is most visible, the
g-mesh arm's post-edit call count (64) sits next to baseline's (58) and its turn mean (27.6) next to
baseline's (27.4). The behaviour is unambiguous; its price is not.

The obvious next move is GMB-139's A/B rerun with two tasks and ~8 repetitions a side. Note what
GMB-139 already showed, though: a sentence added to the doc did not move post-edit tool choice at
all. The problem may not be that the agent has not been told.
