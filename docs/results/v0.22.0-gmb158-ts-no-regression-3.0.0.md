# GMB-158: g-mesh 3.0.0 against 2.12.1 — a one-corpus no-regression read

**Date:** 2026-09-16
**Scope:** a **sanity read, not a full-scale measurement.** One corpus
(`task-tracker-mcp`, 14 tasks), two arms (`gmesh-configured`, `baseline`), 3
repetitions, two builds — 168 runs, **all 168 `ok`**, **$17.33**, 69 minutes of
run time. **excalidraw was not measured at all.**

**Records:** `results/token-economy/2026-09-16T01-10-50-464Z.json` (2.12.1, 84
records) and `results/token-economy/2026-09-16T01-50-50-478Z.json` (3.0.0, 84
records). Transcripts saved for both.

**Answer: no regression, and for once that is not the same sentence as "we
measured nothing".** The strongest evidence is not the token sweep — it is that
**all 20 probed tool responses are byte-identical between the two builds**, on a
probe demonstrated able to see a one-file change. The token sweep agrees and adds
an A/A control that puts a number on its own noise floor.

## Why 2.12.1 is the baseline, not 2.12.0

2.12.0 carries the GM-292 foreign-keys bug, fixed in **both** 2.12.1 and 3.0.0.
Baselining on 2.12.0 would credit that hotfix to 3.0.0 and report a
release-sized improvement 3.0.0 did not make. So:

| build | ref | commit | `core/Cargo.toml` | recorded `gmeshVersion` |
|---|---|---|---|---|
| baseline | `main` | `b64b57a` | 2.12.1 | `g-mesh 2.12.1` (42/42 gmesh records) |
| under test | `release-3.0.0` | `e1dd663` | 3.0.0 | `g-mesh 3.0.0` (42/42 gmesh records) |

`b64b57a` and the `release-2.12.1` tip `8d60e73` share the same tree
(`0cc6b069…`), so "branch main" and "the 2.12.1 release" are the same code here.

What 3.0.0 changes that could plausibly show up: protocol v2 (the TS plugin moved
with it), a schema bump (every index wiped and rebuilt once), containers /
structured placeholder targets in the linker, per-language semantic scheduling.
Its only user-visible claim is that **TS answers did not change**.

## How an arm points at a binary

`harness/lib/mcpConfig.ts`'s `gmeshBinaryPath()` returns
`process.env.G_MESH_BENCH_BINARY ?? <sibling g-mesh checkout>/core/target/release/g-mesh`,
and `buildGmeshArmConfig()` makes that path the `command` of the `g-mesh` MCP
server every gmesh-family arm declares. **One env var swaps the binary under
test**; nothing else about the run changes. The same function is what
`warmGmeshIndex()`, `writeRepoMap()` and `stopTrackedGmeshDaemons()` shell out
to, so warm-up, map and teardown all follow the binary automatically.

The version is recorded rather than assumed: `resolveGmeshVersion()` runs
`<binary> --version` once per invocation and stamps every gmesh-arm record with
`gmeshVersion` (GMB-138). Each run's 84 records name exactly one version, and it
is the expected one.

## Method

- Two detached `git worktree`s under a scratchpad, never the main checkout
  (which is on `release-3.0.0` and in use). `npm ci && npm run build` in
  `plugins/typescript` first — `core/build.rs` needs it — then
  `cargo build --release --manifest-path core/Cargo.toml`.
  2.12.1 built in `real 213s / user 992s`, 3.0.0 in `real 232s / user 1071s`.
- Arms narrowed to `gmesh-configured` + `baseline` by editing
  `g-mesh-bench.config.json`'s `tokenEconomy.arms` for the duration.
  `serena-configured` is a *default* arm and the `G_MESH_BENCH_INCLUDE_*`
  toggles are additive only, so there is no env-var way to drop it. **The file
  was restored afterwards** and is not part of this commit.
- `G_MESH_BENCH_REPS=normal` (3), `G_MESH_BENCH_WARM_CACHE=yes`,
  `G_MESH_BENCH_SAVE_TRANSCRIPTS=yes`, arm concurrency 2 (the default). The 14
  task ids passed on the CLI, which both selects them and leaves excalidraw with
  zero tasks so it is skipped.
- Corpus pinned in `corpora/registry.json` to `35237c8b…`; every one of the 168
  records carries it, and both runs share the same `taskDefHash` set.
- Wiring checked rather than assumed: **0 of 84 gmesh runs** had an unconnected
  MCP server or zero `mcp__*` calls, in either run (the failure mode the README's
  "arm whose MCP server fails to start" section exists for).

Everything except `G_MESH_BENCH_BINARY` was held identical between the two runs.

## Rep count, sized from measured variance

The project's rule is that reps come from variance, not convenience. The variance
used is GMB-150's own 5-rep sweep restricted to *these* 14 tasks and *these* two
arms (140 runs):

| arm | median per-task token CV | mean | max |
|---|---|---|---|
| `gmesh-configured` | **17.0%** | 17.5% | 52.2% |
| `baseline` | **19.1%** | 22.9% | 60.3% |

What that buys, for a paired per-task difference of means:

| reps | per-task SE | per-task 95% CI | pooled over 14 tasks |
|---|---|---|---|
| **3** | 9.8% | **±27%** | **±7.3%** |
| 5 | 7.6% | ±21% | ±5.6% |

**3 was chosen.** Stated honestly: pooled over the 14 tasks it resolves a
systematic shift of ~7% or more, and **per task it cannot resolve anything
smaller than roughly ±27%**. Five reps would have moved the pooled figure to
±5.6% for double the spend — not worth it for a declared sanity read, and the
per-task figure stays coarse either way.

The reason GMB-150 needed 5 does not transfer. It went to 5 because one task,
`tt-implement-release-cancelled-task-bug`, dominated a mean over 46 tasks of very
different sizes — and GMB-152 §1 then traced that task's noise to a **harness
defect**, not to sampling: its oracle runs three ordinary repo test files, so it
grades tests the agent wrote itself (GMB-153, still unfixed — re-verified in
`corpora/task-tracker-mcp/tasks.json` for this run;
`tt-implement-split-task-cancelled-release` has the same shape). A defect is not
averaged away by more reps, so it is reported per task with spread instead.

## The direct test: are the answers the same bytes?

The token sweep answers "did the agent behave differently", which is noisy and
indirect. The release's actual claim — *TS answers did not change* — can be
tested directly, for **zero API spend**, by asking both binaries the same
questions and diffing the responses.

20 queries covering **all 8 tools**, against a pristine clone of the pinned
revision with the index warmed (`g-mesh init`) exactly as the harness does, one
fresh temp project per build:

> **All 20 responses byte-identical. Same sha256 (`aee1095c…`).**

That includes `find_definition`'s `id` fields — symbol ids survive the schema
bump unchanged — `get_dependencies`' whole file lists, and `search_code`'s
similarity scores to full float precision (`0.5605289340019226`), despite
per-language semantic scheduling being one of the things 3.0.0 changed.

**The first attempt at this measured nothing, and that is worth recording.**
Without the `g-mesh init` warm-up every one of the 20 responses was the *"this
project's index is still being built"* placeholder — 453 bytes each, identical
across both builds, a perfect-looking null. Identical output is evidence only
once the output has content.

**The probe is shown able to separate the arms.** Re-run against the *same*
binary on a corpus perturbed by **one added file** (a new `CompletionVerifier`
implementor and a new `requireTask` caller), **5 of the 20** responses change,
across three tools: both `find_implementations` queries, `find_references
requireTask`, and both `get_dependencies … Incoming` queries. So 0-of-20 between
builds is a real null, not a dead instrument.

## The one thing that did change, and what it predicts

The MCP `tools/list` surface is the per-turn schema tax every g-mesh run pays.
Both builds expose the **same 8 tools, same names, same parameters**. The schemas
differ by exactly one description string:

```
2.12.1  "Project-relative path of the file to start from."
3.0.0   "Project-relative path of the file to start from. Also accepts the
         exact key of a logical container (a Go import path, a Rust module
         path, ...) to anchor on the package as a whole."
```

`get_dependencies` alone, 1475 → 1608 bytes; whole surface 9970 → 10103 bytes.
**+133 bytes ≈ +33 tokens per turn** — the containers feature announcing itself.

That is the *only* systematic token difference 3.0.0 predicts here. At GMB-150's
median 3 turns per tt run it is ≈100 tokens on a ~70,000-token run, i.e.
**+0.14%** — two orders of magnitude below what 3 reps resolve. **The token sweep
below cannot see the one change it should see.** It is there to catch a *large*
regression, not to confirm this number.

`g-mesh plugins list` reports `typescript 2.2.0 bundled` for both, and
`~/.g-mesh/plugins/` does not exist — so each binary used its own compiled-in
plugin and no shared on-disk plugin could confound the pair. 3.0.0 additionally
reports protocol-v2 capability flags (`semantic_pass=yes`,
`receiver_calls=unresolved`).

## The A/A control, and why it is the point

`baseline` ran in **both** sweeps. It never touches g-mesh, so the two baseline
columns are the same condition measured twice: their spread **is** the
run-to-run noise floor, measured rather than assumed.

| arm | mean per-task Δtokens | median | sd | 95% CI |
|---|---|---|---|---|
| `gmesh-configured` (under test) | **−2.2%** | +0.1% | 10.8 | [−7.8, +3.4] |
| `baseline` (**A/A control**) | **−2.2%** | −4.7% | 24.8 | [−15.2, +10.7] |

**The control drifted by exactly the same −2.2% as the arm under test**, with a
*wider* spread. Removing that drift:

> **Difference-in-differences (the g-mesh effect): +0.0%, 95% CI [−14.1, +14.2].**
> Mean turn change in the g-mesh arm: **−0.00 turns**.

The control also settles how to read the per-task column. Its biggest per-task
swings are **+74%** (`tt-scenario-bugtrace-createtasks-selfdep`), **−34%**
(`tt-implement-release-cancelled-task-bug`) and **−34%**
(`tt-scenario-deletesafe-taskcode`) — *with the identical binary at both ends*.
So a per-task swing of ±25% in the g-mesh column is noise, exactly as the ±27%
rep-count bound predicted.

## Every oracle failure, traced

Three failures across 168 runs, all on the same task and **all the same
assertion**:

| build | arm | rep | failing test | `mcpToolCalls` |
|---|---|---|---|---|
| 2.12.1 | `gmesh-configured` | 2 | `…still refuses to split a task whose release already shipped` | 3 |
| 3.0.0 | `baseline` | 1 | *(same assertion)* | **0** |
| 3.0.0 | `baseline` | 2 | *(same assertion)* | **0** |

All three are `tests/__bench_holdout__/split-cancelled-release.test.ts`, failing
`AssertionError: expected [Function] to throw an error`, with `1 failed | 97
passed`. The agent implements the cancelled-release case and drops the
already-shipped guard. GMB-152 explicitly classes holdout-file failures on this
task as legitimate signal (unlike the sibling task's, which are the GMB-153
defect) — so this is real task difficulty, not instrumentation.

**The only pass-rate drop between the builds is `baseline` 3/3 → 1/3, in the arm
that never calls g-mesh** (`mcpToolCalls: 0` on both failures). It cannot be a
3.0.0 regression; it is the same coin-flip that cost 2.12.1's g-mesh arm a pass
on the identical assertion. The arm under test moved the other way.

## Cold index

3.0.0 wipes and rebuilds every index once, so the one-time cost is part of the
release. Measured two independent ways on this corpus:

| | 2.12.1 | 3.0.0 |
|---|---|---|
| standalone, 4 interleaved reps each | mean 17.3s, range 14.6–21.9 | mean 17.8s, range 16.7–18.5 |
| in-situ (harness's own fresh clones), n=7 each | mean 15.7s, median 14.8s, range 14.0–20.7 | mean 15.5s, median 14.4s, range 14.1–22.2 |

**No measurable difference — the spread swamps it** (the slowest sample in each
set is that run's first, cache-cold walk). The resulting index is *identical*
every time: **843 nodes, 1259 edges, 183 imports linked, 371 symbols linked**, in
all 8 standalone runs of both builds.

Caveat worth stating: task-tracker-mcp is 48 files. **This says nothing about
what the one-time reindex costs on a large repo** — excalidraw, where GMB-150
measured a 211s cold walk, was not run.

## Machine state

This box's load average is not a usable measure of contention, and the write-up
would be wrong to quote it alone: at one point it read **172 with only 2 `rustc`
processes alive** and total CPU demand of 206% of 800%. Sampled every 30s
throughout, alongside real CPU demand and the runnable count:

| window | 1-min load (median / max) | sum %CPU of 800 (median / max) | runnable (median) |
|---|---|---|---|
| 2.12.1 sweep (01:10:49–01:44:33Z) | 5.2 / 72 | 100 / 565 | 2 |
| 3.0.0 sweep (01:50:49–02:25:53Z) | 4.2 / 17 | 90 / 579 | 2 |
| whole session | 4.8 / 236 | 101 / 630 | 2 |

Both sweeps ran in comparably quiet windows, the 3.0.0 one slightly quieter.
Since the measured quantity is tokens, not wall clock, load affects the result
only through the MCP-handshake failures GMB-150 hit — and none occurred here (0
of 84 gmesh runs mis-wired, in either run).

`durationMs` is again not used for anything.

## Verdict

**No regression found, on one corpus, and the null is a measured one.**

1. **Direct:** 20 of 20 tool responses byte-identical across all 8 tools, on a
   probe that a one-file change moves in 5 of 20 places.
2. **Behavioural:** g-mesh-arm effect +0.0% tokens [−14.1, +14.2] and −0.00 turns
   after subtracting drift measured by an A/A control that moved −2.2% on its own.
3. **Correctness:** g-mesh arm 41/42 → **42/42**. The only pass-rate drop is in
   the non-g-mesh control arm, on one known-hard holdout assertion.

Where it is honestly *"measured nothing"*: the **+33 tokens/turn** the enlarged
`get_dependencies` description must cost is far below this design's resolution,
and per-task token deltas below ~±27% carry no information — the A/A control
produced a +74% per-task swing with one binary.

## What was NOT measured

- **excalidraw — the entire second corpus**, deliberately out of scope. It is the
  larger, more ambiguous, higher-fan-out codebase, and it is where the linker
  changes (containers, structured placeholder targets) and per-language semantic
  scheduling have the most room to behave differently. **A no-regression claim
  for 3.0.0 in general is not supported by this note.**
- **The one-time reindex cost on a large repo** (see Cold index).
- **Any non-TypeScript language.** Containers are described in terms of Go import
  paths and Rust module paths; both corpora here are TS, so the feature's own
  target case is untested by this run.
- **Session-economy** (the amortized, many-questions-per-session shape) — only
  `token-economy` was run.
- **`gmesh-trusted`, `gmesh-configured-map`, serena and kungfu arms.**
- **Wall-clock/latency as a product metric** — `durationMs` is recorded but not
  interpreted, per GMB-150.
