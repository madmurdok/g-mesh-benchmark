## What improved, confirmed

- **`find_references` now actually works.** `tt-references-requiretask` was
  the one oracle failure in the v0.1.0 run (`turn-count-investigation.md`
  traced it to `find_references` returning empty for a symbol `find_callers`
  found real results for). Post-fix it passes, in fewer turns (7→4) and fewer
  tokens.
- Turn counts dropped on the two `find_implementations` tasks (5→3 each),
  consistent with `.claude/worktrees` duplicates no longer polluting
  `find_definition`'s candidate list (the other issue flagged in the same
  investigation doc).

## Two anomalies opened as new bugs in g-mesh (0.1.1 bugfix batch)

1. **`tt-deps-incoming-db-connection` regressed sharply**: 4→10 turns,
   ~6.5x tokens. This is the opposite direction from every other task.
   Filed as a g-mesh bug for investigation (see task tracker, project
   `g-mesh`, release 0.1.1) rather than assumed to be pure sampling noise,
   given the size of the swing.
2. **Token count rose on both `find_implementations` tasks despite fewer
   turns.** Fewer turns but *more* net tokens (and specifically more
   `cacheCreationTokens` per run: 2115→3154, 2035→3168) means each remaining
   turn carried more new, uncached content than before. Filed as a separate
   g-mesh bug — no stream-json trace exists yet for the post-fix runs to
   pin down why; needs one before concluding a specific root cause.

## Caveat, unchanged from v0.1.0

Still a single run per task/arm — real API non-determinism is a live
confound for every number above, including the two anomalies. The bug
tickets ask for a repeat/stream-json trace before committing to a code fix,
not a fix on the strength of one sample alone.
