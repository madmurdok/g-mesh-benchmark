# v0.16.0 — the repo-map ship gate: does pushed context pay for itself on `lookup`?

Date: 2026-08-13. g-mesh-bench task #106.

Measures the ship gate stated in
`g-mesh/docs/architecture/pushed-context-repo-map.md` ("Chosen Approach"):

> Before this is merged on by default, a g-mesh-bench arm (`gmesh` + map vs
> `gmesh` alone vs baseline) must show, on the `lookup` category specifically,
> either a turn-count reduction or a token reduction that exceeds the map's own
> per-turn cost. If it doesn't, the map ships as an opt-in flag and the default
> stays off — and that is a perfectly acceptable outcome for a research task.
> Re-baseline the current 8-tool `tools/list` payload first (C5).

The doc is explicit that a "no" is an expected outcome. This document reports
what was measured, not what was hoped for.

## 1. `tools/list` re-baseline (C5)

The last measurement (11,787 → 10,535 bytes, g-mesh tasks #90/#91, recorded in
`v0.2.0-session-economy-findings.md` §3) was taken on **seven** tools, before
`search_code` existed. Reproduced the same way it was originally taken — a live
stdio JSON-RPC session against the real server (`g-mesh mcp-shim`), not a read
of the Rust source, because MCP gives every tool a fully self-contained
`inputSchema` with no cross-tool `$ref` sharing, so shared-struct docs are
serialized once per tool on the wire.

Measured against the `release-2.2.0` build (commit `83b0f77`), 8 tools:

| Framing | Bytes |
|---|---:|
| Whole `tools/list` JSON-RPC response line | **9,898** |
| `result` object only | 9,864 |
| `tools` array only | 9,854 |
| `initialize`'s `instructions` (separate, not part of the above) | 1,804 |

Per tool (bytes of the serialized tool object):

| Tool | Bytes |
|---|---:|
| `find_implementations` | 2,153 |
| `find_references` | 1,324 |
| `get_dependencies` | 1,305 |
| `find_callers` | 1,186 |
| `find_callees` | 1,182 |
| `search_code` | 1,030 |
| `find_definition` | 971 |
| `get_file_outline` | 694 |

**Eight tools today cost less than seven did at the #91 measurement**: 9,898 vs
10,535 bytes (-6.0%), despite `search_code` adding ~1,030 bytes and
`find_implementations` growing (it is now the single largest tool, carrying the
`transitive` walk parameter added in `0bebc09`). The reason is a *second* trim
that post-dates the #91 numbers and was never written up here: `b200f79`
(2026-08-11) "perf(mcp): trim duplicated parameter prose from the tool schema".
Measured directly, by building `b200f79~1` and probing it the same way in an
isolated project root:

| Build | Tools | `tools/list` response |
|---|---:|---:|
| pre-#90/#91 (historical, from `v0.2.0-session-economy-findings.md`) | 7 | 11,787 B |
| post-#91 (historical, same doc) | 7 | 10,535 B |
| `b200f79~1` (measured here) | 8 | 11,775 B |
| `release-2.2.0` @ `83b0f77` (measured here) | 8 | **9,898 B** |

So the payload had crept all the way back to its pre-trim size (11,775 ≈
11,787) by adding `search_code` and the `transitive` parameter, and the Aug-11
trim then took ~1,877 bytes back out of it. Roughly ~2,500 tokens of always-on
tool schema at today's size, on the usual ~4 bytes/token rule of thumb.

Two caveats stated rather than smoothed over:

- **The exact framing of the historical 11,787/10,535 numbers is unrecoverable.**
  Whole-response-line, `result`-only and `tools`-only differ by just 44 bytes
  here, so the comparison is unaffected at any useful precision — but it is an
  inference, not a byte-identical reproduction.
- **The 7-tool historical binary could not be re-probed.** Building
  `792244a` (the #91 commit) succeeded, but its daemon refuses to bootstrap
  against the current `~/.g-mesh` state (schema/plugin vintage), so the two
  historical rows above are quoted from the earlier doc rather than re-measured.
  `b200f79~1` is recent enough to bootstrap, which is why that row could be
  measured directly.

**Consequence for this experiment**: the tool-schema surface did not grow under
the map branch. `git diff main...release-2.2.0` touches `core/src/mcp/` not at
all (only a one-line `pub mod map;` in `lib.rs`), so any measured difference
between the map arm and its control is the map, not a schema regression.

## 2. Experiment design

### The arms

| Arm | MCP tools | Project context in its cwd |
|---|---|---|
| `baseline` | none (Read/Grep/Glob only) | none |
| `gmesh-configured` | g-mesh's 8 | `CLAUDE.md` = corpus doc + the canonical g-mesh routing/trust guidance (3,235 tokens, measured in §3 — the design doc's "~2,000" is an underestimate) |
| `gmesh-configured-map` | g-mesh's 8 | the same `CLAUDE.md`, plus `@AGENTS.md`, plus an `AGENTS.md` carrying the generated repo-map block |

`gmesh-configured-map` is a new built-in arm (`harness/lib/armConfig.ts`,
`harness/lib/types.ts`, wired in `harness/token-economy.ts`), following the
existing configured-arm pattern: it shares `GMESH_ARM`'s tool list and MCP
config *by construction* (one shared `ArmDefinition` object), so the two arms
cannot drift apart in anything except the pushed context. It is opt-in behind
`G_MESH_BENCH_INCLUDE_GMESH_MAP=yes`, and its budget is
`G_MESH_BENCH_MAP_TOKENS` (default 1000), so the design doc's 500/1000/2000
sweep is a flag rather than an edit.

### How the map gets into the model's context

`g-mesh map --write` writes the marker-delimited block into `AGENTS.md`.
**Claude Code does not read `AGENTS.md` by itself.** Verified with a three-way
probe before spending anything on a run (identical prompt, identical flags, a
distinctive codeword in the file):

| Setup | Model's answer |
|---|---|
| `AGENTS.md` alone | "NONE" — it never saw the file |
| `AGENTS.md` + `CLAUDE.md` containing `@AGENTS.md` | the codeword |
| `CLAUDE.md` containing the text directly | the codeword |

So the arm ships the same one-line bridge file `g-mesh init --agent claude`
writes (`cli::agent_instructions::ensure_bridge_file`) — the real delivery path,
not a benchmark shortcut. Confirmed end-to-end on a real map arm cwd: asked
whether its context contained a "Repo map (g-mesh, …)" section, the model
answered `YES` and quoted the first file path in it (`src/db/connection.ts`).

One production-behaviour gap worth recording: `ensure_repo_map_block` silently
no-ops when the project has no `AGENTS.md` at all (by design — `g-mesh init
--agent` is the only thing allowed to create that file). Neither bench corpus
ships one, so the harness seeds a one-line `# AGENTS.md` first and then
**fails the run loudly** if the marker block is not present afterwards
(`corpusResolver.ts`'s `writeRepoMap`). A silently map-less "map" arm would have
invalidated the whole experiment.

### The binary under test

The map feature is on g-mesh's `release-2.2.0`, which is **not** merged to its
`main`. The bench resolves its binary from
`../g-mesh/core/target/release/g-mesh` (`harness/lib/mcpConfig.ts`), which was a
stale 2026-08-10 build with no `map` subcommand at all. Rebuilt from
`release-2.2.0` @ `83b0f77` (clean tree) before anything ran, and verified three
ways: `g-mesh map --help` prints the subcommand; the harness log records a real
`repo map written (…)` line per arm cwd; and the generated `AGENTS.md` was read
back and asserted to contain `<!-- g-mesh:repo-map:begin -->`.

Also relevant, and easy to get wrong: `g-mesh mcp-shim` is a thin client to a
per-project **daemon**, and an older shim happily reuses a newer daemon. A
tools/list probe therefore measures whichever build owns the daemon for that
project root, not the binary you invoked — which is exactly what happened on the
first historical probe attempt (it returned the current 8-tool payload). Every
number in §1 was taken in an isolated project root so the intended build was the
one bootstrapping the daemon.

### Corpus, category and repetitions

All 15 `lookup` tasks in the corpus (4 in task-tracker-mcp, 11 in excalidraw).
The design doc's "12 of 20" is the corpus as of `v0.2.0`; it has since grown to
45 tasks, of which `lookup` is still the largest single category.

`G_MESH_BENCH_REPS=low` (1 repetition), the setting prior session-economy work
in this repo settled on after a normal-reps run took ~8 hours. The trade-off is
stated plainly in §5: with n=15 paired tasks and one rep each, this run can
detect a *large* effect and cannot resolve a small one — which is adequate for a
gate whose passing condition is "a reduction that exceeds ~1,000 tokens per
turn", and not adequate for fine-grained ranking.

## 3. What the map actually costs per turn (measured, not estimated)

Before the behavioural numbers, the denominator of the gate. Measured with a
paired one-turn probe: the identical trivial prompt under the identical arm
config, from cwds differing only in their pushed context. A single-turn call's
`cacheCreation + cacheRead + input` is the whole prefix the model was sent, and
it came out byte-stable across two passes each, so these are measurements, not
estimates.

| Pushed context in the cwd | Prefix tokens | Delta |
|---|---:|---:|
| none (no `CLAUDE.md`, tools only) | 16,794 | — |
| + the routing/trust snippet (control arm) | 20,029 | **+3,235** |
| + snippet + map @ `--tokens 500` | 21,163 | +1,134 over control |
| + snippet + map @ `--tokens 1000` (default) | 22,097 | **+2,068** over control |
| + snippet + map @ `--tokens 2000` | 23,698 | +3,669 over control |

Two things here were not what the design doc assumed:

- **The map costs about twice its nominal budget.** At `--tokens 1000` the
  rendered block's own header says "986 tokens" and it costs **2,068** real
  ones; 500 → 1,134 (2.27×) and 2,000 → 3,669 (1.83×). g-mesh's budget
  accounting is a character-based estimate, and a repo map is the worst case for
  it: identifier-dense, path-heavy, punctuation-heavy text tokenizes at roughly
  2 characters per token, not 4. Whatever a user writes in `[map].tokens`, they
  should expect to pay about double. This is worth a follow-up in g-mesh
  independently of the gate — the config field currently promises a budget it
  does not keep.
- **The existing routing snippet costs 3,235 tokens per turn**, not the ~2,000
  the design doc assumes throughout. So the always-on pushed-context bill for
  `gmesh-configured` + map at defaults is 5,303 tokens per turn on top of a
  16,794-token base — a 32% prefix increase, of which the map is 12%.

## 4. Results: `lookup`, 15 tasks, 3 arms

`results/token-economy/2026-08-13T19-34-31-836Z.json` — 45 records, all
`status: ok`, no `budget_exceeded`, $3.50 of arm spend.

| Arm | n | mean turns | mean total tokens | mean cacheRead | mean cost | oracle |
|---|---:|---:|---:|---:|---:|---:|
| `baseline` | 15 | 3.40 | 44,928 | 39,239 | $0.0530 | 14/15 |
| `gmesh-configured` | 15 | 3.53 | 70,823 | 61,460 | $0.0822 | **15/15** |
| `gmesh-configured-map` | 15 | 3.73 | 77,374 | 65,677 | $0.0983 | 14/15 |

Paired per-task deltas (same task, same run, so corpus and prompt are held
fixed):

| Comparison | Δ turns (mean / median) | Δ tokens (mean / median / %) | tasks cheaper |
|---|---|---|---:|
| map vs `gmesh-configured` | **+0.20** / 0.00 | **+6,550** / +4,527 / **+9.2%** | 3/15 |
| `gmesh-configured` vs `baseline` | +0.13 / 0.00 | +25,895 / +16,386 / +57.6% | 2/15 |
| map vs `baseline` | +0.33 / 0.00 | +32,446 / +20,279 / +72.2% | 2/15 |

The map arm is **more** expensive than the arm it extends, and takes *slightly
more* turns, not fewer. The `gmesh-configured` vs `baseline` column reproduces
the known `lookup`-category picture from `v0.2.0-session-economy-findings.md`
(g-mesh costs more on `lookup`, where grep has no blowup to prevent); the map
does not soften it, it widens it.

### Isolating the map's own weight

The interesting quantity is not the raw delta — which necessarily contains the
map's own cost — but what the map *bought*. Using §3's measured 2,068 tokens per
turn:

> cost-adjusted saving = control tokens − (map tokens − 2,068 × map turns)

i.e. how many tokens the map arm would have saved if the map itself were free.

| | tokens |
|---|---:|
| mean cost-adjusted saving per task | **+1,170** |
| sd | 18,185 |
| standard error of the mean (n=15) | 4,695 |
| mean map cost per task (2,068 × 3.73 turns) | **7,720** |

So the map recovered roughly **15% of its own cost**, with an error bar that
comfortably includes zero. To pass the gate the saving would have to exceed
7,720 tokens per task; the point estimate is 6.6× below that.

Per-task detail, split by whether turn count moved:

- **On the 10 tasks where the map changed nothing about the turn count**, the
  token delta per turn was +1,751 to +2,418 on eight of them — i.e. the map's
  own prefix weight and nothing else — and −4,725 / −5,522 per turn on two
  (`ex-outline-types-vs-i18n`, `ex-find-callees-updateelbowarrowpoints`), where
  the map arm evidently read less to reach the same answer in the same number of
  turns.
- **The two worst regressions** were `tt-deps-incoming-db-connection` (6 → 7
  turns, +62,624 tokens) and `ex-references-getnondeletedelements-medfanout`
  (6 → 9 turns, +31,897). Both are multi-turn tasks where the arm wandered; see
  the noise section below before reading a mechanism into either.
- **Oracle**: the one map-arm miss was `tt-deps-incoming-db-connection`, where
  the agent's own grep undercounted importers and it corrected itself mid-answer
  — not a case of trusting the map over a query. No evidence in this run of the
  design doc's "agent answers from the map instead of querying" failure mode,
  but also no task designed to catch it (see §6).

### How much of this is noise

Four independent runs of this same session produced repeat measurements of the
same (task, `gmesh-configured`) pairs. They split sharply:

| Task | turns across runs | total tokens | sd |
|---|---|---|---:|
| `tt-find-impl-completionverifier` | 2 / 2 / 2 | 40k / 40k / 41k | 24 (0%) |
| `tt-outline-lifecycle-vs-small` | 4 / 3 / 4 | 69k / 45k / 69k | 13,805 (23%) |
| `tt-references-requiretask` | 6 / 6 / 5 / 4 | 108k / 108k / 63k / 85k | 21,394 (24%) |
| `tt-deps-incoming-db-connection` | 6 / 6 / 8 | 115k / 118k / 182k | 38,011 (27%) |

Two-turn tasks are essentially deterministic; anything that takes four or more
turns varies 23–27% run to run. That is exactly the population where a map could
plausibly help, and exactly where a single repetition cannot resolve a moderate
effect. It also means the two large map "wins" and two large "losses" above are
each within one run-to-run sd of their task's own noise, and should not be read
as mechanisms.

What survives that caveat: the map's *cost* is not noisy at all (§3, byte-stable
prefix measurements), and the mean cost-adjusted saving is 6.6× short of it. A
run this size can exclude a benefit large enough to clear the gate; it cannot
exclude a small one.

## 5. Budget sweep (500 / 1000 / 2000) — cost side conclusive, behaviour side not

The design doc flags 1,000 as an unvalidated default inherited from Aider.

**Cost side** (§3, deterministic): the map's real per-turn price is 1,134 /
2,068 / 3,669 tokens at 500 / 1,000 / 2,000. Sub-linear in the budget, because
the block's fixed header/disclaimer is amortized — but always ~2× the nominal
number.

**Behaviour side** (`…19-59-07-672Z.json`, `…20-02-25-696Z.json`): the four
task-tracker-mcp `lookup` tasks, control + map arm, at 500 and at 2,000.

| Map budget | Δ turns vs control (mean) | Δ tokens vs control (mean / median) |
|---|---:|---|
| 500 | −0.75 | −3,549 / +14,864 |
| 1000 (from §4, tt tasks only) | 0.00 | +15,426 / +7,365 |
| 2000 | −0.75 | +8,521 / +9,195 |

**This sweep is inconclusive and should not be quoted as a ranking.** n=4 tasks
× 1 rep, and one of those four (`tt-deps-incoming-db-connection`) has a 27%
run-to-run sd that alone accounts for the sign flips: its control arm alone
measured 6, 6 and 8 turns (115k / 118k / 182k tokens) across the three runs. The
mean/median disagreeing in sign in two of the three rows is the same story. A
usable sweep needs the full 15-task set at ≥3 reps per budget (~$30, ~6h), which
was not spent given §4's verdict.

## 6. Verdict and recommendation

### Gate: **FAIL**

> "…must show, on the `lookup` category specifically, either a turn-count
> reduction or a token reduction that exceeds the map's own per-turn cost."

- **Turn count**: no reduction. Mean turns went *up* (3.53 → 3.73, median delta
  0). Fails outright — this half of the gate does not even need the cost
  comparison.
- **Tokens**: no reduction. Total tokens went up 9.2% (+6,550/task). Netting out
  the map's measured 2,068-tokens-per-turn weight leaves a mean saving of
  +1,170 ± 4,695 tokens per task against a cost of 7,720 — 15% of its price,
  indistinguishable from zero.

The design doc anticipated this outcome explicitly ("If the bench shows no
turn-count reduction, the correct answer is to ship the `g-mesh map` CLI as a
useful inspection tool and leave the automatic injection off permanently").
Nothing here was massaged toward a yes; the raw run sets are in
`results/token-economy/` for re-analysis.

### Recommendation: keep `[map].enabled = false`

1. **Do not flip the default.** The feature costs a measured 2,068 tokens on
   every turn of every session in every project, forever, and bought ~15% of
   that back on the category it was designed for.
2. **Keep the `g-mesh map` CLI.** It works, it is fast (26–159 ms), the output is
   genuinely good orientation material for a human, and `--write` is the right
   escape hatch for someone who wants to opt in per project.
3. **Fix the budget accounting first, regardless of the gate** (suggested
   follow-up in g-mesh, not done here): `[map].tokens` under-counts by ~2× on
   identifier-dense text, so a user asking for 1,000 tokens of always-on context
   silently gets ~2,000. Any future re-test of this gate is measuring a
   mislabelled budget until that is fixed.
4. **If the gate is ever re-run**, three changes would make it decisive:
   - ≥3 reps (the 4+-turn tasks carry 23–27% run-to-run sd; n=15×1 has a
     ±4,695-token standard error on the quantity being tested);
   - session mode as well as isolated mode — the design's whole cost argument is
     about a prefix re-read on every turn of a *long* session, and
     `session-economy.ts` is where that compounding is visible;
   - a task whose oracle fails if the agent answers from the map instead of
     querying (the design doc's own residual-risk item). None exists today, so
     this run says nothing about that risk either way.

### Not measured

- **Snippet/map redundancy.** The design doc hypothesizes that the best
  configuration may be a *shorter* routing snippet plus a map, rather than both
  at full size. Testing it needs a fourth arm (map + trimmed snippet, and
  ideally map + no snippet), which is real harness work plus another full run;
  it was not done. What this run does contribute is the price tags: the snippet
  costs 3,235 tokens/turn and the map 2,068, so the question is worth about
  5,300 tokens/turn of always-on context — the largest single lever left in
  pushed context, and larger than the whole 8-tool schema (~2,500 tokens).
- **Session mode.** Isolated (`token-economy`) only, for cost reasons.
- **Corpora beyond TypeScript**, and monorepo behaviour at 100k files (the
  design doc's own open question). The excalidraw map at 659 indexed files
  already renders only ~10 files at the default budget.

## Reproducing

```sh
# arms: gmesh-configured, baseline (config) + the map arm (env)
G_MESH_BENCH_REPS=low \
G_MESH_BENCH_INCLUDE_GMESH_MAP=yes \
G_MESH_BENCH_MAP_TOKENS=1000 \
G_MESH_BENCH_HTML_NARRATIVE=no \
G_MESH_BENCH_WARM_CACHE=no \
npm run token-economy -- <the 15 lookup task ids>
```

Requires a g-mesh binary built from `release-2.2.0` (or later) at
`../g-mesh/core/target/release/g-mesh`, or `G_MESH_BENCH_BINARY` pointing at
one; `writeRepoMap()` fails the run loudly on a binary without `g-mesh map`.
