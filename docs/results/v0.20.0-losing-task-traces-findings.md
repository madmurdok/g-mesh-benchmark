# Why g-mesh costs more: it is the prefix, charged once per turn

**Runs**: `results/token-economy/2026-08-20T15-34-40-749Z.json` (8 tasks × 3 arms × 3 reps, $5.93)
and `2026-08-20T16-17-37-241Z.json` (the four-arm isolation below).
**Under test**: g-mesh 2.8.1, bench 0.20.0, with the per-turn instrumentation added in task
2c2617af.

The 2026-08-20 sweep established that 93% of g-mesh's premium is cache-read and inferred, from
serena as a control, that the driver was what the tools *return*. With per-turn data that inference
is now testable, and **it was wrong**. The driver is the prefix each arm carries before it does
anything, re-read on every turn.

## 1. The measurement that settles it

Every arm's first message caches a prefix: system prompt, tool schemas, and any project doc the arm
ships. Every later turn re-reads it in full. So the prefix is not a one-time cost — it is a cost per
turn.

Running the same task with the bare `gmesh` arm (tools, no project doc) alongside the configured one
separates the two halves for the first time:

| arm | prefix | what it carries |
|---|---|---|
| `baseline` | 12,280 | no tools, no doc |
| `gmesh` | 16,942 | 8 tools, no doc |
| `gmesh-configured` | 21,395 | 8 tools **and** the 28,900-char guidance doc |

- tool schema alone: **+4,662 tokens**
- guidance doc alone: **+4,453 tokens**
- together: **+9,115 tokens, charged again on every turn**

Roughly half each. (A chars-based estimate said 75/25 — the schema is denser per character than
prose. Worth recording as a caution against sizing prompt costs in characters.)

## 2. What that does to the tasks g-mesh loses

Per task, median of three repetitions. `prefix×turns` is the constant prefix delta multiplied by the
turns g-mesh took — arithmetic, not a fit:

| task | turns g/b | gap | prefix×turns | share of gap |
|---|---|---|---|---|
| `ex-default-export-dropdownmenu-group` | 4/3 | +49,404 | +35,828 | **73%** |
| `tt-outline-lifecycle-vs-small` | 3/2 | +39,048 | +27,354 | **70%** |
| `ex-namespace-import-laserpointer-plerp` | 4/4 | +38,327 | +35,828 | **93%** |
| `ex-deps-package-math-incoming` | 2/2 | +24,237 | +17,914 | **74%** |
| `ex-references-pointfrom-highfanout` | 2/3 | +10,768 | +17,914 | 166% |

The last row is not an error: g-mesh was *better* than baseline on everything except the prefix
there, and still lost, because the prefix alone outweighed what it saved.

## 3. The same penalty is paid on the tasks it wins

| task | turns g/b | gap | prefix×turns |
|---|---|---|---|
| `ex-ambiguous-exporttosvg-public-api` | 3/**11** | −157,300 | +26,871 |
| `tt-scenario-deletesafe-taskcode` | 3/**6** | −21,994 | +27,354 |

g-mesh carries the same handicap and wins anyway, by not taking the turns. Baseline's eleven turns
re-read its own 12,957-token prefix ten times — 129,570 tokens before a single tool result is
counted.

So the whole model is one line:

> **cost ≈ prefix × turns**, and g-mesh trades a bigger prefix for fewer turns.

It wins when the trade clears, loses when it does not. Every task above fits this, in both
directions.

## 4. What to change, with the number behind each

**a. Shrink the guidance doc (−4,453 per turn available).** It is 28,900 characters, and a large
part of it is *justification* rather than instruction — "measured: mean cost dropped ~38% … see
g-mesh's README", "verified empirically for this experiment with a three-way probe". The evidence
belongs in the findings docs it cites; the agent needs the rule. This is the cheapest lever in the
project: it is paid on every turn of every task, winning and losing alike, and no tool behaviour has
to change.

**b. Shrink the tool schema (−4,662 per turn available).** 9,854 characters over 8 tools, the
largest single declaration `find_implementations` at 2,153. Same shape as (a): descriptions that
explain when to use a tool, in a place that is billed per turn. This is bench task 188's subject;
what is new is the price tag and that it is only half the prefix.

**c. Trim high-fan-out payloads (worth ~6,000 on the two tasks where it appears).**
`get_dependencies` returned 16,324 chars on `ex-deps-package-math-incoming`; `find_references`
returned 18,793 on `ex-references-pointfrom-highfanout`. Real, but an order below (a) and (b), and
concentrated rather than universal. This is g-mesh task 55466232, whose premise — that payload is
the main lever — this document corrects.

**The trap to avoid, stated as measurement.** The guidance doc *already* tells the agent to read the
`files` array instead of paging rows on exactly these high-fan-out cases, and the agent took the
large payload anyway. Adding guidance to fix a payload problem costs +4,453 tokens **per turn, on
every task**, to change behaviour on a few; fixing the tool's default costs nothing at inference
time. The doc has been growing to compensate for tool defaults, and that trade is measurably bad.

**The constraint on all three.** g-mesh's wins come from turns it does not take (3 vs 11). A change
that saves prefix or payload but costs one extra round trip loses ~21,000 tokens on a g-mesh-sized
prefix — more than (a) and (b) together return. Total tokens per task is the metric; nothing else is.

## 5. What this run does not establish

- **Task-level variance is large.** `ex-outline-types-vs-i18n` was +168% in the sweep and −6,579
  here, on the same task definition. Three repetitions per cell is not enough to rank tasks by how
  badly they lose; it is enough to decompose a gap that exists.
- **No change was tested.** Every number above is the current build. The proposals are sized from
  what is being paid, not from a measured saving — (a) and (b) are upper bounds, reached only by
  removing the text entirely, which nobody is proposing.
- **The prefix figures are per-arm, not per-corpus.** Both corpora ship their own CLAUDE.md that
  every arm reads; that is inside all four prefix numbers equally and cancels in the deltas.
