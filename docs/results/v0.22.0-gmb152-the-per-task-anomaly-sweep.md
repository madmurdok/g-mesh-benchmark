# GMB-152: five anomalies, one of which invalidates a task

**Date:** 2026-08-26
**Data:** the 5-rep sweep — 690 `ok` records over 46 tasks × 3 arms, plus 600 saved transcripts
(`results/transcripts/2026-08-26T12-31-03-311Z/`). **No new run; cost zero.**
**Headline:** the corpus's most-cited noisy task,
`tt-implement-release-cancelled-task-bug`, is noisy because **its oracle grades tests the agent
wrote itself**. All three of its oracle failures are the agent's own test failing on its own setup
bug, in all three arms. That is not a difference between arms; it is a defect in the task.

## Flag definitions, stated before use

| flag | rule | why this threshold |
|---|---|---|
| `noisy` | `gmesh-configured` CV on turns > **23%** | not chosen here — 23% is `tt-implement-release-cancelled-task-bug`'s own measured CV, the figure GMB-141/143/150 already treat as "too noisy to trust at low reps" |
| `flaky:<arms>` | an arm passes some reps and fails others (`0 < pass < n`) | a task that is neither always-passable nor never-passable at fixed inputs |
| `flat` | **every** arm passes 5/5, turn spread across arms ≤ 1.0, and the slowest arm ≤ 4 turns | a task that cannot separate arms it cannot separate; the ≤4 bound keeps genuinely-easy-and-equal apart from equal-but-long |
| `inverted` | task declares `expectedWinner: gmesh`, yet g-mesh costs >5% more tokens **and** saves no turns (Δturns ≥ −2%) | the turn clause is the point: a token loss *with* a turn saving is the known per-turn prefix premium (GMB-145), not an inversion |
| `spiral` | a `gmesh-configured` rep at ≥2× that task's own g-mesh median turns and ≥8 turns absolute | median-relative so it scales with the task; the absolute floor stops 2t→4t counting |

27 of 46 tasks raise at least one flag. The table is at the end; the five findings are below.

## 1. `tt-implement-release-cancelled-task-bug`'s oracle grades the agent's own tests

Its `testCommand` is:

```
npx vitest run tests/lifecycle.test.ts tests/status.test.ts tests/ownership.test.ts \
               tests/__bench_holdout__/release-cancelled.test.ts
```

Only the last file is a holdout the harness copies in. The first three are **ordinary repo files in
the working tree the agent has just been editing**. Every one of this task's three oracle failures —
`serena` rep4, `gmesh` rep5, `baseline` rep5 — is a failure inside `tests/lifecycle.test.ts`, in a
test that **does not exist in the pristine checkout**:

| arm/rep | failing test name |
|---|---|
| serena rep4 | `release_task rejects a task that is already cancelled, and does not resurrect it to pending` |
| gmesh rep5 | `release_task rejects a cancelled task instead of resurrecting it as pending` |
| baseline rep5 | `release_task rejects a task that is already cancelled, instead of reviving it to pending` |

Three different names for the same intent is the giveaway: the agent wrote each one. The pristine
`describe("ownership conflicts (A3)")` block holds seven tests and **none** of them concerns
cancelled tasks (verified against `git show HEAD:tests/lifecycle.test.ts` in the cached corpus).

All three then fail identically:

```
TaskConflictError: Task <uuid> is currently held by session session-1; pass force to override
```

— the agent's own new test claims the task and then calls `release_task` from another session
without `force`. **The implementation under test is not what failed.** The oracle graded the agent's
test-writing, and did so equally badly in all three arms.

**This is the mechanism behind the CV that GMB-141, GMB-143 and GMB-150 each observed and none
explained.** It is also why the task reversed its own headline twice inside 24 hours (GMB-150 §2):
one draw of a self-inflicted test failure moves a 16-turn, 8.8%-of-the-sweep task.

**Fix, for a later task:** run the regression half of a test-mode oracle against a pristine copy of
those files, restored after the agent finishes, so only the holdout grades the agent. Note the
contrast with `tt-implement-split-task-cancelled-release`, whose three failures are all in
`tests/__bench_holdout__/split-cancelled-release.test.ts` — a genuine guard-pinning failure, and
legitimate signal.

## 2. `find_callers` → `find_references` costs 7 real turns, and GM-256's disclosure is visible

GMB-143 concluded the `excludedReferences` disclosure "cannot appear on a tool that is never
invoked". Across the 5-rep sweep it is invoked, and the disclosure does appear:

| | count |
|---|---|
| `find_callers` calls in `gmesh-configured` runs | 44 |
| responses carrying `excludedReferences` | **28 (64%)** |
| followed by `find_references` on the same anchor | 9 |
| …of which in the **same** assistant turn (parallel, free) | 2 |
| …of which in a **separate** turn (a real extra round-trip) | **7** |

Of the 7 paid re-asks, **4 followed a response that carried the disclosure**. So GM-256 is not
inert — but its measured effect is a *cost*: it tells the agent the page is incomplete, and the
agent spends a turn asking the question again with the tool that returns a superset.

| arm/rep | anchor | disclosure fired |
|---|---|---|
| `ex-implement-mutateelement-elbow-zero-position` rep3 | `Scene#mutateElement` | no |
| `ex-multihop-mutateelement-nondeleted-callers` rep3, rep5 | (by `symbol_id`) | yes |
| `ex-multihop-mutateelement-sizehelper-transitive` rep5 | `getSizeFromPoints` | yes |
| `ex-multihop-trail-impl-pointfrom` rep2 | `pointFrom` | no |
| `ex-scenario-impact-getelementabsolutecoords` rep1 | `getElementAbsoluteCoords` | yes |
| `ex-semantic-cjk-charclass-check` rep1 | `containsCJK` | no |

7 turns over 200 runs is 0.035 turns/run — small, but it is the **first intervention target in this
programme with a confirmed trigger in the traces** rather than a hypothesised one. The obvious shape
is to have `find_callers` return the excluded `REFERENCES` rows inline when they fit the page,
turning two turns into one; that is a g-mesh task, not a bench task.

## 3. Pool-mode oracle failures are undiagnosable from the record

`OracleCheckResult` computes `missed: string[]` — exactly which candidates were absent — and **both
write sites discard it** (`token-economy.ts:557`, `session-economy.ts:416`); only `reason` is
persisted, and `reason` is set by judge and test modes alone.

The consequence is concrete: the eight `ex-find-callers-mutateelement` failures (serena 4/5,
baseline 4/5) carry **no field at all** saying what was missed. Judge- and test-mode failures are
fine — their reasons are in `judgeReason`. Persisting `oracleMissed` is a two-line change to a
struct that already carries the data.

## 4. Four non-control tasks cannot separate the arms

`flat` fires on six tasks. Three are `ex-control-*`, where flatness is the *point* — a control that
discriminated would be the bug. The other four are a standing cost that settles nothing:

| task | turns g / s / b | Δtok | note |
|---|---|---|---|
| `ex-deps-package-math-incoming` | 2.4 / 3.0 / 2.2 | **+90%** | see §5 |
| `ex-scenario-impact-getelementabsolutecoords` | 2.2 / 2.8 / 2.2 | **+91%** | one grep answers it as well as one index call |
| `ex-semantic-cjk-charclass-check` | 4.0 / 3.0 / 3.8 | +83% | |
| `ex-semantic-collab-conflict-keep-local` | 3.8 / 3.4 / 3.0 | **+110%** | g-mesh is *slower* here, 3.8 vs 3.0 turns |

Per GMB-152's own brief these are reported, not acted on. But the point of the list is that each of
them charges the sweep a full 15 runs to restate that a one-call lookup is a one-call lookup — the
same objection that got GMB-143's task reverted.

## 5. `ex-deps-package-math-incoming` is the one place the arm abandons its own tool

The only task in the corpus where `gmesh-configured` runs made **zero** native calls — 2 of 5 reps —
and it is a `get_dependencies` task:

```
rep1  Glob(packages/math/src/index.ts) → gm:get_dependencies(index.ts)
rep2  Grep(from ["']@excalidraw/math)                       ← no index call at all
rep3  gm:get_dependencies(index.ts)
rep4  Grep(from ["']@excalidraw/math)                       ← no index call at all
rep5  Glob(packages/math/src/index.ts*) → gm:get_dependencies(index.ts)
```

Baseline runs the identical grep in all five reps. So in 2/5 reps the arm is baseline with a 9,123-
token prefix attached, and in 2/5 more it spends a Glob turn just to discover the `file_path` that
`get_dependencies` requires — the only tool of the eight that will not accept a symbol or a package
specifier. Both halves point the same way, and `get_dependencies` is also the least-used tool in the
sweep (3 calls, against `find_definition`'s 197).

## What was checked and found *not* to be a problem

- **`find_definition` as a warm-up.** 47 of 197 calls are followed by a graph query. 24 of those
  downstream calls actually passed the returned `symbol_id`, so the resolve was needed. Of the 23
  that re-anchored by name instead — the shape the guidance calls a wasted round-trip — **18 sit in
  the same assistant turn as the `find_definition`**, issued in parallel and therefore free. Real
  wasted round-trips: **5, across 200 runs** (`ex-control-i18n-dynamic-locale-import`,
  `ex-multihop-elbowarrow-routing-callees`, `tt-feature-bulk-cancel-epic-tasks`, and
  `tt-implement-split-task-cancelled-release` twice).
- **Costing more is mostly not an inversion.** Of 46 tasks, 15 cost fewer tokens than baseline and
  19 cost more *while saving turns* — the per-turn prefix premium, expected and already documented
  (GMB-145). Only **12** both cost more and save no turns, and of those 12 the 8 that also declare
  `expectedWinner: gmesh` are what the `inverted` flag reports.
- **No task is failed by every arm.** The `NO-ARM-PASSES` check fires nowhere.
- **`expectedWinner` is nearly uniform** — of the 46 tasks that ran, 31 declare `gmesh`, 11
  `parity`, 4 nothing. A field that takes one value on two thirds of the registry carries little; it
  is used here only through the `inverted` rule.
- **Two registry tasks never ran** — `ex-implement-library-dedup` and
  `ex-implement-linear-editor-order-crash`, 48 in the files against 46 measured. Not an anomaly:
  the run recorded `excalidrawScope: low`, which by design caps excalidraw's `implementation` tasks
  at the cheapest one because each pays a ~90s `yarn install` per (task, arm, repetition).

## What was filed off this

Per GMB-152's brief nothing here was acted on; four tasks carry the actions.

| finding | task |
|---|---|
| §1 test-mode oracle grades agent-authored tests | **GMB-153** — restore non-holdout regression files from the pristine revision before running |
| §2 `find_callers` → `find_references` re-ask | **GM-258** — return the excluded `REFERENCES` rows inline when they fit |
| §3 pool-mode failures carry no reason | **GMB-154** — persist `oracle.missed` |
| §5 `get_dependencies` needs an exact path | **GM-259** — accept a package specifier or module name |

§4's four non-discriminating tasks are deliberately **not** filed. Removing a task is a registry
decision with comparability consequences across every past sweep, and this note is evidence for that
decision, not the decision.

## Method, and what it cannot do

Records are de-duplicated by `(taskId, arm, repetition)` across the partial and final files, as
GMB-150 does. Tool sequences are walked from the transcripts by `tool_use` block, **de-duplicated on
the block's own `id`, not the message's** — the CLI re-sends an assistant message up to three times,
and a first attempt at this walker deduped on `message.id` and so dropped every tool call after the
first in any multi-block message, reporting five runs as having used no tools when they had.

CV at n=5 is a weak estimator; a single `noisy` flag is a prompt to open the transcript, not a
measurement. `spiral` fires on 2 runs in 200 and both were confirmed by reading the per-rep figures.
The `flat` threshold is a judgement call and is stated above so it can be argued with.

**Durations are not used anywhere here** — the sweep straddled machine loads of 5 and 150+ and
nothing in the record says which (GMB-150).
