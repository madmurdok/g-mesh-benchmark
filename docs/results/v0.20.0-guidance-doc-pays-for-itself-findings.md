# Cutting the guidance doc saves 2,776 tokens a turn and costs more than that in turns

**Runs**: `2026-08-20T16-17-37-241Z` and `16-43-33-786Z` (prefix isolation, before/after),
`15-34-40-749Z` (8 tasks, original doc), `16-45-43-526Z` (8 tasks, trimmed doc),
`17-23-05-779Z` (4 tasks, one imperative restored). ~$15 total.
**Under test**: g-mesh 2.8.1 + a trimmed `AGENTS_MD_SNIPPET`, bench 0.20.0.

**Result: the trim was reverted.** This documents why, because the reasoning generalises past this
one attempt.

## What was tried

`v0.20.0-losing-task-traces-findings.md` established that `cost ≈ prefix × turns` and priced the
prefix at +9,115 tokens against a no-tools baseline — about half tool schema, half the guidance doc
g-mesh ships and `init --agent` installs. The doc was 12,529 characters, much of it evidence for its
own rules ("measured: mean cost dropped ~38% … see g-mesh's README").

Cutting the evidence and keeping every rule took it to 5,385 characters, 57% smaller. The prefix
saving was exactly as predicted:

| | before | after | saved |
|---|---|---|---|
| tool schema | +4,662 | +4,308 | 354 |
| guidance doc | +4,453 | +2,031 | **2,422** |
| together, per turn | +9,115 | +6,339 | **2,776** |

The baseline arm's prefix was unchanged at 12,280, so nothing else moved.

## What it cost

Re-running the same eight tasks at three repetitions, four gaps shrank and four grew. The tool
sequences say why, and they are unambiguous — this is a behavioural change, not variance:

| task | before | after |
|---|---|---|
| `ex-references-pointfrom-highfanout` | `find_references` — all 3 reps | `find_definition` → `find_references` — all 3 reps |
| `ex-namespace-import-laserpointer-plerp` | grep-led, `find_references` mid-chain | `find_definition` → `find_references` — all 3 reps |

The agent started calling `find_definition` before the tool it actually wanted — a wasted round
trip, since those tools take `symbol_name` directly and return the declaration site in their
`anchor` field. Across the four affected tasks: **3 of 12 runs did this on the original doc, 9 of 12
on the trimmed one.**

At +6,339 tokens of prefix, one extra turn costs more than the trim saves on a three-turn task.

## The repair that did not work

The original doc states that rule twice — in `find_definition`'s own bullet ("skip this call when
the name is likely unambiguous… only when you expect ambiguity") and again in a "Typical flow"
bullet. The trim softened the first and dropped the second.

Restoring it as one emphatic sentence (**bold**, "calling it first is a wasted round trip") moved
the count from 9/12 to **8/12**. Effectively nothing.

So what made the rule stick was not any single sentence. Either the repetition across two bullets
did it, or the surrounding evidence made the rules salient enough to follow — this run cannot tell
those apart, and that is the interesting question, not the one it set out to answer.

## What this means

**The doc's 4,453 tokens per turn are not overhead. They are buying turns.** g-mesh's whole
advantage is answering in fewer round trips — three against baseline's eleven where it wins biggest
— and the doc is part of what produces that. Treating it as prompt bloat and cutting by volume is a
straightforward way to make the tool worse while making one metric look better.

**Bulk trimming is the wrong instrument.** A doc where 57% of the characters can be removed without
touching a single rule, and where doing so still changes behaviour, has to be cut one bullet at a
time with a measurement after each. That is a much longer piece of work than it looked, and it is
the only honest version of it.

**The schema half was kept** (−354 tokens per turn, g-mesh commit `27fc89c`): wording only, no
observed behaviour change. It is a small fraction of its own half, and the rest of that half is
per-field detail with the same load-bearing risk.

## What this run does not establish

- **Whether the net token effect is positive or negative.** Summed over the four re-measured tasks
  the trimmed doc is ~15k worse and the prefix saving over the same runs is ~39k — inside the noise
  this project has already documented (`ex-outline-types-vs-i18n` moved 174 percentage points
  between two runs of the *same* build). What is established is the tool-sequence change, which is
  consistent across every repetition.
- **Which part of the removed text was load-bearing.** Repetition and evidence were removed
  together. Separating them needs per-bullet ablation.
- **That the same applies to the tool schema.** Only the doc was ablated here.
