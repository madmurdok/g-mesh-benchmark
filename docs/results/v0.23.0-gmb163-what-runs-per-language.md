# GMB-163 — what actually runs, per language, before a corpus is authored

**Date:** 2026-09-20
**Binary under test:** `g-mesh 3.7.0`, built from `main` at `fcc7a4f` on 2026-09-20
**Probe:** `scripts/probeLanguageTiers.ts`, run outside the registry
**Corpora probed:** gin (Go), ripgrep (Rust), requests (Python) — shallow clones, not yet registered

This note exists because the batch it opens (0.23.0) authors three corpora on
one assumption: that a plugin answers. Nothing in this benchmark had ever
tested that assumption for Go, Rust or Python. Establishing it costs an hour;
discovering it wrong after three corpora are written costs the batch.

---

## 1. The benchmark has been pointing at a binary no build produces

`harness/lib/mcpConfig.ts` defaults to:

    ../../../g-mesh/core/target/release/g-mesh

That was right until g-mesh became a cargo workspace on 2026-09-16 (g-mesh
commit `0686d0d`, GM-295). A workspace member's build goes to the workspace
target directory, so since that day `cargo build --release` writes the core
binary to `g-mesh/target/release/g-mesh`, and nothing writes to `core/target/`.

Measured on this machine:

    core/target/release/g-mesh   g-mesh 2.12.0   built 2026-08-27
    target/release/g-mesh        g-mesh 3.7.0    built 2026-09-20

The old path still resolves, because the pre-restructure artifact is still
lying there. That is what makes it dangerous rather than merely wrong: a run
started without `G_MESH_BENCH_BINARY` spawns a g-mesh five minor versions old,
records `gmeshVersion: "g-mesh 2.12.0"` accurately, and every conclusion drawn
from it is about a build nobody meant to measure.

How far off that build is, from its own mouth:

    $ core/target/release/g-mesh plugins list
    go          error: plugin manifest ... declares protocol_version 2, but core
                expects protocol version 1 - refusing to load
    python      error: ... same
    typescript  error: ... same
    rust        error: ... same

    $ target/release/g-mesh plugins list
    go          0.2.0  bundled  semantic_pass=yes receiver_calls=resolved
    python      3.7.0  bundled  semantic_pass=yes receiver_calls=resolved
    typescript  2.2.0  bundled  semantic_pass=yes receiver_calls=unresolved
    rust        3.7.0  bundled  semantic_pass=yes receiver_calls=resolved

So on the stale default, a Go corpus would have indexed to nothing and
reported no error to the agent — an empty index, not a broken one. Filed as
**GMB-171**, deliberately outside this batch so the approved plan stays
approved.

Everything below uses the 3.7.0 binary, named explicitly through
`G_MESH_BENCH_BINARY`.

## 2. `plugins list` is a manifest, not evidence

All four plugins above declare `semantic_pass=yes`. That declaration is the
manifest's, and GM-341 is the reason it cannot be taken for the answer: on
Windows, Python's semantic tier could not start by any of its three routes
while two module docs asserted that it could. A capability claim in this note
is therefore always anchored to a call whose expected answer was read out of
the probed repository's own source first.

What the plugins need from the host, read from their source rather than
recalled:

| plugin | semantic tier resolves | present on this machine |
|---|---|---|
| go | `go` on PATH (`plugins/go/semantic.go:455`, degrades with a logged message otherwise) | **yes** — `/usr/local/bin/go` |
| rust | `rust-analyzer` (`plugins/rust/plugin.toml:74`) | **yes** — `~/.cargo/bin/rust-analyzer` |
| python | `pyright-langserver`, then `pyright`, then `npx pyright` (`plugins/python/src/semantic.rs:231`) | **no** direct binary; `npx` present |
| typescript | bundled (SEA) | n/a for this batch |

Two further host facts that the arms depend on, not only g-mesh:

- `gopls` — **absent**
- `pyright` / `pyright-langserver` / `basedpyright` — **absent**
- `uvx` — present, which is how the `serena` arms are launched

## 3. A second build-layout trap, found by falling into it

The rust and python manifests name a **debug** path for the structural binary:

    plugins/rust/plugin.toml:43    command = "../../target/debug/g-mesh-plugin-rust"
    plugins/python/plugin.toml:42  command = "../../target/debug/g-mesh-plugin-python"

A `--release` build of the workspace does not produce those. On this machine
`target/debug/g-mesh-plugin-python` did not exist at all, and
`target/debug/g-mesh-plugin-rust` was from 2026-09-16. The first probe run was
started in that state and was discarded rather than reported: it would have
measured which binaries happened to be lying on the disk, and a reader would
have seen "python: no answer" and read it as a plugin failure.

`cargo build --workspace` (debug) was run, both binaries dated 2026-09-20
19:04, and the probe re-run from a clean start.

## 4. Ground truth, read before the probe was written

Each probe carries the answer the repository's own source requires. These were
read from the pinned checkouts, not recalled:

**Go — gin.** `render.Render` (`render/render.go`, line 10 by grep — see the
line-numbering note below) has 15 implementors under
`render/`, every one of them satisfied implicitly: Go has no `implements`
keyword, so there is nothing in the text of an implementing type that names the
interface. This is the query no TypeScript corpus can ask, and it is why gin was
probed instead of cobra — cobra declares exactly one interface in the whole
repository (`SliceValue`, `completions.go:311`), which would have tested nothing.
`Binding` is declared twice, `binding/binding.go:32` and
`binding/binding_nomsgpack.go:30`, behind build tags — a real ambiguity case.

**Rust — ripgrep.** `Sink` (`crates/searcher/src/sink.rs:102`) has 9 impls across
four crates, three of them blanket or generic: `impl<'a, S: Sink> Sink for &'a mut S`,
`impl<S: Sink + ?Sized> Sink for Box<S>`, and the `UTF8<F>` / `Lossy<F>` / `Bytes<F>`
wrappers.

`RegexMatcher` is declared **four** times, not three. This paragraph originally
said three and named three crates, while §5 below reported g-mesh resolving to
a fourth location the count had never included — a document disagreeing with
itself one section apart. Corrected against the pinned revision (GMB-172, found
by the GMB-167 agent re-deriving it rather than trusting this note):

    crates/regex/src/matcher.rs:367      pub struct RegexMatcher          (production)
    crates/pcre2/src/matcher.rs:302      pub struct RegexMatcher          (production)
    crates/searcher/src/testutil.rs:24   pub(crate) struct RegexMatcher   (test helper)
    crates/matcher/tests/util.rs:9       pub(crate) struct RegexMatcher   (test helper)

Two are production matchers wired into `crates/core/search.rs`'s
`PatternMatcher` enum; two are `pub(crate)` test helpers. The finding in §5 is
sharper for the correction, not weaker: a bare-name query resolves silently to
one of the *test* helpers while four declarations exist. ripgrep is also a cargo
workspace, so it asks whether the plugin walks one at all.

**Python — requests.** `AuthBase` (`src/requests/auth.py:78`) is extended directly
by `HTTPBasicAuth` (:85) and `HTTPDigestAuth` (:124). `HTTPProxyAuth` (:116)
extends `HTTPBasicAuth`, not `AuthBase` — so a correct non-transitive answer
must **not** list it, and `transitive: true` must add exactly it. That pair is
the cheapest available test that the flag does something.

## 5. Results

**The chain holds for all three languages.** Every plugin spawned, every
project indexed, every tool answered. That was the question this task existed
to settle, and the answer is yes — so the corpus tasks below it are worth
writing.

**All three semantic tiers ran**, and the evidence is a call rather than a
manifest. `receiver_calls_structural=unresolved` holds for go, rust and python,
so a resolved receiver call is something only a semantic pass can produce:

    go      find_callers(Context.JSON)      15 rows, all resolved=true
    rust    find_callers(sink::Sink::matched) 3 rows, all resolved=true
    python  find_callers(HTTPAdapter.send)   1 row,  resolved=true

Python's single row is worth naming rather than rounding up — and the original
version of this paragraph got it wrong, which is corrected here (GMB-172, found
by the GMB-168 agent re-probing instead of accepting this note's framing).

It resolved `auth.py:272`. It did **not** leave `sessions.py:784`,
`r = adapter.send(...)`, unresolved, as this note first claimed. That call is
resolved — to `BaseAdapter.send`:

    def get_adapter(self, url: str) -> BaseAdapter:      sessions.py:870
    find_callers("BaseAdapter.send")  ->  Session.send @ src/requests/sessions.py

The receiver's type comes from the annotated return of `self.get_adapter(...)`,
so the edge binds to the interface-level declaration rather than to
`HTTPAdapter.send`, the concrete method that actually runs — `Session.__init__`
mounts `HTTPAdapter()` instances, but nothing in the annotation says so.

So the honest statement is not that the semantic tier's coverage is partial. It
is that asking for callers of a concrete override returns callers written
against the concrete type and not callers written against the interface:
defensible, arguably correct, and a different claim entirely from the one this
note first made. It is catalogued as a boundary rather than a defect in
`g-mesh/docs/architecture/tool-answer-guarantees.md` §2.

That settles the arm side for g-mesh. It does **not** settle it for serena:
`gopls` and `pyright` are absent from PATH on this machine, and only
`rust-analyzer` is present. Whether the serena arm installs its own server
through `uvx` was not established here and must be before GMB-169 reports a
three-arm table.

### The four findings worth carrying into the corpus tasks

**1. `get_dependencies` Incoming answers nothing when anchored by a file path,
and does not say so.** The parameter is called `file_path`, and on all three
languages an Incoming walk from a real file returns `results: []`,
`truncated: false` — a complete answer meaning "nothing imports this". It is
wrong. Anchored by the module's dotted name instead:

    get_dependencies("src/requests/adapters.py", Incoming)  ->  0 rows
    get_dependencies("requests.adapters",        Incoming)  ->  4 rows:
        src/requests/sessions.py, src/requests/models.py,
        tests/test_requests.py, tests/test_adapters.py

The mechanism is visible in the Outgoing rows: they come back as
`kind: "Module"`, `filePath: null`, `qualifiedName: "requests.auth"` /
`"grep_searcher::sink"`. Outside TypeScript a module is not a file, so a
file-anchored Incoming walk has no edge to follow. In TypeScript the two
coincide, which is why this has never shown up. g-mesh's own guidance —
"an `Incoming` walk already answers every file that imports this" — is
therefore true only for TypeScript, and an agent reading it on a Go repo gets
a confident zero. This is the same gap GM-259 already names for package
specifiers; on go/rust/python the specifier form is not a convenience, it is
the only form that works.

**2. Rust: a bare name can resolve, exactly and unambiguously, to a test
fixture.** `RegexMatcher` is declared four times in ripgrep. `find_definition`
returned one answer with `resolvedBy: "qualifiedName"` and no `ambiguous` flag
— `crates/matcher/tests/util.rs:8`, a `pub(crate) struct` in a test helper.
The mechanism is that the other three carry module-qualified names
(`matcher::RegexMatcher`), so the bare query matched the single declaration
whose qualified name *is* the bare name. Asking the way a Rust developer would
is worse, not better: `find_definition("matcher::RegexMatcher")` falls to
`resolvedBy: "semanticNeighbours"` — nothing structural matched at all.
Contrast Go, where `Binding`'s two build-tag declarations came back correctly
as `ambiguous: true` with both candidates.

**3. Rust: blanket impls are in the graph but not in
`find_implementations`.** `find_implementations("Sink")` returned 12 rows and
none of them is `impl<'a, S: Sink> Sink for &'a mut S` or
`impl<S: Sink + ?Sized> Sink for Box<S>`. Those impls are indexed — the very
next probe found them as callers, `sink::<&'a mut S as Sink>::matched` and
`sink::<Box as Sink>::matched`. So this is a reporting gap in one tool, not a
hole in the index. The same 12 rows also contain four exact duplicates
(`StandardSink`, `JSONSink`, `SummarySink`, `KitchenSink` each twice) and one
row that is a module rather than a type (`sink::sinks`).

**4. Go: `find_implementations` includes the anchor itself.** The `Render`
interface is returned as its own first implementor, with
`implementingSymbolId` equal to the anchor's `id`. Whether TypeScript does the
same was not established — the task-tracker-mcp daemon did not finish a cold
index inside the 10s bootstrap window, and chasing it was out of scope here.
That comparison belongs to GMB-166.

### Two corrections to my own expectations, recorded because they cut the other way

`find_references("HTTPBasicAuth")` returned three rows and I had expected uses
in `sessions.py`. The answer was right and the expectation was wrong: the
symbol is used in `models.py:40` and `models.py:685`, which is exactly what
came back. Had I not checked, a correct answer would have been written up as
a miss.

Go's `find_implementations("Render")` returned 20 rows where I had read 15
implementors out of `render/`. At least one of the extras — `TestRender` in
`context_test.go:1128` — is a genuine implementor my source read had missed
because I only grepped `render/`. The remaining reconciliation is left to
GMB-166, where the oracle has to be exact.

### `startLine` is zero-based, and every corpus oracle has to know it

g-mesh's `startLine` is consistently one less than the line a text search
reports, on all three languages — so it is core behaviour, not a plugin's:

    grep  render/render.go:10  type Render interface {     g-mesh startLine 9
    grep  auth.py:78           class AuthBase:             g-mesh startLine 77
    grep  auth.py:85           class HTTPBasicAuth(...)    g-mesh startLine 84

The response confirms it against itself: `find_definition("RegexMatcher")`
returns `"startLine": 8` beside `"source": {"firstLine": 9, ...}` for the same
declaration. `startLine` is a zero-based index; `source.firstLine` is the
one-based line a human would cite.

This has never mattered here because both TypeScript corpora grade on file
paths and symbol names. A ground truth that quotes a line — and a Go or Rust
oracle plausibly would, since several of these repos declare the same name in
several places — must be computed from the tool's own numbering, never from a
grep's.

### Cost, and one thing it implies

Indexing ripgrep took **552 seconds**, against 150s for gin and 152s for
requests, and a single `get_file_outline` against it took 33 seconds on a warm
daemon. ripgrep is 110 `.rs` files — small. Whatever that cost is, it is not
proportional to the corpus, and GMB-169 should expect the Rust arm to dominate
its wall clock. Machine state was not recorded alongside these numbers, so they
are reported as observations, not as measurements.

## 6. Raw probe output

The full run is reproducible with:

    G_MESH_BENCH_BINARY=<g-mesh>/target/release/g-mesh \
      npx tsx scripts/probeLanguageTiers.ts <probeDir>

where `<probeDir>` holds `go-gin`, `rs-ripgrep` and `py-requests` as shallow
clones. Every probe in that script carries the expectation it was written
against, so a future run shows a changed answer rather than a green tick.
