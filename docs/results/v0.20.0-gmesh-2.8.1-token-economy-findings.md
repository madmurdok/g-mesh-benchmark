# g-mesh 2.8.1: the transport rewrite did not move token economy

**Run**: `results/token-economy/2026-08-20T10-30-23-181Z.json` — 387 records, 385 `ok`, 2 `error`.
**Under test**: g-mesh 2.8.1 (`core/target/release/g-mesh`, rebuilt for this run), bench 0.20.0.
**Invocation**: `G_MESH_BENCH_WARM_CACHE=yes npm run token-economy` — normal repetitions,
`excalidrawScope: low`, arms `gmesh-configured`, `serena-configured`, `baseline`.
**Wall clock**: 196m55s. **Spend**: $39.55.

## Why this run exists

2.8.0 replaced the shim↔daemon transport with an IPC abstraction so the crate would compile on
Windows. g-mesh's task 216 measured what that did to Unix as a side effect: a flat ~152 ms cost on
large responses disappeared, p50 on the affected tools going 152.5 ms → ~1.0 ms.

A latency win is not a token win, and the two are routinely conflated when a project reports
benchmarks. This sweep asks whether the rewrite reached the metric this project actually optimises.
The expected answer was "no". Measuring it anyway is what makes the "no" quotable.

## 1. Nothing moved

`gmesh-configured` against the spread of the six prior full sweeps (2026-08-09 … 2026-08-16), all
of them on pre-port builds:

| metric | prior sweeps | this run | |
|---|---|---|---|
| median total tokens | 66,846 – 71,881 | **71,781** | inside |
| median turns | 3.0 (every sweep) | **3.0** | unchanged |
| arm spend | $12.09 – $12.95 | **$12.63** | inside |
| oracle pass | 126–129 / 129 | **129 / 129** | best-equal |
| median call duration | 9.8 – 10.0 s | **9.9 s** | inside |

Every number sits inside the band the same code produced before the rewrite. The last row is the
one that explains the rest: against a ~10 s median call, 152 ms is 1.5% — below the noise this
experiment can resolve, and invisible in a metric denominated in tokens rather than seconds.

**So: faster, and exactly as cheap.** The port is a portability and latency change; it is not a
token-economy change, and nobody should cite it as one.

## 2. The schema tax is growing, and that is a real finding

The one number that moved monotonically across all seven sweeps is g-mesh's median
`cacheCreationTokens` — the per-isolated-call cost of advertising its tool schema:

| sweep | 08-09 | 08-11 | 08-11 | 08-14 | 08-16 | 08-16 | **08-20** |
|---|---|---|---|---|---|---|---|
| gmesh-configured | 4,894 | 5,266 | 5,441 | 5,543 | 5,874 | 6,293 | **6,560** |
| baseline (control) | 5,224 | 2,913 | 2,872 | 3,165 | 2,986 | 3,016 | **2,958** |

+34% for g-mesh since 2026-08-09 while the baseline arm — which advertises no MCP server at all —
stays flat at ~3.0k. A monotone trend in one arm and a flat line in the control is not something
model nondeterminism produces.

Two things make it stronger, not weaker. This run had the prompt cache **warmed** (`WARM_CACHE=yes`),
which can only push cache-creation down, and it still recorded the highest value of the seven. And
the same 45 tasks were asked each time, so the growth is in what g-mesh advertises, not in what was
asked of it.

This is the subject of bench task 188 (*trim the tool-schema static tax*), which quoted 5.5k against
serena's 3k. The current figure is 6.5k. The task's premise has aged in the wrong direction.

## 3. Category-level verdicts from this registry are not usable

The obvious next move is to read per-category medians and attribute the movements. That move does
not survive its own control.

`baseline` contains no g-mesh. Nothing in this release can affect it. Yet its per-category medians
land outside the six-sweep spread in **four of eight** categories — `multi-hop` at 76.0k against a
prior range of 122.0–163.6k, a 38% drop in an arm that did not change.

The reason is sample size. Per arm, this registry gives:

| category | tasks | records |
|---|---|---|
| lookup | 15 | 45 |
| semantic-search | 11 | 33 |
| scenario | 5 | 15 |
| multi-hop | 4 | 12 |
| control | 3 | 9 |
| ambiguous-name | 2 | 6 |
| implementation | 2 | 6 |
| feature-request | **1** | **3** |

A `feature-request` "movement" is one task's three repetitions. `implementation` is two tasks.
g-mesh's own two out-of-band categories were `feature-request` (176.4k vs a 199.5–242.0k prior
range — one task) and `semantic-search` (72.4k vs a 66.9–71.9k range — +0.7% past the top, on the
second-largest cell). Neither is a finding.

Only `lookup` and `semantic-search` carry enough records to be worth a sentence, and both are inside
or a hair outside their band.

**Recommendation for future reports, including past ones in this directory**: category medians on
this registry are safe for describing *shape* — which categories g-mesh wins — and unsafe for
comparing one sweep against another. The arm-level aggregate is what has the n.

## 4. Where g-mesh still loses

Per task, median over three repetitions, g-mesh against baseline:

**Cheaper on 10 of 43 tasks; median delta +29%.**

Biggest wins — all of them questions with a graph-shaped answer:

| delta | task | g-mesh | baseline |
|---|---|---|---|
| −71% | `ex-ambiguous-exporttosvg-public-api` | 69k | 240k |
| −66% | `tt-scenario-deletesafe-taskcode` | 44k | 129k |
| −53% | `ex-multihop-mutateelement-nondeleted-callers` | 181k | 382k |
| −35% | `ex-implement-mutateelement-elbow-zero-position` | 209k | 320k |

Biggest losses — all of them questions grep answers in one pass:

| delta | task | g-mesh | baseline |
|---|---|---|---|
| +168% | `ex-outline-types-vs-i18n` | 86k | 32k |
| +164% | `ex-references-pointfrom-highfanout` | 76k | 29k |
| +120% | `ex-default-export-dropdownmenu-group` | 90k | 41k |
| +115% | `tt-outline-lifecycle-vs-small` | 73k | 34k |

This is the same shape every sweep has produced and matches how g-mesh's own README positions the
tool. Worth restating precisely because it did not change: the rewrite moved neither the wins nor
the losses.

### What the premium is actually made of

Summed over the 32 tasks where g-mesh costs more:

| component | tokens | share |
|---|---|---|
| `cacheCreation` — advertising the tool schema | 68,750 | 7.1% |
| `cacheRead` — the conversation prefix, re-read every turn | 899,297 | **93.3%** |
| `output` | −4,291 | −0.4% |

It is not extra round trips. On those same tasks g-mesh takes **fewer** turns than baseline (3.0 vs
3.5) and makes fewer search calls (2.0 vs 2.5). Each turn just carries more: median re-read per turn
21,870 against 12,907.

And it is not the schema, which section 2's trend might suggest. Serena is the control that
separates the two:

| arm | schema (`cacheCreation`) | turns | re-read per turn |
|---|---|---|---|
| baseline | 2,958 | 4.0 | 12,732 |
| serena-configured | 4,636 | 6.0 | 12,707 |
| gmesh-configured | 6,560 | 3.0 | **21,518** |

Serena advertises a schema 57% larger than baseline's and its per-turn read is baseline's, to within
25 tokens. A bigger advertisement does not raise the per-turn read. A bigger *answer* does, because
the answer lands in the conversation and is re-read on every subsequent turn.

The clearest case is `semantic-search` (11 tasks): g-mesh resolves it in 3 turns with **one**
`search_code` call and still reads 68,130 — about what serena reads across 6 turns and 2 calls, and
9.7k per turn more than baseline. The six highest per-turn reads in the whole sweep are all
`ex-semantic-*` tasks, every one of them a single MCP call. One large structured answer costs more,
for longer, than several small grep results.

So g-mesh saves turns and pays for it in payload — which is the opposite of the optimisation the
backlog was aiming at. Filed as g-mesh task 55466232 (trim what the tools return) with the caution
that matters: its wins come from answering in fewer turns, so an answer trimmed until the agent has
to ask again trades a 7% saving for a whole extra round trip.

## 5. Failures, counted rather than averaged away

Two records, both on `ex-multihop-mutateelement-nondeleted-callers` repetition 3, both `status:
error`: the `serena-configured` arm (5 turns, $0.05) and `baseline` (20 turns, $0.29). They are
excluded from every figure above. `gmesh-configured` completed all 129 of its records.

Oracle failures are inside the arm figures as recorded: baseline 121/128, serena 122/128,
g-mesh 129/129.

## 6. What this run does not establish

- **The first attempt aborted and is not part of these numbers.** `serena` failed to bring up its
  MCP server twice in a row, and the harness refused to record an arm that would have run on
  `Read`/`Grep`/`Glob` while labelled `serena-configured` — the guard working as designed. Cause:
  `uvx --from git+…/serena` takes over seven minutes when its cache is cold, against a much shorter
  connect timeout. The partial (48 records, $3.29) is kept as
  `2026-08-20T07-52-00-093Z-partial.json`; re-running with the warm-up on both fixed the flake and
  removed a caveat, since the warm-up catches a dead arm for the price of one prompt.
- **Whether prior sweeps ran with the cache warm-up is not recorded in their data.** It is bounded
  to the first call per arm and would depress cache-creation, so it cannot manufacture the section-2
  trend — but the comparison is not perfectly like-for-like and should not be presented as such.
- **Nothing here measures Windows.** The port's whole point is a platform this bench cannot run on.
- **The schema-versus-payload split is inferred, not measured.** Per-turn re-read is
  `cacheRead / numTurns`; the records carry no per-turn breakdown, so the split rests on the serena
  control rather than on direct attribution. The data to settle it already passes through the
  harness and is discarded — every `type: "assistant"` event in the `stream-json` output carries its
  own `usage`, and every `tool_result` block carries what a tool returned. Filed as bench task
  2c2617af.
