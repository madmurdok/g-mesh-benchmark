# GMB-157 — no demand for `get_diagnostics`, measured as an upper bound

**Date:** 2026-09-22
**g-mesh under test:** `g-mesh 3.10.0` (recorded on every `gmesh-configured` record)
**Arms:** `gmesh-configured`, `baseline`. Nothing else — see "What this contains no data on".
**Corpus:** task-tracker-mcp, pinned `35237c8bab17c6b9bf1939d0a06e9e5d1c36bf4f`.
**Repetitions:** n=3 on every variant, extended to n=8 on the deciding one. Sizing is
justified from this run's own observed variance below, not chosen for convenience.
**Raw:** `results/token-economy/2026-09-22T16-04-22-625Z.json` (stage 1, 18 records)
and `results/token-economy/2026-09-22T16-19-20-437Z.json` (stage 2, 10 records).
HTML: the two matching files under `results/html/`. Run logs were written to
`results/gmb157-stage1.log`, `results/gmb157-stage2a.log` and
`results/gmb157-stage2b.log` but are **not committed** — `.gitignore` carries
`*.log`. (The third is the stalled negative control; see "Can the comparison
tell anything apart?", demonstration 3.)

## The headline

**Arms with no diagnostics tool and no shell found a seeded `tsc` error every
single time, including the cross-file one, in two to five tool calls.**
Nothing in this sweep needs a diagnostics tool. Because the conditions were
rigged in that tool's favour — nobody here can run `tsc --noEmit` — this is an
**upper bound on `get_diagnostics`' benefit**, and an upper bound that came
back empty is the one direction in which this experiment can conclude
something firm.

**GM-198's decision stands.**

## Read this first: what this measures, and what it cannot

GM-198 declined to build `get_diagnostics` and named the experiment that would
overturn it: a bench task asking an agent what is wrong with a file carrying a
known diagnostic, run across `baseline`, a Serena arm that has diagnostics, and
`gmesh-configured`. Two of that sentence's three premises do not hold in this
harness. Both were settled deliberately on 2026-09-15 rather than worked around.

**No arm has diagnostics.** `harness/lib/armConfig.ts`'s `SERENA_DENIED_TOOLS`
denies `mcp__serena__get_diagnostics_for_file` and
`get_diagnostics_for_symbol` to `serena` and `serena-configured` alike, and this
task left that as it is. So this does not compare against a tool that has
diagnostics. It measures how badly arms *without* one do.

**No arm has Bash.** Checked rather than assumed: `armTools()` returns
`Read,Grep,Glob` for `baseline` and `Read,Grep,Glob,mcp__g-mesh__*` for
`gmesh-configured`. No agent here can run `tsc --noEmit`, which is the
real-world alternative to a diagnostics tool and the thing GM-198's own "if
baseline handles it with `tsc`" branch depended on.

Both absences push the same way, and that is what makes the result usable.
Removing the shell takes away reading's best instrument while leaving the
hypothetical tool's advantage intact. So the reading has to be asymmetric:

- If the arms find the seeded error by reading — cheaply and reliably, and
  above all on the **cross-file** variant — then there is no demand even under
  conditions favourable to the tool. **That conclusion is firm.**
- If they had failed, that would have shown **nothing about demand**. It would
  have licensed exactly one follow-up: a `baseline`-with-Bash arm compared
  against real `tsc`, before anything was concluded for g-mesh.

They did not fail.

## What this contains no data on

**Serena's diagnostics tools.** No arm in this harness may call them, so
nothing here says whether `get_diagnostics_for_file` would have won, lost, or
tied. Any future claim that Serena's diagnostics were measured and found
wanting cannot cite this document.

## The seeds

Three seeded variants plus a negative control, all seeding the same destination
path `src/domain/epicAudit.ts` into their own throwaway clone (`seedFiles`,
GMB-155). All derive from **one clean base file that compiles**: `tsc --noEmit`
exits 0 on a seeded clone at the pinned revision with the base in place. Each
broken variant differs from that base by **exactly one line**, and each produces
**exactly one** diagnostic — no incidental second error for an arm to find by
accident or for an oracle to accept instead.

That construction is the point. The local and cross-file variants are not two
different tasks that happen to both be about type errors; they are the same
file with the error's *provenance* moved, which is what makes the pair an A/B.

### (a) `tt-diag-local-literal-severity` — the control

`severityFor`'s first branch returns the string literal `"urgent"`.
`AuditSeverity` is declared 25 lines above it **in the same file** as
`"ok" | "warning" | "critical"`. Everything needed is on one screen.

```
src/domain/epicAudit.ts(35,53): error TS2322: Type '"urgent"' is not assignable to type 'AuditSeverity'.
```

If reading did not win here, the task would be broken, not the finding.

### (b) `tt-diag-crossfile-arity-requireepic` — the variant that decides it

`auditEpicLeases` calls `requireEpic(db, epicRef)` with two arguments.
`requireEpic` is declared in **another file**, `src/domain/epics.ts`, as
`requireEpic(db: DatabaseInstance, projectId: string, ref: string)` — three
parameters, because an epic's name is unique only within a project, so the
lookup has to be scoped by project id.

```
src/domain/epicAudit.ts(51,16): error TS2554: Expected 3 arguments, but got 2.
```

Two choices here are load-bearing.

**Arity, not a mismatched argument type.** A wrong argument type leaks: a model
can often guess that a field called `remaining_work` holds a string without
opening the file that declares it. An argument *count* cannot be guessed from
the call site at all. That makes "did the arm actually consult the neighbour"
an observable, not an inference.

**A decoy that points the wrong way.** The line immediately above is
`requireProject(db, projectRef)` — correct at two arguments, as are
`requireTask(db, taskId)` and every other `require*` helper in this repository
except `requireEpic` and `requireRelease`. The surrounding file positively
suggests that two arguments is the house style, so an arm reasoning from local
context alone should conclude the call is fine.

### (c) `tt-diag-crossfile-arity-unlocated` — confounded, reported anyway

Byte-identical seed to (b); the only intended difference was that the prompt
does not name the file. **It did not work, and the reason is worth more than
the variant was.** See "The confound" below.

### (d) `tt-diag-clean-no-error` — the live-arm negative control (authored, not run)

Seeds the **clean** base file behind the **byte-identical prompt** (b) uses —
a prompt which therefore states a falsehood, that the build reports exactly one
error in that file. Its rubric passes only an answer that refuses the premise.
Added after stage 1, for reasons given under "Can the comparison tell anything
apart?". **It produced no records** — its run stalled on the API and was
stopped. The task is committed and ready; it has never been executed.

## `revealsLocation`, and why

**(a), (b) and (d): `revealsLocation: true` — the prompt names the file.** The
capability under consideration is per-file: GM-198's `get_diagnostics` anchors
on a file or a symbol, and Serena ships
`get_diagnostics_for_file`/`get_diagnostics_for_symbol`. Naming the file is
therefore the condition *most favourable* to the tool, which is what an upper
bound needs, and it isolates the diagnostic step from the search step. Hiding
the file would mostly measure search ability — which a per-file diagnostics
tool does not supply either, so a loss there would not have been evidence for
it.

**(c): `revealsLocation: false`** was meant to measure the search step
separately. The field is accurate about the prompt. It turned out not to be
accurate about what the agent knows.

## `expectedWinner`, stated before the run

**`parity` on all four**, recorded in `corpora/task-tracker-mcp/tasks.json`
before a single rep executed. Neither arm has diagnostics and neither has a
shell, so there is no mechanism by which g-mesh's tools should change *whether*
the error is found; GMB-176 found g-mesh differing from baseline on cost, not
on pass rate. Parity on correctness is what happened; the cost difference is
reported below and is not parity.

## The confound in (c): a seeded file cannot hide

(c)'s prompt said only that `tsc --noEmit` failed *somewhere* in the repository
and that nobody had recorded where. All six runs went to `src/domain/epicAudit.ts`
first or near-first. None of them searched for it. Four said why, unprompted,
in their opening sentence:

> "I'll start by examining the **new untracked file** since it's the most likely source of a new type error." — gmesh-configured rep1
> "I'll look at the **untracked file** first since it's the most likely source of a new type error." — baseline rep1
> "I'll start by examining the **untracked file** and the project structure, since I can't execute `tsc` directly." — baseline rep3
> "...starting with the **recently added/changed files**." — gmesh-configured rep3

Claude Code's environment block reports the cwd's git status, and a seeded file
is untracked in the throwaway clone. The location was handed over for free.

The harness was cleared of blame before the environment was blamed:
`armPrompt()` appends a suffix only for `gmesh-trusted`, so `baseline` and
`gmesh-configured` receive the task prompt verbatim.

**So (c)'s 6/6 is not evidence that these arms can locate an unnamed type
error, and is not read as such anywhere in this document.** It is evidence for
something narrower and still true: given a file, they diagnose it. Which is
what (b) already says.

This generalises past this task, and is now recorded in the README's
`seedFiles` section: **`revealsLocation: false` is not achievable for any
`seedFiles` task**, because seeding either adds an untracked file or modifies a
tracked one and git status reveals either. A future task written to measure
whether an agent can *find* a broken file will silently measure whether it can
*diagnose* a named one, and will report a pass rate belonging to the wrong
question.

## Can the comparison tell anything apart?

A null is worth nothing until the instrument has been shown able to produce a
non-null. Three demonstrations, of decreasing remove from the real thing.

### 1. The grader discriminates (8 judge calls, $0.0633, 8/8 as intended)

Each rubric was fed hand-written correct and wrong answers, offline, before the
sweep:

| variant | answer fed to the judge | expected | got |
|---|---|---|---|
| (a) local | correct: the `"urgent"` return in `severityFor` | PASS | PASS |
| (a) local | plausible-but-wrong: blames the `as Task[]` cast | FAIL | FAIL |
| (a) local | shotgun: lists four candidates, commits to none | FAIL | FAIL |
| (b) cross-file | correct: `requireEpic` missing the project id | PASS | PASS |
| (b) cross-file | plausible-but-wrong: blames `requireProject` | FAIL | FAIL |
| (b) cross-file | "I read it carefully, there is no type error" | FAIL | FAIL |
| (c) unlocated | correct, with the file named | PASS | PASS |
| (c) unlocated | right diagnosis, wrong file (`board.ts`) | FAIL | FAIL |

The two failure modes that would most easily fake a pass — hedging across
several candidates, and confidently naming the wrong call — are both rejected.

### 2. The measurement responds to the manipulated variable

This is the demonstration that matters most, because it is made of real runs
rather than synthetic answers, and because the variable it responds to is
exactly the one under study — *where the information lives*.

(a) and (b) share a prompt shape and a file that differs by one line. If passes
were being handed out regardless of work done, the two would look alike. They
do not, in either arm, on any axis:

| | baseline (a) | baseline (b) | gmesh (a) | gmesh (b) |
|---|---|---|---|---|
| tool calls | 1–2 | 2–3 | 1 | 4 |
| left the seeded file | never | **every rep** | never | **every rep** |
| turns | 2–3 | 3–4 | 2 | 5 |
| tokens (min–max) | 26,570–41,329 | 41,614–43,487 | 45,670–46,052 | 70,781–71,070 |

Both arms' (a) and (b) token ranges are separated with no overlap. The
behaviour changed in the predicted direction because the information moved, and
by no other difference.

### 3. A live arm's answer, recorded FAIL end to end — ATTEMPTED, NOT OBTAINED

Demonstration 1 grades strings a human wrote. The gap it leaves is that no
*real* arm output has been shown to this instrument and recorded as a failure.
The negative control (d) was built to close that gap and **did not complete.**

The task is written, its seed is verified clean (`tsc --noEmit` exit 0), its
rubric is in `corpora/task-tracker-mcp/tasks.json`, and the run was launched
at `REPS=normal`. Its first arm call stalled on the Anthropic API — `ELAPSED
13:18` against `TIME 0:14.37` of CPU, process state `S`, i.e. waiting, not
working, with a `rate_limit_event` (`seven_day` utilization 0.52) visible in an
earlier transcript from the same sweep. After the same check returned the same
answer five times across thirteen minutes, the run was stopped rather than
checked a sixth time. **No records exist for `tt-diag-clean-no-error`, and none
are claimed.**

So the honest accounting of this section is: **demonstrations 1 and 2 hold,
demonstration 3 is outstanding.** Of the three, 2 is the one made of real runs
and the one aimed at the variable under study, which is why the conclusion is
not left hanging on the missing piece. But the specific reassurance (d) would
have provided — that these arms do not invent a type error when a leading
prompt insists there is one — is **not** in evidence here, and anyone extending
this work should run it first. It is six runs.

## Results

### Correctness

**28 of 28 graded runs passed.** Every record `status: ok`; no
`budget_exceeded`, no arm error.

| variant | baseline | gmesh-configured |
|---|---|---|
| (a) local | 3/3 | 3/3 |
| (b) cross-file | **8/8** | **8/8** |
| (c) unlocated *(confounded — see above)* | 3/3 | 3/3 |

`expectedWinner` was `parity` and correctness came out parity. The interesting
number is not that both arms passed; it is **how little it cost them** on the
variant that was supposed to be hard.

### Tokens and effort, with spread

Per-run totals (`input + output + cacheRead + cacheCreation`), reported as a
GMB-117 range rather than a mean.

| variant | arm | n | tokens (min–max) | median | turns | tool calls |
|---|---|---|---|---|---|---|
| (a) local | baseline | 3 | 26,570–41,329 | 26,724 | 2–3 | 1–2 |
| (a) local | gmesh-configured | 3 | 45,670–46,052 | 46,035 | 2 | 1 |
| (b) cross-file | baseline | 8 | 41,468–51,473 | 41,668 | 3–5 | 2–4 |
| (b) cross-file | gmesh-configured | 8 | 70,763–71,070 | 70,847 | 5 | 4 |
| (c) unlocated | baseline | 3 | 43,721–62,579 | 58,338 | 4–7 | 3–6 |
| (c) unlocated | gmesh-configured | 3 | 71,126–129,215 | 71,538 | 5–10 | 4–9 |

**On (b), the two arms' ranges do not overlap: baseline tops out at 51,473 and
g-mesh starts at 70,763.** At the medians g-mesh costs **1.70x** baseline for
the same 8/8 answer. That direction and rough size match GMB-176's headline
(g-mesh ~33% more across three language corpora, 97.2% of it `cacheRead`), and
it is worth restating in this document's own terms: **on the task a diagnostics
tool was supposed to be needed for, the arm carrying extra tool schemas paid
about 29,000 extra tokens per run and bought no extra correctness.** Adding a
further ~600-token tool to that side is the trade GM-198 declined.

The g-mesh side is also strikingly stable — 70,763–71,070 across eight runs,
a spread of 307 tokens, with an identical 5-turn/4-call shape every time.
There is no variance here to buy down with more reps.

## Per-rep tool sequences

This is the evidence the conclusion rests on. The question is not whether the
arms answered correctly — it is whether they *consulted the neighbouring file*
on (b), or guessed.

**They consulted it. 16 of 16 runs.**

### (a) local — nobody left the file, in either arm

| arm | rep | sequence |
|---|---|---|
| baseline | 1 | `Read(epicAudit.ts)` → `Grep(lock_expires_at)` |
| baseline | 2, 3 | `Read(epicAudit.ts)` |
| gmesh-configured | 1, 2, 3 | `Read(epicAudit.ts)` |

One file, one read, answer. `gmesh-configured` **never invoked a single g-mesh
tool** on this variant — with the whole MCP surface available and paid for, the
model correctly judged that reading one file was the entire job.

### (b) cross-file — every rep went and checked the signature

`baseline`, 7 of 8 reps, second tool call verbatim:

```
Grep {"pattern":"export function requireEpic|export function requireProject", "path": ".../src/domain", "output_mode":"content"}
```

It did not merely look up `requireEpic` — it grepped for **both** helpers in one
pattern, i.e. it went to check the decoy too. The 8th rep (n=8 rep5) skipped
grep and read the files outright: `Read(epicAudit.ts)` → `Read(epics.ts)` →
`Read(projects.ts)` → `Read(tasks.ts)`, which is also the most expensive run in
the cell at 51,473 tokens.

`gmesh-configured`, 8 of 8 reps, the same four calls every time:

```
Read(epicAudit.ts) → find_definition(requireProject) → find_definition(requireEpic) → find_definition(Task)
```

(rep1 of stage 1 ordered the two `find_definition` calls the other way round;
otherwise the sequences are identical across all eight runs.)

Both arms resolved the decoy and the real target. Neither guessed. The
difference between them is the *mechanism* — grep versus `find_definition` —
and it changed the price, not the answer.

### (c) unlocated — read in light of the confound

All six reps opened the seeded file first or near-first, four of them saying
they were going to the untracked file. Two runs did more work
(`gmesh-configured` rep3: 10 turns, 9 calls, 129,215 tokens, including
`find_references` on both `auditEpicLeases` and `requireEpic` and a read of
`tsconfig.json`), but none of them performed a search that had to *find* the
file, because none of them had to.

## How the reps were sized

Not chosen for convenience, and not fixed in advance beyond the first stage.

**Stage 1: n=3 on all three variants** (`REPS=normal`). n=1 is barred on this
project for anything but tool-sequence claims, and n=3 is the standing choice
for token comparisons.

**Stage 2 was made conditional on stage 1's observed variance, and written down
before it ran** (recorded on GMB-157 as a handoff note): any (variant, arm)
cell whose three reps disagreed on pass/fail would be extended first, because
that is where the variance would be; if every cell came back unanimous, the one
extension would go to **(b) alone** — the variant the ticket's conclusion rests
on — at `REPS=max`.

Every stage-1 cell was unanimous, so the pre-registered branch fired: (b) went
to n=8 per arm. That is the sizing argument in full — reps were spent where the
claim is load-bearing, not spread evenly over variants that had already
answered.

**What n=8 does and does not buy.** Sixteen consecutive passes bound the
per-run failure probability at roughly 17% (95%, one-sided). That is a real
limit and it is stated rather than glossed: this run cannot distinguish "never
fails" from "fails one run in eight". It does not need to. The claim being
made is not that reading is infallible; it is that reading is **sufficient and
cheap enough that a 600-token permanent schema tax does not pay for itself** —
and the cost half of that claim is measured with far more precision than the
correctness half (a 307-token spread across eight g-mesh runs).

## Machine state

Recorded because wall-clock numbers appear nowhere in the argument above, and
this is why. Load average ran 3.9–13.1 during the sweep (another session was
running `cargo test` on the same machine throughout), and the negative-control
run stalled on the API rather than on this box: `ELAPSED 12:05` against
`TIME 0:13.13` of CPU, process state `S`. Seconds of real time at ~0 user means
waiting, not working. Every claim in this document is made from token counts,
tool sequences and pass/fail, none of which that affects.

## Verdict for g-mesh GM-198

**Its decision stands, and this is the falsification test it asked for coming
back negative.**

GM-198 wrote: *"a bench task asking an agent what is wrong with a file carrying
a known diagnostic... If serena wins decisively the capability is worth 600
tokens; if baseline handles it with `tsc --noEmit` it is not."* It also
recorded, correctly, that the experiment could not be run at the time because
the harness could only seed files *after* the agent's turn. GMB-155 fixed that;
this is the experiment.

What came back:

1. **Arms with no diagnostics tool answered 28/28**, including 16/16 on the
   cross-file variant that was designed to be the one where type information
   should matter.
2. **They did it in 2–4 tool calls**, and the tool-sequence record shows they
   genuinely resolved the signature rather than guessing — `baseline` grepped
   for `requireEpic` *and* the decoy `requireProject` in a single pattern.
3. **They did it without a shell.** The condition GM-198 expected baseline to
   win under — `tsc --noEmit` — was never available. They won anyway.

That last point is what makes this an upper bound and what makes the negative
result strong rather than merely absent. A diagnostics tool's best case is an
agent that cannot compile the code. That case was measured, and reading still
sufficed at a cost of roughly 42,000 tokens a run.

Meanwhile the cost side got sharper, not softer: on the same variant
`gmesh-configured` already pays **1.70x** baseline's tokens for an identical
pass rate, ranges non-overlapping across eight runs. GM-188 priced a diagnostics
tool at ~600 tokens of schema on every isolated run whether called or not — a
12% rise in a tax GM-188 also found to be 58% prose and effectively
irreducible. This sweep found nothing on the benefit side to set against that,
under conditions chosen to favour it.

**Two things this does not say, stated so they cannot be misquoted later:**

- It says nothing about **Serena's** diagnostics tools. No arm here may call
  them.
- It says nothing about agents that **do** have a shell. If anything, such an
  agent's alternative to `get_diagnostics` is stronger than the one measured
  here, not weaker — which pushes the same way.

**Recommended follow-up, and it is small:** none that blocks anything. If
someone wants the remaining branch closed, the task is a `baseline`-with-Bash
arm graded against real `tsc` on these same four seeds — but that branch only
matters if the arms had *failed*, and they did not. What is worth doing
regardless is the README note this run produced about `seedFiles` and
`revealsLocation`, which is already written.
