# GMB-144: three quarters of an implementation run happens where no index helps

**Date:** 2026-08-25
**Answer:** on the two task-tracker implementation tasks, **70% and 80% of a g-mesh run's tokens
fall after the first `Edit`** — and `baseline`, which has no index to abandon, spends 73% and 76%
there. The phase is a property of the task, not a behaviour of the arm.
**Cost:** zero; all from saved transcripts.

## Why this was asked instead of a fifth intervention

GMB-141 found `gmesh-configured` stops using its index at the first edit — 0 of 64 post-edit search
calls native, against 37% before it. Four attempts to act on findings like that have returned
nothing (GM-237, GMB-139, GM-256, GM-257), each reasoned from what an agent ought to need.

So this asks a bounding question rather than a causal one. If the index is provably unused after the
first edit, the share of a run that falls there is a **ceiling** on what any navigation improvement
could ever move.

## The ceiling

On the two tasks with a substantial verify phase, navigation improvements can address at most the
pre-edit share: **20% and 30% of the run's tokens**. The elbow task is the exception at 86% pre-edit, and it
is the exception for a plain reason — its arm makes almost no post-edit calls, so there is barely a
verify phase to be excluded from.

Put against the sweep as a whole: 3 of 46 tasks have an edit phase at all. So the ceiling is not a
statement about the benchmark's headline, which is dominated by lookups where the index is the whole
job. It is a statement about **implementation work**, where most of the cost sits somewhere an index
was never going to reach.

## The finding that changes what to do next

`baseline` spends the same share there — 76% and 73% against g-mesh's 80% and 70%.

`baseline` has no index. There is nothing for it to abandon at the edit boundary, and yet its
pre/post split is the same shape. That makes the "collapse" GMB-141 named **not a behaviour to
correct**. Editing a file and checking what the edit touched is work that reads files and searches
text; it is not navigation, and an index answering "where is X declared" has little to offer it.

This reframes four null results at once. GM-256's disclosure, GMB-139's guidance sentence, GM-257's
source lines and GM-237's provenance field were all aimed, directly or indirectly, at making the
agent trust the index more. On lookups it already does — it opens with a native call in 93% of runs
and stops at the answer 60% of the time (GMB-142). On implementation tasks the majority of the cost
is in a phase where trusting the index more would change nothing, because baseline does the same
work without one.

## What this does not say

It does not say the post-edit phase is efficient, or that nothing could improve it. It says an
*index* is the wrong lever for it, on the evidence that an arm without an index spends the same
share of its run there. Something that made the verify phase cheaper — a way to check a diff's blast
radius without re-reading files, say — would be attacking the three quarters. That is a different tool,
not a better `find_references`.

## Method, and its rounding error

`perTurnUsage` is recorded per assistant message, **deduplicated by message id** — see the
correction above for what happens without that. The edit boundary comes from the order of
`toolResults`. A turn that contains both the first `Edit` and other calls is attributed whole to the
post-edit side. That inflates the post-edit share by at most one turn per run — against post-edit
phases of 8.8 and 17.4 turns, it does not move the conclusion, but it is the reason these figures are
quoted to two significant figures and not three.
