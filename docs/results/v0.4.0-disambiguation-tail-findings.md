# The "shared disambiguation tail" is not disambiguation, and not shared

Date: 2026-07-31. Investigation-only (task #47, release 0.4.0). No new
`claude -p` runs were made: everything below comes from re-reading run records
already in `results/token-economy/*.json` and `results/session-economy/*.json`
together with the live Claude Code transcripts under
`~/.claude/projects/-Users-Valentin-Taiurskii-Projects-excalidraw/*.jsonl` and
`.../-Users-Valentin-Taiurskii-Projects-ClaudeProjects-task-tracker-mcp/*.jsonl`,
plus a read of g-mesh's resolver (`plugins/js-ts/src/extract.ts`,
`core/src/graph/symbol_links.rs`).

Task #47's premise was that `ex-multihop-mutateelement-nondeleted-callers`
exposes a *cost floor both arms pay equally*: g-mesh flags real ambiguity
(`getNonDeletedElements` has three same-named declarations) but has no bulk
"which of these declarations does each of these N call sites resolve to"
primitive, so the gmesh arm falls back to the same ~83 single-file greps
baseline does. **That premise does not survive contact with the transcripts.**
The greps are real; what they are for is not what the premise says, and g-mesh
already answers the question the premise says it cannot.

## 3. Feasibility: g-mesh already does per-call-site disambiguation, at index time

A "bulk per-call-site disambiguation" tool would be redundant. The resolution
already happens during extraction and is already stored as edges; a
`symbol_id`-anchored `find_callers`/`find_references` *is* the bulk query.

`plugins/js-ts/src/extract.ts` classifies every call site by receiver shape,
which tree-sitter gives for free (`handleCall`, lines 1254-1298):

| Call-site shape | `receiver` | Resolution (`lookupCallTarget`, `resolveCall`) |
|---|---|---|
| `foo(...)` | `none` | file-local `Function` named `foo`, else this file's **import binding** for `foo` → pending placeholder → `core/src/graph/symbol_links.rs` follows the import and any re-export chain (≤ 8 hops) to the real declaration |
| `this.foo()` / `super.foo()` | `this` / `super` | member of the enclosing (or a named super-) type |
| `Base.foo()` / `NS.foo()` | `qualified` | member of that type/namespace when it is declared in this file |
| `someVar.foo()` | `qualified`, owner is a `Variable` | **deliberately no `CALLS` edge** — only a `REFERENCES` edge on the receiver |

Mapped onto the actual excalidraw case, where the three declarations are
`packages/element/src/index.ts:55` (exported standalone),
`packages/element/src/Scene.ts:50` (module-local `const`, not exported) and
`packages/element/src/Scene.ts:159` (`Scene#getNonDeletedElements`):

- `actionFrame.ts:46` — bare call after `import { getNonDeletedElements } from "@excalidraw/element"` → barrel hop → `index.ts:55`. Correct.
- `frame.ts:353` — bare call after `import { … } from "."` → `index.ts:55`. Correct.
- `Scene.ts:293,298` — bare call, and Scene.ts declares its own `const` of that name, which shadows the import lookup (`importedSymbol` is only consulted *after* the local lookup misses). Correct, and it never pollutes `index.ts`'s caller list.
- `app.scene.getNonDeletedElementsMap()` and every `this.scene.mutateElement(…)` in App.tsx — variable receiver → no `CALLS` edge. Correct by omission.

So the whole of #47's motivating case is resolvable syntactically, and *is*
resolved — the two caller lists in §1 are the proof. `lookupByName`'s doc
comment states the rule that makes this safe: "Ambiguity … yields nothing — a
missing edge beats a wrong one."

**What genuinely needs the deferred semantic layer** (g-mesh task #26), i.e.
what tree-sitter cannot do and no bulk primitive would fix:

- `someVar.foo()` where `someVar`'s type is not locally obvious. This is why
  `find_callers(Scene#getNonDeletedElements)` cannot return App.tsx: g-mesh
  systematically **under-reports method callers reached through a variable**.
  A false negative by design, not a wrong answer.
- `default` imports where the target exports its default under a declared name
  (`symbol_links.rs`'s own "What stays unresolved" list).
- A name exported by several nodes at once where the edge kind does not
  single one out.

None of these is the shape #47 describes.

### The real gap is an affordance, not a primitive

Nothing in g-mesh's tool surface tells the agent what a `symbol_id`-anchored
answer *guarantees*. `find_callers`'s whole description is *"List the functions
that call the given function."*; the `symbol_id` field doc is *"Id of the anchor
symbol, as returned by `find_definition`."* (`core/src/mcp/mod.rs:121, 212`).
Neither says the returned call sites are already resolved to that exact
declaration and exclude same-named ones — which is precisely the fact the agent
spends 20-80 greps rediscovering. The per-row `resolved: bool`
(`find_callers_callees.rs:79`), which is the honest signal for "this edge is
unconfirmed", is likewise undocumented in the schema.

The `gmesh-trusted` arm is the existing proof that closing this gap works: one
prompt sentence, zero tool changes, tail → 0.

## 5. Confirmed vs. open

**Confirmed by data:**

- The "disambiguation tail" on `ex-multihop-mutateelement-nondeleted-callers` is
  71.7% greps for the *unambiguous* symbol. It is hop-1 completeness distrust,
  i.e. the already-documented self-verification pattern, not per-call-site
  overload resolution. (9 `gmesh` + 2 `gmesh-trusted` transcripts.)
- g-mesh answers the task exactly and completely in 4 `symbol_id`-anchored
  calls; the two caller lists intersect to the judge's ground truth, reproduced
  identically in 4 independent runs.
- The shape occurs on **2 of 20** corpus tasks, both excalidraw, both
  "enumerate every file that…" phrasings. `task-tracker-mcp` shows it zero times.
- Ambiguity alone does not cause it: the same three-way-ambiguous symbol in
  `ex-references-getnondeletedelements-medfanout` costs the gmesh arm 0.6 manual
  calls against baseline's 6.6.
- Per-call-site disambiguation is already computed at index time from
  tree-sitter's receiver shape + the file's import bindings + re-export chains
  (`extract.ts:1254-1298, 1383-1438`; `symbol_links.rs`). A bulk primitive would
  be redundant.
- The tail costs ~11,171 tokens per call (R²=0.984) on a ~101k-token base, and
  is 54-72% of gmesh's spend on the two tasks where it happens.
- Removing the single tail task takes isolated-mode multi-hop from -23.4% to
  +3.8% — the category's gmesh advantage is one task, not a trend.
- The tail is fully eliminable without any tool change: `gmesh-trusted` → 0
  manual calls on both tasks; a 12-task session chain → 0-2 manual calls, 4/4
  oracle passes.

**Open / would need more investigation:**

- **Is the distrust ever load-bearing?** On these two tasks it bought nothing
  (`gmesh-trusted` matched or beat the natural arm's correctness). But g-mesh
  *does* under-report variable-receiver method calls by design, so "trust it
  blindly" is not universally safe. Quantifying that recall gap needs a
  targeted comparison against the ts-morph pools, not this task's data.
- **n is small where it matters most**: 2 tail tasks, 3 `gmesh-trusted` runs on
  them. `G_MESH_BENCH_INCLUDE_TRUSTED=yes` on a full corpus run would turn the
  cost-split numbers above from "measured on 2 tasks" into a category-level
  number. (Filed, see below.)
- **Why does the tail fire on some runs and not others** with an identical
  prompt (manual calls 1, 5, 6, 24, 48, 68, 69, 77, 83 across the nine
  plain-`gmesh` runs)? Bimodal, not a smooth distribution. This looks like a
  sampling/decision-point effect rather than anything about the task, and this
  investigation cannot separate them.
- **Two candidate-pool imprecisions** surfaced in passing and are not chased
  here: `ex-find-callers-mutateelement`'s pool includes `App.tsx`, which only
  calls the Scene method; `ex-ambiguous-exporttosvg-public-api`'s pool includes
  `packages/excalidraw/index.tsx`, which only re-exports the symbol
  (`index.tsx:415`). Both are generous pools with `minMatches` slack, so no
  recorded grade is wrong — but they make g-mesh look like it is missing
  callers when it is being correct.

### Correctness: where trusting cost something real

Category-level oracle pass rate (`gmesh` / `baseline` / `gmesh-trusted`):
`ambiguous-name` 17/17 · 17/17 · 8/8; `control` 14/14 · 14/14 · 7/7;
`multi-hop` 19/23 · 20/23 · 12/13; `lookup` **107/108 · 96/108 · 48/52**.

Every category is at or near 100% except `lookup`, where `gmesh-trusted`
(92.3%) noticeably underperforms plain `gmesh` (99.1%) — and it is not spread
thin across many tasks. Task-level detail:

| Task | gmesh | baseline | gmesh-trusted |
|---|---|---|---|
| `tt-references-requiretask` | 8/8 | 8/8 | **1/4** |
| `tt-deps-incoming-db-connection` | 7/8 | 8/8 | 3/4 |

`tt-references-requiretask` is the one real, concentrated correctness cost of
blanket trust found in this run: both `gmesh` and `baseline` pass it every
time, `gmesh-trusted` fails it 3 of 4. The task's own prompt is a direct

## 9. Correction: no resolver bug — it was g-mesh #99 a third time (2026-07-31)

§8's causal conclusion was wrong, caught by direct verification before
implementation started rather than after. Two long-lived daemons were found
serving `task-tracker-mcp` simultaneously: one (PID 67982) running since
`02:21` that morning — predating every fix landed that day, including #96 —
and a second (PID 50156) from `14:41`, running an intermediate worktree

Killing both and letting a fresh daemon bootstrap from the current binary
fixed both symptoms immediately, with no code change:

```

  39 real importers (was: {"results":[],"frontierNodes":[]})
```

Cross-file resolution for NodeNext `.js`-suffixed specifiers works correctly.

property of *which corpus happened to have a stale daemon*, not the trigger —
task-tracker-mcp's daemon simply hadn't restarted since before that day's
work, so it never got the chance to run #96's own fix. g-mesh #103 (the
resolver-fix ticket §8 filed) is cancelled as a result.

This is the third time #99's absence — nothing makes a running daemon notice
its own binary changed underneath it — has surfaced as a different-looking

caught before a fix was built for a problem that doesn't exist. #99's priority
