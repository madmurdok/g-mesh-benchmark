# GM-237: does `resolvedBy` change what the agent does, or just cost tokens?

**Date:** 2026-08-23 (superseding an earlier, invalid version of this note)
**Answer:** No measurable behavioural difference, at 15 runs a side with arms
proven distinguishable.

## What the first attempt got wrong

The first version of this note reported a null result off arms that were **the
same binary**. The control's edits were never committed, `git checkout` carried
them into the release branch's working tree, and the "with" binary was then
built from that same tree. Both arms were the control. The note was right by
accident and wrong in its reasoning, and the leak also shipped the control
condition into `release-2.11.0` until CI caught it.

Two rules came out of it and are now in the operator's CLAUDE.md: stage named
paths rather than `git add -A`, and build control variants in a `git worktree`.

## Method (the valid run)

- **Arms proven distinguishable before spending anything.** Same symbol through
  both binaries: `with` returns 331 bytes, `control` 302, differing by exactly
  `"resolvedBy":"qualifiedName"`. Compiler warnings about the control prove a
  property of the control, not a difference between arms — that confusion is
  what invalidated the first attempt.
- Control built in a detached `git worktree`; main checkout verified clean with
  `git -C`. The worktree needs its own `npm ci` — without it `build.rs`
  downgrades the plugin build failure to a warning and the binary answers
  nothing, which is GM-243's shape in a new place.
- Task `ex-default-export-dropdownmenu-group` (excalidraw), the only task where
  rung 4 fires. Arm `gmesh-configured` only. 15 reps a side.
- Control drops the field **and** the CLAUDE.md bullet that teaches it, since
  the two ship together.
- Raw transcripts saved (`G_MESH_BENCH_SAVE_TRANSCRIPTS=yes`).
- Load average 6.0 at the start, 11.3 at the end.

## Result

| | with `resolvedBy` (n=15) | control (n=15) | control, earlier batch (n=16) |
|---|---|---|---|
| `find_definition` alone | 12 | 12 | 15 |
| `find_definition -> Read` | 1 | 3 | 0 |
| `Grep -> Read` (tool unused) | 2 | 0 | 1 |
| mean tokens | 48,688 | 48,741 | 45,570 |
| oracle pass | 15/15 | 15/15 | 16/16 |

**Follow-up-read rate: 1/15 with, 3/31 across all control runs.** Mean token
totals differ by 53 tokens on ~48,700 — noise.

## The measurement's own variance is bigger than the effect

The two control batches are the same condition and produced **0/16 and 3/15**
follow-up reads. So a 3-in-15 difference between arms is inside batch-to-batch
variation, and nothing below roughly 20 percentage points is measurable here at
this n.

That is worth stating loudly because an intermediate 5-a-side result looked like
a clean, mechanistically satisfying signal — 0/5 against 2/5, exactly the
behaviour the field is designed to prevent — and it did not survive more reps.
This task has now produced two plausible-and-wrong effects at small n (the other
being GM-231's −14.3%, also one deviant run in three).

## What the transcripts show, which the numbers cannot

The two tool responses are byte-identical apart from 24 bytes at the front:

```
control:  {"ambiguous":false,"explanation":"No declaration is named ...
with:     {"resolvedBy":"fileName","ambiguous":false,"explanation":"No declaration ...
```

The `explanation` is the same in both and already says *"Re-query by one of
these ids"*. So the field is the only additional signal — and in the runs that
went on to `Read`, the agent did so with **no reasoning text at all** between
the two calls. Whatever drives that follow-up read, it is not deliberation the
transcript records, and it is not the presence or absence of the rung label.

## What the field costs

| rung | bytes | ≈ tokens |
|---|---|---|
| `id` | 18 | 4.5 |
| `qualifiedName` | 29 | 7.2 |
| `fileName` | 24 | 6.0 |
| `semanticNeighbours` | 34 | 8.5 |

Once per response, not per row. Ceiling 8.5 tokens per call against ~20,000 for
an extra turn.

## Recommendation

**Keep it, on cost rather than on demonstrated benefit** — unchanged from the
earlier note, and now resting on a valid measurement. At 8.5 tokens the field
can neither pay for itself nor fail to. The reason to keep it is that a
suggestion presented as a resolution is a correctness problem and this field is
what separates them on the wire; that argument was never about tokens.

What would be wrong is keeping it *believing it improves decisions*. Across 15
runs on the one task where its most interesting rung fires, it does not.
