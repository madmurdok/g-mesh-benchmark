# Calibrating the semantic threshold

**Date:** 2026-08-21
**Script:** `scripts/calibrateSemanticThreshold.ts`
**Raw data:** `results/semantic-threshold-calibration.json`
**Corpora:** both, at their pinned revisions, indexed to completion before any
query (excalidraw `1acf66ed`, task-tracker-mcp `35237c8b`)
**Cost:** no API spend — `search_code` against an already-built index

## The question

`docs/architecture/symbol-resolution-ladder.md` puts semantic neighbours on the
last rung before a refusal. That rung needs a cutoff, and the only evidence
before this was three hand-run queries: 0.61 for a right answer, 0.468 and 0.431
for junk. A line drawn between 0.47 and 0.61 on three points would have been a
guess wearing a number's clothes.

## Result: the distributions separate cleanly, and 0.60 is the cutoff

| | n | min | p10 | p25 | median | p75 | p90 | max |
|---|---|---|---|---|---|---|---|---|
| **right answers** (score of the correct hit) | 21 found of 26 | 0.472 | 0.615 | 0.643 | **0.684** | 0.781 | 0.831 | 0.892 |
| **no right answer** (score of the top hit) | 54 | 0.212 | 0.285 | 0.338 | **0.423** | 0.479 | 0.535 | 0.699 |

| cutoff | recall | false positives |
|---|---|---|
| 0.50 | 77% | 19% |
| 0.55 | 77% | 4% |
| **0.60** | **77%** | **2%** |
| 0.65 | 54% | 2% |
| 0.70 | 35% | 0% |

**0.60.** It keeps every right answer that 0.55 keeps — recall is identical —
while halving the false-positive rate, and 0.65 costs 23 points of recall to buy
nothing. The choice is not close, which is the useful part: a cutoff anywhere in
0.56–0.64 behaves the same, so this does not need to be tuned finely and will
not need re-tuning over small index changes.

Recall is against all 26 queries. The achievable ceiling is 21/26 = 81%, so 0.60
keeps **20 of the 21 findable answers (95%)**. The one it drops is `LaserTrails`
at 0.472, which was already ranked 7th — a hit the caller would likely have
skipped past anyway.

## The one false positive is a package specifier, and it should never reach this rung

The single negative above 0.60 is `@excalidraw/element` at **0.699**, landing on
`useExcalidrawElements`. By kind:

| negative kind | n | median | max |
|---|---|---|---|
| package specifier | 10 | 0.493 | **0.699** |
| path | 8 | 0.474 | 0.550 |
| invented identifier | 10 | 0.423 | 0.543 |
| symbol from the other corpus | 26 | 0.368 | 0.506 |

Package specifiers are the only kind that gets anywhere near the line, and the
reason is structural: **only declarations' doc comments and signatures are
embedded**, so a specifier has nothing to match and similarity is computed
against unrelated text. The same string scores 0.566 against the *task-tracker*
index, where no such package exists at all — so the high score is a property of
the query shape, not evidence about the corpus.

**Implication for GM-234:** guard on the query's shape, not only on the score. A
specifier-shaped query (`@scope/name`, or anything with a `/`) already has its
own rung — GM-232's path matching — and the semantic rung should decline it
outright. With that guard the false-positive rate at 0.60 is **0 of 54**.

That is cheaper and steadier than raising the cutoff to 0.70, which would clear
the same single false positive at the cost of 42 points of recall.

## Ranking is not the problem

Where the correct hit exists, it is ranked **first in 19 of 21** cases. So the
rung does not need to present long candidate lists: the top hit, or the top two
or three, carries essentially all of the value. This matters for the payload
budget — a candidate page is only worth its tokens if the answer is near the top,
and it is.

## What the 5 remaining misses are, and why two of them are not the tool's fault

- `export`, `command_palette` — these are not symbol names. They appear in
  `mustMentionSymbols` because the oracles use that field loosely. `export` is a
  keyword; the top hit was a component literally named `Export` at 0.880, which
  is arguably right and unverifiable. **Oracle-quality issue, not a search
  failure** — worth its own bench task.
- `DrawShapeTrail` → `AnimatedTrail#drawTrail` (0.779), `ExcalidrawImperativeAPI`
  → `App#createExcalidrawAPI` (0.839), `AppState` → `createAppState` (0.845).
  Genuine near-misses: closely related declarations, confidently scored, not the
  declaration asked for. **These are the reason the rung must present candidates
  rather than an answer.** A 0.845 hit that is not what you asked for is exactly
  the failure mode that makes a confident answer worse than a refusal.

## Two corrections to how this was measured

Both are recorded because each produced a plausible, publishable, wrong number.

**The first run queried a half-built index.** The script connected as soon as the
shim bootstrapped a daemon, and excalidraw takes ~7 minutes to walk. Every
excalidraw query returned "no correct hit" — 20 of 26 overall — which reads as
"semantic search finds nothing, do not ship this rung". It was wrong, and the
give-away was that `DropdownMenuGroup` had been observed scoring 0.61 by hand ten
minutes earlier. Fixed by calling the harness's own `warmGmeshIndex`, which
blocks until the walk finishes.

**The matcher then under-counted correct hits.** It compared only the *trailing*
identifier segment of `qualifiedName`, so `AppStateDelta#inverse` — a method of
the queried type, scored 0.831, ranked first — was recorded as a miss because the
last segment is `inverse`. Fixed to match any whole segment, which stays strict
where it matters: `createAppState` is a single segment and still does not match
`AppState`. That correction moved recall at 0.60 from 69% to 77%.

## Reproducing

```
npx tsx scripts/calibrateSemanticThreshold.ts
```

Needs the embedding model present. The right-answer set is read from the
corpora's `tasks.json` oracles rather than written by hand, so it cannot be
tuned to flatter the result; re-running after the corpora change will re-derive
it.
