# The semantic rung answers a question this agent does not ask

**Date:** 2026-08-21
**Subject:** g-mesh GM-234 — the resolution ladder's semantic rung
**Runs:** 24 total across four rounds, `gmesh-configured` and bare `gmesh`,
3 reps each. Records in `results/token-economy/2026-08-21T13-53-06-857Z.json`,
`…T14-03-44-391Z.json`, `…T14-47-21-652Z.json`, `…T15-16-53-173Z.json`
**Tasks added:** `ex-stale-name-canvas-search`, `tt-stale-name-doc-sync-check`

## The finding

**Across 24 runs, `find_definition` was called once.** The semantic rung
therefore fired once. Every other run reached for `search_code` — usually as
the very first tool call.

Three prompt shapes were tried, deliberately, because the first result looked
like a task-design failure and partly was:

| prompt shape | example | what the agent did |
|---|---|---|
| functional description | "the menu entry that saves the canvas as an image, which our notes call `ImageExport`" | `search_code` first, 6/6 |
| name only, no context | "a design doc refers to `ImageExport`. Find where it is declared" | `search_code` 5/6; **oracles failed** — the name alone does not determine which answer is right |
| name-led with minimal context | "our documentation refers to the canvas text-search panel by the name `CanvasSearch`. Find where that component is declared" | `search_code` first, 6/6, oracles pass |

The middle shape is the one that provoked the single `find_definition` call. It
also made the tasks unanswerable, which is its own lesson: a stale name with no
context has no verifiable right answer.

**It is not the guidance doc.** `gmesh-configured` carries the rule "default to
`search_code` when no symbol name is given", so that arm skipping
`find_definition` is expected. The **bare** arm, with no guidance at all, behaved
identically. Both were run precisely to separate "the doc steers them away" from
"they would not go there anyway", and the answer is the latter.

## Why the miss path may be unprovokable by prompt

The two requirements are in tension, and this is the part worth carrying
forward:

- For the rung to fire, the queried name must be **stale** — absent from the
  code.
- For an agent to query it with `find_definition`, the prompt must present it as
  **a name worth looking up**.

But saying "our docs call it `CanvasSearch`" is itself the signal that the name
may not be the code's. A model that reasons about the prompt reads that and goes
semantic directly — which is the correct move, and exactly what happened.

So the rung's audience is not an agent that reasons about naming. It is a client
that mechanically maps a name onto a definition lookup: an IDE-style "go to
definition", an integration that forwards a user's typed identifier, or a
weaker model. None of those are what this harness runs.

## Where the rung is right, and where it is wrong

Probed directly against both indexes, no model in the loop. This corrects the
scope claimed in GM-234's description, which said the semantic index generalises
to "a renamed symbol, an approximate name, a description instead of an
identifier".

| kind of stale name | query → top candidates | verdict |
|---|---|---|
| approximate / user-facing | `CanvasSearch` → `SearchMenu` | **right** |
| | `FrameName` → `getDefaultFrameName`, `App#renderFrameNames` | right |
| | `LaserTrail` → `AnimatedTrail#drawTrail` | right |
| | `command_palette` → `CommandPalette` | right |
| | `DocSyncCheck` → `checkDocSync`, `isDocDrifted` | right |
| **rename that changed the concept** | `draggingElement` → `snapDraggedElements`, `dragSelectedElements` | **wrong** — the answer is `newElement` |
| junk | `PriorityQueue`, `TaskLocking`, `FreedrawTool` | correctly refused |

**Renames do not generalise, and the reason is structural.** `draggingElement`
was renamed to `newElement` (excalidraw `3cf14c73`). Those two names are not
semantically close — a rename usually changes what the name *means*, which is
why it was worth doing. The embedding matches the old name's meaning, so it
returns the drag-related functions and misses the answer entirely. Any rename
that is more than a spelling change will behave this way.

The claim that survives is narrower and still useful: **the rung helps when the
stale name is a synonym of the real one**, and not when the concept moved.

## One run where the rung did fire, and it did not save a turn

`tt-stale-name-completion-check` rep 1: the agent called
`find_definition("TaskCompletionCheck")`, the rung returned `completeTask` as a
candidate — and the agent did not stop. It reformulated into `search_code`, read
`verification.ts`, and answered `GitDiffCompletionVerifier.verify()`, which is a
better answer than the oracle's.

Labelled candidates being treated as suggestions rather than answers is the
designed behaviour. But it means the rung did not remove the round trip in the
one instance where it fired. Whether a *correct* candidate would stop the agent
is untested — n=1, and this candidate was arguably wrong.

## Recommendation

Keep the rung: it is cheap, guarded, correct on the class of names it handles,
and silent on junk. Describe it as **shipped and unmeasured for this client**
rather than validated.

Do not keep tuning prompts to provoke it. Two rounds of that produced one
`find_definition` call and one broken task; a third would be fitting the
benchmark to the tool rather than measuring the tool.

If its value is to be demonstrated, the experiment is not a prompt — it is a
client that maps names onto lookups mechanically. That is outside this harness.
