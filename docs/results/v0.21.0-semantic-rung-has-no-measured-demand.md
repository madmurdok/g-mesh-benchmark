# The semantic rung answers a question agents do not ask

**Date:** 2026-08-21
**Subject:** g-mesh GM-234 — the resolution ladder's semantic rung
**Runs:** `results/token-economy/2026-08-21T13-53-06-857Z.json` (gmesh-configured),
`2026-08-21T14-03-44-391Z.json` (bare gmesh), 3 reps each, 2 tasks
**Corpus tasks added for this:** `ex-stale-name-image-export`,
`tt-stale-name-completion-check` (GMB-134)

## The finding

Across **12 runs and two arms, `find_definition` was called zero times.**

| arm | task | tool sequence |
|---|---|---|
| gmesh-configured | tt-stale-name | `Grep → search_code → Read` (×3) |
| gmesh-configured | ex-stale-name | `search_code → Read` / `search_code → Grep → Read` |
| bare gmesh | tt-stale-name | `Grep → search_code → …` (×3) |
| bare gmesh | ex-stale-name | `search_code → Grep → Read` (×3) |

Every run passed its oracle. The semantic rung never fired, because its trigger
— a `find_definition` call on a name with no structural match — never happened.

## Why this is the strong version of the result, not a weak one

The tasks were built specifically to provoke it, and they were verified against
the index before being written: `find_definition("ImageExport")` and
`find_definition("TaskCompletionCheck")` both miss every structural rung and are
answered by the semantic one, with the correct declaration among the candidates.

Both prompts **name an identifier explicitly** ("our release notes refer to it as
`ImageExport`"). That is the most favourable phrasing a symbol lookup can get. The
agent still reached for `search_code` and `Grep`.

And it is not the guidance doc's doing. `gmesh-configured` carries the CLAUDE.md
rule "default to `search_code` as your *first* move when no symbol name is given",
so that arm behaving this way is expected. The **bare** arm has no guidance at all
and behaved the same. Both were tested precisely to separate "the doc steers them
away" from "they would not go there anyway", and the answer is the latter.

## What it means for the rung

The rung is correct, guarded and cheap — it fires only on a total structural
miss, declines specifier-shaped queries before embedding anything, and falls
through to the previous terse refusal when it has nothing above 0.60 (GMB-133).
Its unit tests cover all of that.

What it does not have is **measured demand**. It is a safety net under a path
this agent does not walk. That is worth stating plainly rather than filing as
"verified, no regression", which is what a run of the untargeted task set would
have produced.

Three readings, and the evidence does not yet separate them:

1. **It is redundant with `search_code`.** An agent that reaches for semantic
   search directly gets the same answer without needing `find_definition` to
   forward the query. On this evidence that is the simplest explanation.
2. **It is insurance for clients that are not this one.** A different MCP client,
   a different model, or an integration that maps "go to definition" onto
   `find_definition` would hit the miss path routinely. None of that is measured
   here, and this harness cannot measure it.
3. **The corpora still do not provoke it.** Two tasks, one model, one phrasing
   style. Possible — but the phrasing was chosen to be maximally favourable and
   still failed to provoke it, which weakens this reading considerably.

## What would settle it

A task where semantic search is *not* a reasonable first move but a symbol
lookup is — for instance, a prompt that supplies a symbol name and asks a
question about that symbol specifically (its callers, its file), where the name
happens to be stale. There the agent should call `find_definition` or
`find_references` by name, and the miss becomes reachable.

Until then, GM-234 should be described as shipped and unmeasured rather than as
validated. The distinction matters: "no regression observed" and "the thing that
would have regressed never ran" are different claims, and only the second one is
true here.

## Method note

The expensive run was made targeted by a free one. `scripts/probeSemanticRung.ts`
asks which rung answers each oracle symbol, and a scan of recorded `toolResults`
showed which queries agents had historically made. Together they established,
before any spend, that the *existing* task set could not exercise the rung at
all — over all 26 oracle symbols it fires once, on `command_palette`, which is
not a symbol name but an artifact of an oracle using `mustMentionSymbols`
loosely. Running the default set would have produced a confident "no regression"
about nothing.
