# GMB-151: almost none of them

**Date:** 2026-08-26
**Answer:** of **138 greps across 230 `gmesh-configured` runs** on 46 tasks, **4 (2.9%)** re-ask a
question the index had already answered — all four on one task. **Zero** are index gaps. The
category that actually exists is different from the one GMB-142 named, and smaller than it too.
**Cost:** zero; all from the 5-rep sweep's saved transcripts.

## What GMB-142 said, and why this redoes it

That note counted "redundant" greps by testing whether a resolved `symbol_name` appeared as a
substring of the grep's pattern, first at 25%, then corrected to 19% after comparing returned paths.
Its own correction showed the method was still wrong in two ways: a grep after `find_definition` is
a *different question* (declaration ≠ usages), and paths, not patterns, decide whether a grep found
anything new.

Two more flaws surfaced here, both found by reading the traces rather than trusting the count:

- **Scoped native queries were being compared against unscoped greps.** A `find_callers` with
  `file_paths: ["packages/element/src/Scene.ts"]` answers a narrower question than a repo-wide grep
  for the same name, so the grep finding more files is not a gap. The first pass of this analysis
  reported one "index gap" on that basis. Corrected, **there are none.**
- **`Scene#mutateElement` and `mutateElement` are different symbols.** Matching on the bare tail of a
  qualified name conflated a method with a free function of the same name.

A third of greps search for a *shape* — `updates\.x \|\| |updates\.y \|\|`, `function require\w*Task`

a declaration, so they are asking something else.

## The 4 that are genuinely unnecessary

All four are on `ex-scenario-deletesafe-getrectangleboxabsolutecoords`, all pre-edit, all re-running
a symbol whose usage query had already returned the same paths. Nine other tasks contribute none.

**Post-edit: zero.** That is worth stating against GMB-141, which found native-tool use collapsing to
0% after the first edit. The agent does stop using the index there — but it does not spend the
difference re-asking answered questions. Whatever the post-edit greps are, they are new questions.

## The 40 "never asked" split, which is where the real number is

Grepping a plain symbol name without ever taking it to the index sounds like the bigger waste. It
mostly is not, once split by scope:

| | greps | mean response |
|---|---|---|
| **file-scoped** — "does *this file* mention X" | 31 | 343 chars |
| **repo-wide** — a usage question the index could have answered | **9** | 310 chars |

The 31 scoped ones are local existence checks against a named file. That is not what
`find_references` is for, and the responses are tiny.

Of the 9 repo-wide, most are not misses either:

| task | pattern | files found | reading |
|---|---|---|---|
| `ex-control-analytics-track-categories` ×4 | `ALLOWED_CATEGORIES_TO_TRACK` | 2 | a **control** task — the guidance doc says grep is the cheaper choice on simple lookups |
| `ex-stale-name-canvas-search` ×2 | `CanvasSearch` | **0** | a stale-name task by construction; the symbol does not exist, and the index would have said so too |
| `ex-namespace-import-laserpointer-plerp` | `laser` | 19 | a word, not a symbol |
| `ex-implement-mutateelement-elbow-zero-position` | `isElbowArrow` | 22 | a genuine symbol question |
| `tt-implement-release-cancelled-task-bug` | `releaseTask` | 5 | a genuine symbol question |

**So the honestly-actionable set is two or three greps out of 138.**

## What it costs

A grep costs at most one turn, and a turn on this arm is roughly 15,100 tokens with the 9,123-token
prefix charged on it. Four unnecessary greps is therefore an upper bound of four turns across 230
runs — **under 0.02 wasted turns per run**. Parallel tool calls share a turn, so the true figure is
lower still.

Set against the arm's measured +10.0% token premium over baseline, this is not where that premium
comes from. The premium is the prefix, charged per turn, on every task (GMB-145).

## Method, and what it cannot do

The classifier is a heuristic over `args` strings, not a parse. A pattern counts as a symbol
question only if it is a bare identifier or an alternation of bare identifiers longer than two
characters; anything carrying regex machinery is classed as a shape search, which will misfile a
pattern like `foo\(` that is really a symbol question. Scoping is read from the presence of a `path`
argument. **19 greps (13.8%) carry no parseable pattern and are reported as unclassified rather than
distributed** — if all of them were re-asks, the unnecessary share would still be under 17%, and
nothing suggests they are.

Path comparison uses the `paths` array the harness records per tool result, which is a list of files,
not of match sites. A grep that finds a *new occurrence in an already-known file* reads as
"no new paths" and would be counted unnecessary. That biases the 2.9% upward, not down.
