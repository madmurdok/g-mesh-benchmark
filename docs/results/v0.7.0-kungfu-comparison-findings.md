# kungfu comparison arm: findings

Task #57. Adds [kungfu](https://github.com/denyzhirkov/kungfu) — a comparable
Rust/tree-sitter MCP code-intelligence server — as a third comparison arm
alongside `gmesh`/`baseline`, and reports a real, paired, oracle-graded run
against it. Cross-references this project's own established rigor lessons
(taskDefHash staleness, paired-vs-unconditional reduction, pool-oracle
negation) rather than re-deriving them, since they apply to a new arm exactly
as they apply to `gmesh`/`baseline`.

## Tool-set decision

kungfu exposes 40 MCP tools (confirmed via a direct `tools/list` probe against
`kungfu mcp` v2.6.2 — 22,231 bytes of schema) against g-mesh's 7. Giving the
agent the full 40-tool surface would measure "retrieval quality *and*
schema-tax difference" conflated together — this project's own #90/#91
findings (`v0.2.0-session-economy-findings.md`) already established that
tool-schema tax is real and separately measurable. **Chose a curated 6-tool
subset** (`harness/lib/armConfig.ts`'s `KUNGFU_TOOLS`) matching g-mesh's 7
capabilities as closely as kungfu has analogs for, to isolate retrieval
quality as the variable under test:

| g-mesh tool | kungfu tool | fit |
|---|---|---|
| `find_definition` | `find_symbol` | good |
| `find_callers` | `callers` | good, exact |
| `find_callees` | `callees` | good, exact |
| `get_file_outline` | `file_outline` | good, exact |
| `find_references` | `search_text` | approximate — text/regex search, not a resolved-symbol reference walk |
| `get_dependencies` | `affected` | approximate — transitive-callers blast radius over the call graph, not an import/module graph |
| `find_implementations` | *(none)* | **gap** — kungfu has no interface/supertype tool in its 40-tool surface at all |

`find_implementations` is dropped rather than mapped to a poor substitute, so
the kungfu arm runs 6 tools against g-mesh's 7 — stated here, not silently
normalized away. Both `find_references`→`search_text` and
`get_dependencies`→`affected` are structural mismatches (kungfu's graph is
call-based only; it has no general reference-graph or import-graph tool
distinct from the call graph) — a real architectural difference from g-mesh's
node/edge taxonomy (`DEFINES`/`IMPORTS`/`CALLS`/`REFERENCES`/`SUPERTYPE_OF`/
`EXPORTS`), not just a naming gap.

## Run

`G_MESH_BENCH_REPS=low`, both corpora, 7 tasks spanning `lookup`,
`ambiguous-name`, and `multi-hop` categories (task-tracker-mcp:
`tt-find-impl-completionverifier`, `tt-deps-incoming-db-connection`,
`tt-references-requiretask`; excalidraw: `ex-references-pointfrom-highfanout`,
`ex-find-callers-mutateelement`, `ex-ambiguous-clamp-math-utils`,
`ex-multihop-mutateelement-sizehelper-transitive`) — a deliberately small
first pass per task #57's own "keep it small and cheap first" scope, not a
full-corpus run. 21 runs (7 tasks × 3 arms × 1 rep), real spend $1.39.
Recorded at `results/token-economy/2026-07-31T21-27-56-212Z.json`.

kungfu writes a `.kungfu/` index directory into its cwd (unlike g-mesh, which
indexes into `~/.g-mesh`) — the arm runs against a throwaway `resolveFresh()`
clone per corpus, never the live registry-registered checkout, per task #57's
explicit constraint (see `harness/token-economy.ts`'s `kungfuCwd` handling).

## A grading bug found and fixed along the way (task #58)

The first pass of this run scored kungfu 4/7 on oracle correctness — worse
than baseline. Before trusting that number, each kungfu "failure" was
checked by hand against its resultText, following this project's own standing
practice of verifying a surprising result before writing it down (see
`v0.4.0-disambiguation-tail-findings.md`, `docs/gmb-correct-false-resolver-bug`
for precedent). Two of the three were false negatives in this project's *own*
pool-mode negation guard (`checkPool`, added by task #53 this same project) —
kungfu had answered both `tt-references-requiretask` and
`ex-multihop-mutateelement-sizehelper-transitive` completely correctly, naming
every real pool candidate affirmatively.

Root cause: the negation guard scanned a flat ±150-char window around each
candidate mention for *any* negation cue, with no check that the cue was
actually about that candidate. kungfu's answers are more discursive/bulleted
than gmesh's or baseline's typical answers in this sample, and on multi-line
markdown a negation about a *different* file in an adjacent bullet or aside
(e.g. "it does **not** call `requireTask`" about an unrelated decoy helper,
or "**Excluding** that definition file ..., the other callers are: X") landed
within the window of a real, affirmed mention purely by document layout.
Confirmed this wasn't fixable by shrinking the radius — the false positives
triggered as close as 20 chars while the original calibration case needs
~100, so the two ranges overlap and no single threshold separates them.

Fixed in task #58 by bounding the window to the candidate's own line (never
crossing a newline) in addition to the existing char cap — see
`harness/lib/oracleCheck.ts`. Both real false positives now grade correctly;
all 4 pre-existing negation tests (2 true-positive, 2 true-negative
calibration cases) are unaffected, since those are single-paragraph prose
with no line structure to narrow against. The stored run's `oraclePassed`
values for these two `(kungfu)` rows were corrected in place after the fix
landed (re-graded from the same `resultText`, not re-run — no additional API
spend); the HTML report was regenerated to match.

**This may have affected historical pool-mode grading on other, non-kungfu
runs too**, wherever a multi-line answer used "excluding"/"except" near an
affirmed candidate in a different clause, or a stray negation landed in an
adjacent bullet. No general re-audit of historical results is launched here —
flagged for awareness; task #58's own scope was limited to the fix itself.

## Corrected results (post-#58)

| arm | n | oracle pass | mean tokens | mean turns | total cost |
|---|---|---|---|---|---|
| gmesh | 7 | 7/7 | 71,323 | 3.43 | $0.4406 |
| baseline | 7 | 6/7 | 65,180 | 4.57 | $0.4092 |
| kungfu | 7 | 6/7 | 85,064 | 5.00 | $0.5361 |

- **Correctness**: gmesh and kungfu/baseline are much closer than the raw
  (pre-fix) numbers suggested — 7/7 vs 6/7 vs 6/7, not 7/7 vs 6/7 vs 4/7. All
  three miss the *same* task, `ex-find-callers-mutateelement`
  (`minMatches: 6` of 13 pool candidates) — baseline and kungfu both name
  real, distinct-but-different callers of `mutateElement` and both land at
  4/13 pool matches. This reads as a genuine completeness gap shared by
  non-structural (or partially-structural) call-graph search on a
  high-fanout target, not something that distinguishes kungfu specifically —
  gmesh's edge here traces to its ts-morph-grounded candidate pool being a
  structurally complete reference set that grep/call-graph tools don't
  reliably reproduce in full, echoing this project's own outlier-close-reading
  finding (`v0.4.0-outlier-close-reading-findings.md`) that fan-out tasks are
  where structural indexing earns its keep.
- **Token economy**: kungfu is the most expensive arm on this sample — +19.3%
  tokens vs gmesh, +30.5% vs baseline — despite running a *smaller* curated
  tool set (6 tools) than gmesh's 7. The gap is driven by turn count (5.00
  mean turns vs gmesh's 3.43), i.e. cache-read/conversation-length cost, not
  by a bigger schema tax on the first call: mean `cacheCreationTokens` was
  gmesh 5,908 / kungfu ~6,950 — a modest ~18% difference, nowhere near the
  raw ~3.4x byte-size gap between the full 40-tool schema (22,231 bytes) and
  g-mesh's 7-tool schema (6,586 bytes). This is consistent with (though not a
  rigorous proof of) `--tools` actually restricting which tool schemas get
  sent to the model, not just gating which of a fully-loaded 40-tool catalog
  the model is *permitted* to call — if the full schema were always sent
  regardless of the allowlist, a much larger first-call cache-creation gap
  would be expected.
- **kungfu's own README** claims 190x/100x token reduction vs "naive
  grep+read" — that methodology is not disclosed and not reproducible from
  the README alone. Nothing in this run contradicts or confirms that
  specific claim (this run compares kungfu against gmesh/baseline, not
  against literally-naive unassisted grep+read with no tooling at all), but
  it stands in explicit contrast to this project's own paired, oracle-graded,
  taskDefHash-pinned methodology — kungfu costing *more* tokens than a plain
  Read/Grep/Glob baseline on this sample is the opposite of a 100x+ claim on
  any reading of it.

## Caveats

- n=7 tasks, 1 repetition (`REPS=low`) — a first pass, not a trusted
  aggregate; matches this project's own established "low reps is for a
  sanity check, not for trusting the numbers" convention.
- Only task-tracker-mcp + a subset of excalidraw tasks were run; the full
  20-task registry (minus the one dropped for lack of a
  `find_implementations` analog) was not exercised against kungfu.
- The curated 6-tool mapping has two structurally approximate legs
  (`find_references`→`search_text`, `get_dependencies`→`affected`) — a
  different task mix weighted more heavily toward those specific tools could
  shift kungfu's numbers in either direction.
