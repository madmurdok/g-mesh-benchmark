# Outlier close reading: four cost mechanisms that are not self-verification

Date: 2026-07-31. Investigation-only (task #48, release 0.4.0). No new
`claude -p` runs were made. Everything below comes from the run records already
in `results/token-economy/*.json` and `results/session-economy/*.json` plus the
live Claude Code transcripts under
`~/.claude/projects/-Users-Valentin-Taiurskii-Projects-excalidraw/*.jsonl` and
`.../-Users-Valentin-Taiurskii-Projects-ClaudeProjects-task-tracker-mcp/*.jsonl`.

This is the follow-on to **`v0.4.0-disambiguation-tail-findings.md` (#47)**,
which read one outlier (`ex-multihop-mutateelement-nondeleted-callers`) in depth
and established that its 40-80 call manual tail is a *self-verification /
distrust* pattern, not a tooling gap — g-mesh already resolves call sites to an
exact declaration at index time, and the `gmesh-trusted` arm collapses the tail
to zero. **That method, that mechanism, and the reasons a `symbol_id`-anchored
answer is already exact are not repeated here — read #47 first.**

#48 asks a different question: *are there other outliers, driven by other
mechanisms?* Answer: yes, four of them, and none is #47's pattern. The
discriminator used throughout is the `gmesh-trusted` arm. #47's mechanism
vanishes under the trusted prompt. **Every mechanism below survives it** — three
of them make `gmesh-trusted` the single most expensive arm on their task — which
is what proves they are structural rather than behavioural.

## 1. `get_file_outline` paginates at 20 symbols, and every extra page is a turn

**Exactly three of the thirteen lookup tasks cost the gmesh arm *more turns*
than baseline. Two of them are the `outline` tasks (§1); the third is
`tt-deps-incoming-db-connection` (§2). No other lookup task has a positive turn
delta in either mode:**

| Lookup task | Δ turns (iso) | Δ turns (sess) |
|---|---|---|
| `ex-outline-types-vs-i18n` | **+3.0** | **+3.0** |
| `tt-outline-lifecycle-vs-small` | **+1.0** | **+1.0** |
| `tt-deps-incoming-db-connection` | **+1.0** | **+1.0** |
| the other 10 | ≤ 0 (7 of them −1 or −2) | ≤ +0.5 |

(gmesh median minus baseline median, current `taskDefHash`, `status: ok`.
Several of the ≤0 tasks still cost gmesh more *tokens* — that is the
tool-schema prefix tax from `v0.2.0-session-economy-findings.md`, not a
mechanism this pass is about. The turn delta is what isolates extra round-trips.)

| Task | Mode | baseline | gmesh | gmesh-trusted |
|---|---|---|---|---|
| `ex-outline-types-vs-i18n` | iso | 58,980 / 3 turns | **94,476 / 6** | **126,846 / 6** |
| `ex-outline-types-vs-i18n` | sess | 55,077 / 3 | **170,704 / 6** (+210%) | — |
| `tt-outline-lifecycle-vs-small` | iso | 38,377 / 3 | **62,491 / 4** | **63,182 / 4** |
| `tt-outline-lifecycle-vs-small` | sess | 42,626 / 3 | **80,192 / 4** | — |

(medians, current `taskDefHash`, `status: ok`. Oracle: `tt-outline-lifecycle-vs-small`
10/10 on both arms; `ex-outline-types-vs-i18n` gmesh 9/9, baseline 7/9. So the
extra turns are near-pure cost — a small correctness edge on one task, none on
the other.)

L1's transcript is four `get_file_outline` calls against
`packages/excalidraw/types.ts` — one initial and three `cursor`-anchored
continuations — plus one against `i18n.ts`. Baseline answers the same question
with two `Read` calls. L2 is the same shape one page smaller, and the agent
narrates the cause verbatim:

> *"lifecycle.ts has more (hasMore: true), fetching the rest."*

Sweeping every `get_file_outline` call in both corpora:

- **134 calls, 45 of them (34%) are continuation pages.**
- The page size is a hard **20 symbols**: every non-final page returns exactly
  20, final pages return 3, 4, 7, 8, 9, 10, 14, 18, 19.
- `packages/excalidraw/types.ts` (66 exported types) needs 4 pages;
  `src/domain/lifecycle.ts` needs 2.

The per-page payload is small — 4,324 / 4,301 / 4,358 / 1,984 characters for
types.ts, ~15 KB total — so this is not an output-volume cost. It is #47's
~11k-tokens-per-extra-call effect: every additional round-trip re-pays the whole
conversation prefix, which is why the same 3-extra-turn pattern costs +36k in
isolated mode and +116k inside a 15-task session chain.

Decisively **not** self-verification: `gmesh-trusted` pays the *same* 6 and 4
turns and the *same or higher* token count (126,846 and 63,182). Telling the
agent to trust g-mesh cannot remove a page it has not been given yet.

**Recurs:** yes — both outline tasks, both corpora, both modes, 10/10 gmesh runs
of `tt-outline-lifecycle-vs-small` at exactly 4 turns. This is the most
deterministic mechanism in the sample.

## 2. `get_dependencies(direction: Incoming)` returns empty on task-tracker-mcp

L3 is the most expensive lookup run recorded in either mode, in either corpus —
and it is on the **trusted** arm, which is supposed to be the cheap one. Its
sequence:

| Call | Result |
|---|---|
| `Glob **/db*.{ts,js}`, `Glob src/**/*.ts` | locates `src/db/connection.ts` |
| `get_file_outline(src/db/connection.ts)` | 749 chars — the file *is* indexed |
| `get_dependencies(…, Incoming, max_depth 1, max_fanout 50)` | `{"results":[]}` |
| `find_references(symbol_id=<openDatabase>, limit 50)` | `{"results":[]}` |
| `find_callers(symbol_id=<openDatabase>, limit 50)` | `{"results":[]}` |
| `get_dependencies(…, Incoming, max_depth 2, max_fanout 100)` | `{"results":[]}` |
| `get_dependencies(…, Incoming, max_depth 1, max_fanout 100)` | `{"results":[]}` |
| 3 × `Grep` | 22 files |

Then the agent's own narration: *"g-mesh даёт пустой граф зависимостей и ссылок,
поэтому подстрахуюсь через grep."* The trusted prompt explicitly permits
`Read/Grep/Glob` "for information g-mesh cannot provide at all", so the trusted
arm is *correct* to fall back — it just pays for the six wasted structural calls
first, including two parameter-widening retries, and then pays the full baseline
path on top. Cost is strictly additive: 12 turns against baseline's 6.

Sweeping every `get_dependencies` call in both corpora — 30 calls, **22 empty
(73.3%)**:

- `src/db/connection.ts`, `direction: Incoming`: **empty in 19 of 19 calls**,
  across 19 different transcripts spanning 2026-07-30 12:55 → 2026-07-31 01:14,
  every parameter combination tried. `grep` finds 22 importers. ~~This is
  current, not a stale-build artifact.~~ **Wrong — corrected 2026-07-31, see
  §6.** It *was* a stale-build artifact, of exactly the kind this sentence
  said it wasn't: not a stale g-mesh *binary*, but a stale cached *index* that
  no binary version ever invalidated (g-mesh #96).
- `packages/math/src/index.ts`, `direction: Incoming`: empty on 2026-07-29 only
  (3 calls); on 2026-07-30 20:11 the identical call returns 10,436 chars. The
  07-29 empties are the pre-fix build family already covered by
  `v0.2.0-session-economy-findings.md` §4 and are not counted as current.

Same-corpus control: `find_references(symbol_id=<requireTask>)` on
task-tracker-mcp returns 741 chars and works fine, so this is **not** a blanket
failure of `.js`-extension import resolution — `resolve.ts`'s header documents
that both `"./x.js" → x.ts` substitution and workspace bare specifiers are
handled by design. Something is specific to this file/symbol. Two candidate
explanations the transcripts cannot separate:

1. 21 of the 22 importers use `import type { DatabaseInstance } from
   "../../db/connection.js"` — **type-only imports**.
2. The one value importer, `src/index.ts`, uses it at **module top level**
   (`const db = openDatabase();`), where there is no enclosing function for a
   `CALLS` edge to hang off. That would make `find_callers` empty *correctly*
   (#47 §3's "missing edge beats a wrong one"), but does not explain
   `find_references` or the file-level `IMPORTS` walk.

Marked open below; a follow-up is filed against g-mesh to reproduce.

Cost: `tt-deps-incoming-db-connection` gmesh 114,748 / 7 turns vs baseline
79,827 / 6 (iso). L4 (session, 207,381, 11 turns) is the same pattern inside a
chain **and fails the oracle** — 3 of 5 session gmesh runs of this task fail
against baseline's 1 of 5.

**Recurs:** within the task, exhaustively (19/19). Across tasks, the *empty
result* shape also appears on `find_references` (21/82 = 25.6% of all calls) and
`find_implementations` (14/117 = 12.0%) — but §4 shows most of those are
correct-by-design empties, not bugs.

## 3. Oversized results are rejected wholesale, and that is what breaks the trail task

M1 (`gmesh-trusted`, 13 turns — again the most expensive arm on its task) shows
the mechanism in eight calls:

```
find_implementations(Trail)          → LaserTrails, DrawShapeTrail, AnimatedTrail
find_implementations(LaserTrails)    → []
find_implementations(DrawShapeTrail) → []
find_implementations(AnimatedTrail)  → EraserTrail, LassoTrail
find_implementations(EraserTrail)    → []
find_implementations(LassoTrail)     → []
find_references(pointFrom, limit=200)
    → Error: result (54,600 characters across 1 line) exceeds maximum
      allowed tokens. Output has been saved to …/tool-results/…
5 × Grep(pointFrom, path=<one of the five files>)
```

Two things go wrong, and they compound.

**3a. Hop 1 costs one probe per node, including every leaf.**
`find_implementations` has no transitive/depth option, so walking a two-level
hierarchy means asking about every class and paying for the four that return
`[]`. Those empties are *correct* — nothing extends `LaserTrails` — but they are
indistinguishable in the response from "not indexed", which is why M1 then greps
anyway despite the trusted prompt.

**3b. Hop 2 has no scoped query, and the unscoped one is too big to return.**
The question the agent actually has is a membership test — *does file F reference
`pointFrom`?* for five known files. g-mesh cannot express that: `find_references`
takes a symbol and a row `limit`, not a file scope. The agent asks for all 200
rows and g-mesh produces 54,600 characters, which the MCP transport **rejects
entirely**. Not truncated — rejected. The agent pays a full turn and receives
nothing but an error and a filesystem path.

Corpus-wide, three tool results were rejected this way:

| Transcript | Call | Size |
|---|---|---|
| `5d87ee2c` | `find_references(pointFrom, limit 200)` | 54,600 chars |
| `8cf5c713` | `get_dependencies(packages/math/src/index.ts, Incoming, max_fanout 50)` | 115,863 chars |
| `bed9ac27` | `get_dependencies(packages/math/src/index.ts, Incoming, max_fanout 50)` | 115,863 chars |

`max_fanout` bounds breadth but `max_depth` is optional and unset by default
(`core/src/mcp/get_dependencies.rs:119-134`), so an unqualified Incoming walk
returns a full transitive closure. Adding `max_depth: 1` to the *same* call
drops it to 10,436 chars and it succeeds. So this is a defaults problem, not a
capacity problem — and the size cap is on bytes while the only knob the agent is
offered is rows.

Note the calibration is inconsistent in both directions across the same tool
surface: `get_file_outline` pages at 20 symbols / ~4 KB (§1, far too small, costs
round trips), `find_references` and `get_dependencies` will happily emit 50-115 KB
(too large, costs the whole answer).

### 3c. The fallback grep is silently wrong, and that is where the oracle failures come from

`ex-multihop-trail-impl-pointfrom` is the multi-hop task with the worst
correctness in the corpus: **7 of 18** current-hash `ok` runs fail, on both arms
(gmesh iso 3/5 pass, gmesh sess 2/4, baseline sess 0/3).

Reading the failing segments of M3 (`e8ba9fd6`, gmesh) and the two failing
baseline chains (`530a2f40`, `707b2c34`) — all three used the same fallback:

```
Grep {"pattern": "pointFrom\\(", "path": ".../drawShapeTrail.ts", "output_mode": "content"}
  → No matches found
```

and all three concluded **"no file calls pointFrom"**, which the judge rejected.
The regex is the bug. Verified directly against the working tree:

| File | `pointFrom(` | `pointFrom<` |
|---|---|---|
| `packages/excalidraw/drawShapeTrail.ts` | **0** | 1 |
| `packages/excalidraw/eraser/index.ts` | **0** | 2 |
| `packages/excalidraw/lasso/index.ts` | **0** | 1 |

Every real call site is generic-instantiated — `pointFrom<GlobalPoint>(x, y)` —
so `pointFrom\(` matches **zero of four**, in exactly the three files that are
the rubric's positives. The runs that passed (M2, `f4ca7dce`) are the ones that
happened to grep the bare name instead.

The full causal chain: *g-mesh can answer hop 2 exactly, but the only query shape
available (unscoped `find_references` on a high-fanout symbol) exceeds the
transport limit → the agent falls back to grep → the natural "call, not import"
regex is invisible to generic instantiation → wrong answer.* This is precisely
the class of question structural search exists to answer, and the tool surface
routes the agent away from it.

**Recurs:** the oversized-rejection shape recurs across two different tools and
two different tasks (`trail-impl-pointfrom`, `deps-package-math-incoming`). The
`pointFrom\(` trap is specific to this task but hit **both arms**, three
independent runs.

## 4. Not every empty is a bug — and one whole outlier is baseline tool misuse

Two negative results worth recording, because both cut *against* g-mesh's
headline numbers rather than for them.

**4a. `find_definition` and `get_file_outline` never return empty** (0 of 176 and
0 of 134). The empties concentrate in `get_dependencies` (73.3%),
`find_references` (25.6%) and `find_implementations` (12.0%), and of the
`find_implementations` empties, 4 of 4 distinct inputs are §3a's
correct-by-design leaf probes. The genuinely suspicious empties are the ones in
§2 only.

**4b. A1's 39 turns are a `Grep` mode mistake, not a baseline capability cost.**
The clamp outlier issues 37 greps. Its shape: after `Grep(clamp,
files_with_matches)` returns 22 files, the agent re-greps each file individually
with `{"-n": true}` but *without* `output_mode: "content"` — which silently
discards line content and returns `Found 1 file`. Having learned nothing, it
repeats 18 of those greps with `output_mode: "content"`. Roughly half the run is
a no-op.

Sweeping all 2,502 `Grep` calls in both corpora: **219 (8.8%) pass `-n` without
`output_mode: "content"`.** Crucially the rate is *symmetric* — 8.4% on
gmesh-arm transcripts (72/859), 8.9% on the rest (147/1,643) — so it adds noise
to both arms without biasing the comparison. But it means individual
baseline-side "cost" figures on ambiguous-name are partly agent tool-misuse, not
evidence about grep-vs-structure: `ex-ambiguous-clamp-math-utils` baseline is
84,594 / 7 turns at the median and 123,917 / 39 turns in this one run.

## 5. The control category has no outliers, which is the right answer

Deliberately included in the sample as a falsification check. The largest control
deviation in the corpus is C1 at **×1.34** tokens / ×1.33 turns — one extra
`Grep` turn on a 3-turn task, which is exactly the per-turn prefix cost and not a
mechanism. Every other control run sits at ×0.8-1.1 of its group median. Both
control tasks pass the oracle on every arm in every mode.

The one extra turn is worth a footnote because it rhymes with §3c: the run opens
with `Grep("function getShortcutKey")` → *No matches found*, because the target
is `export const getShortcutKey = (…) =>`. A regex encoding an assumption about
declaration shape misses, and costs a turn. C1 is also a gmesh-arm run that never
called a g-mesh tool — correct behaviour on a control task, and a reminder that
"gmesh arm" and "used g-mesh" are not the same set when reading transcripts.

The one systematic control effect — gmesh 133,975 vs baseline 93,574 median in
session mode (+43%) — is the g-mesh tool-schema prefix tax already measured in
`v0.2.0-session-economy-findings.md` and is not re-derived here.

That control is flat while every other category has a live mechanism is the main
reason to believe §§1-3 are about the tasks and the tools rather than about
sampling noise.

## 6. Confirmed vs. open

**Confirmed by data:**

- `get_file_outline` pages at a hard 20 symbols; **34% of all 134 outline calls
  in the corpus (45) are continuation pages**. `packages/excalidraw/types.ts`
  needs 4 calls, `src/domain/lifecycle.ts` needs 2, against baseline's 1 `Read`.
- That pagination is the *entire* cost gap on both outline tasks: gmesh +60% /
  +63% tokens and +1 to +3 turns in isolated mode, +210% / +88% in session mode.
  Correctness does not pay for it: on `tt-outline-lifecycle-vs-small` both arms
  pass 10/10; on `ex-outline-types-vs-i18n` gmesh passes 9/9 against baseline's
  7/9, so the extra turns buy a small correctness edge on one of the two tasks
  and nothing on the other.
- The mechanism is not distrust: `gmesh-trusted` pays the same turn count and
  the same or higher token count on both outline tasks (126,846 and 63,182).
- `get_dependencies(src/db/connection.ts, Incoming)` returns `{"results":[]}` in
  **19 of 19 calls** across 19 transcripts and every parameter combination tried,
  on current g-mesh *builds* — but, per the §6 correction, against a stale
  cached *index* — while 22 files import that module.
  `find_references`/`find_callers` on `openDatabase` are empty in 6 of 6.
  Fixed in g-mesh #96.
- The resulting cost is additive, not substitutive: L3 (`gmesh-trusted`,
  204,536 tokens / 12 turns) spends 6 structural calls, gets nothing, and then
  pays the full grep path — the most expensive lookup run in the corpus.
- Three tool results in the corpus (54,600 / 115,863 / 115,863 chars) exceeded
  the MCP transport limit and were **rejected entirely**, costing a full turn and
  returning no information. `get_dependencies`'s `max_depth` is optional and
  unset by default; supplying `max_depth: 1` drops the same call from 115,863 to
  10,436 chars and it succeeds.
- `find_implementations` has no transitive option, so walking the 5-class `Trail`
  hierarchy costs 6 calls of which 4 return `[]`.
- All three `ex-multihop-trail-impl-pointfrom` runs that concluded "no file calls
  pointFrom" (1 gmesh, 2 baseline — of 7 failures across 18 `ok` runs) did so
  after grepping `pointFrom\(`, which matches **0 of the 4** real call sites —
  every one is `pointFrom<GlobalPoint>(…)`. Verified against the working tree.
- 219 of 2,502 `Grep` calls (8.8%) pass `-n` without `output_mode: "content"` and
  silently return a filename list. The rate is symmetric across arms
  (8.4% vs 8.9%), so it is noise rather than bias — but it accounts for roughly
  half of A1's 39 turns.
- The control category shows no outlier above ×1.34 on any arm, in either mode.

- ~~Why is `src/db/connection.ts` invisible to the incoming walk? The two

  specifiers resolved at all; nothing in g-mesh ever invalidated an index once
  its DDL (`schema_version`) stopped changing, so the daemon kept serving that
  first, import-free extraction for three releases of resolver fixes. Fixed by

  same way `schema_version` already was. Against a rebuilt index of the same
  files, `get_dependencies(Incoming)` returns all 39 real importers. This also
  means every other "empty on current builds" claim measured against a
  long-lived local corpus checkout in this doc and in
  `v0.4.0-disambiguation-tail-findings.md` shares the same latent risk — the
  builds were current, the *indexes* were not, and nothing said so.
- **Is `get_file_outline`'s 20-symbol page a hard cap or a default?** No `limit`
  parameter appears in any recorded outline call, while `find_callers` and
  `find_references` accept one and agents use it (`limit: 200`). If it is a
  default with no override, that is a one-line fix; if it is a cap, it needs the
  same `limit` treatment the symbol tools already have. Filed.

  exactly 20 symbols and the agent did not fetch a continuation. Whether that
  file has exactly 20 symbols or was truncated with an unnoticed `hasMore` was

  first page is indistinguishable from a complete one at a glance.
- **Is `ex-multihop-trail-impl-pointfrom` measuring what it intends?** It is a
  legitimate discriminator — generic-instantiated calls are exactly what a parser
  sees and a regex does not — but with hop 2 unreachable through g-mesh (§3b),
  both arms fall into the same regex trap and the task currently measures
  regex-luck rather than structure-vs-text. Filed against the bench.
- **n is thin on `gmesh-trusted`**, as #47 also noted: 1 run each on L3 and M1.
  Both are extreme (worst-in-corpus and worst-on-task respectively) and both are
  consistent with the plain-`gmesh` runs of the same task, but a single run is a
  single run. #47's already-filed `G_MESH_BENCH_INCLUDE_TRUSTED=yes` full pass
  (`dd87688b-7c58-4b3b-ae09-d530886608bc`) would settle it.
- **Are there more mechanisms?** This pass was capped at 9 transcripts by design.
  The four found are all *tool-surface* mechanisms, which suggests the remaining
  variance is worth a sweep specifically over tool-result shapes (empty,
  oversized, paginated) rather than over runs. Not done here; suggested as a
  follow-up rather than executed.
