# GM-257: not built — the follow-up it would remove does not happen

**Date:** 2026-08-25
**Decision:** **do not implement.** The design pass the task demanded, run before any code, found
both that the payload cost is real and that the behaviour it targets is not there.
**Cost:** zero. Everything below is from runs already on disk.

## The premise

`find_references` answers with coordinates and no source, so — the reasoning went — the agent goes
and reads the line. GM-231 closed the same gap for `find_definition` and measured 44,164 tokens
against a 51,515 control.

The task itself flagged that GM-231's evidence is one discriminating rep of three, and required a
recorded design decision with payload arithmetic before implementation. That order is what saved the
work.

## The behaviour, over 42 `find_references` calls

What immediately follows the call:

| follower | calls | share |
|---|---|---|
| **nothing — it was the last tool call of the run** | 25 | **60%** |
| `Grep` | 11 | 26% |
| `Read` | 3 | **7%** |
| another g-mesh call | 3 | 7% |

**Sixty percent of the time the agent answers straight out of the response and stops.** The Read that
GM-257 exists to remove happens in 3 calls out of 42.

And those three are not fetching a call site. Their arguments:

```
Read  offset=1  limit=90   lifecycle.ts
Read  offset=1  limit=100  tasks.ts
Read  offset=50 limit=15   tasks.ts
```

Two are ninety- and hundred-line reads — the agent opening a file to understand it, which a per-row
source line would not have replaced.

The eleven greps are not fetching lines either. **Not one of them uses a context flag** (`-C`, `-A`,
`-B`). Most run `output_mode=files` or `files_with_matches`, asking *which files* — a question the
response's own `files` array already answers. The two `output_mode=content` greps search for
different symbols (`function (require\w*Task|…)`, `getNonDeletedElements`), which are new questions,
not a re-read of the rows just returned.

## The arithmetic, for the record

Measured over 83 captured `find_references` responses: median 15 rows / 4,205 chars, p90 45 rows /
14,008 chars, max 51 rows / 18,826 chars.

Attaching a trimmed 60-character source line to every row:

| response | rows | added | inflation |
|---|---|---|---|
| median | 15 | +900 chars, +533 tokens | **+21%** |
| p90 | 45 | +2,700 chars, +1,598 tokens | +19% |
| max | 51 | +3,060 chars, +1,811 tokens | +16% |

Across the sweep's 42 calls that is ~22,400 tokens of cache-creation, **before** counting that every
inflated response is re-read on every later turn of its run — and tool-result volume is what
cache-creation tracks (r = 0.862, 1.69 chars/token, `v0.20.0-gmesh-2.8.1-token-economy-findings.md`
§2a).

Against a ceiling of 3 saved Reads. Even valuing a Read at a full turn (~15,100 tokens) the trade is
roughly break-even on creation alone and negative once re-reads are counted — and that ceiling
assumes a source line would have replaced a hundred-line read, which it would not.

## Why an opt-in parameter is not the escape hatch

The obvious rescue is `include_source`, defaulting off. But a parameter is a permanent line in
`tools/list`, and that payload is re-read on **every turn of every run**, not just the ones that use
the tool — `find_references` is already 11.5% of it. Paying schema tax on every turn forever to
serve 7% of calls of one tool inverts the same arithmetic in a worse direction.

The `tally_is_worth_sending` shape — attach source only when the row count is small enough that the
answer is the whole answer — remains defensible and costs nothing when it does not fire. It is not
worth building now, because the behaviour it would serve still has not been observed: the 3 Reads
are large-range file reads, not row lookups.

## What would change this

A measured case of an agent fetching *the line at a row it was just given*. That is a specific,
recognisable shape — a `Read` with a narrow `offset`/`limit` around a `startLine` from the response,
or a grep with a context flag against a returned path. Across 42 calls it appears zero times. If it
starts appearing, this task becomes worth reopening; the query that would detect it is the one
above.

## The pattern this is the fourth instance of

GM-237 added a response field: measured, no change. GMB-139 added a guidance sentence: measured,
target metric unmoved. GM-256 shipped a disclosure: unmeasurable, because the agent picks the other
tool. GM-257: not built, because the follow-up it removes does not occur.

The common thread is not that these ideas are bad. It is that each was reasoned from what an agent
*ought* to need, and the saved transcripts kept answering with what it actually does — which is to
take the index's answer and stop, 60% of the time.
