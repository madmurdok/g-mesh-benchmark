# GMB-165 — what the arm doc's TypeScript scope line actually does

**Date:** 2026-09-20
**Binary under test:** `g-mesh 3.7.0` (`g-mesh/target/release/g-mesh`, named explicitly through
`G_MESH_BENCH_BINARY` — see GMB-163 §1 for why the default path is a five-versions-old build)
**Harness:** `token-economy`, one arm per invocation (`gmesh-configured`),
`G_MESH_BENCH_WARM_CACHE=no`, `claude-sonnet-5`
**Corpora:** gin (Go, pinned `73726dc`), psf/requests (Python, pinned `6e83187`)
**Raw records:** `docs/results/gmb165-raw/` — seven `token-economy` result files, deliberately
**not** under `results/token-economy/`, because four of them were produced by a modified
`GMESH_CONFIGURED_CLAUDE_MD` while still labelling themselves `arm: "gmesh-configured"`.
`harness/report.ts` only ever globs `ROOT/results`, so they cannot reach a cumulative report.

**Answer:** the scope line suppresses the tool under test, measurably, on Python
(5/16 runs called g-mesh with it, 16/16 without it, Fisher one-sided p = 3e-05).
It does not on Go. The benchmark now selects a de-scoped variant of the same
document for non-TypeScript corpora — option 2 of the three GMB-165 listed —
and the TypeScript text stays byte-identical.

---

## 1. The question, and why looking at the text could not answer it

`GMESH_CONFIGURED_CLAUDE_MD` (`harness/lib/armConfig.ts`) opens
`# Code search (TypeScript/JavaScript projects)`, and its first bullet begins
"In TS/JS projects, prefer g-mesh". The 0.23.0 batch registered a Go, a Rust
and a Python corpus, so the `gmesh-configured` arm now runs on repositories
its own first line excludes.

GMB-168's two dry runs on psf/requests recorded `mcpToolCalls: 0` with the
server connected, and the arm said why:

> "I used grep because this is a Python repo and the lookup was a single,
> unambiguous name."

Two causes in one sentence. The same bullet that scopes the doc to TS/JS also
licenses skipping the tool for "simple, unambiguous single-symbol lookups" —
which applies on TypeScript just as much. Both zero-call runs cited both, so
nothing on the table separated *the doc excludes this language* from *the doc
says easy lookups are not worth the tool*. A heading rewrite could have
changed nothing while looking like a fix.

## 2. Design

Three arms, identical in every respect except the first two lines of
`GMESH_CONFIGURED_CLAUDE_MD`. Each ran from its own `git worktree` off
`release-0.23.0` with a byte-identical `g-mesh-bench.config.json`, so the doc
text is the only variable and no control edit could leak into a committed
branch.

| arm | heading | first-bullet opener |
|---|---|---|
| **A** current text, unchanged | `# Code search (TypeScript/JavaScript projects)` | `- In TS/JS projects, prefer g-mesh (` |
| **B** scope line removed | `# Code search` | `- Prefer g-mesh (` |
| **C** scope line hardened (control) | `# Code search (TypeScript/JavaScript projects only — these tools do not apply to any other language)` | `- In TS/JS projects, and only there, prefer g-mesh (` |

Every other byte — all the tool-semantics bullets, TypeScript-flavoured
examples included — is identical across the three.

Arm C is not a candidate fix. It exists because a null between A and B is
unreadable without it: "the scope line makes no difference here" and "nothing
could have made a difference here" produce the same table. C turns the scope
line up instead of off, and shows the dependent variable moves.

`mcp` below counts `mcp__g-mesh__*` calls. `search` counts every search-bucket
call — Read/Grep/Glob **and** the g-mesh tools (see `classifyToolCall`) — so
`search − mcp` is the number of greps and reads.

## 3. gin (Go): no difference, and a control proving that is a real null

Two tasks the first bullet unambiguously assigns to g-mesh and that cannot be
re-read as single-name lookups — `gin-scenario-abort-callers` ("I'm about to
change this method's signature, list every caller") and
`gin-scenario-handlerfunc-references` ("...this type's signature, list every
file that references it") — 3 repetitions each, 6 runs per arm.

| arm | runs calling g-mesh | g-mesh calls | greps/reads | turns | oracle | cost |
|---|---|---|---|---|---|---|
| **A** scoped | **6 / 6** | 8 | **0** | 14 | 6/6 pass | $0.2364 |
| **B** de-scoped | **6 / 6** | 8 | **0** | 14 | 6/6 pass | $0.2587 |
| **C** hardened | **0 / 6** | 0 | **29** | 35 | 6/6 pass | $0.3389 |

A and B agree run for run, not just in aggregate:

    gin-scenario-abort-callers           A: 2 1 2    B: 2 1 2    C: 0 0 0
    gin-scenario-handlerfunc-references  A: 1 1 1    B: 1 1 1    C: 0 0 0

**The control fired, in its own words.** Arm C on the Abort task:

> "Non-test code calls it directly from these four places. I found them with a
> grep for `.Abort()`, not g-mesh, because your `CLAUDE.md` limits g-mesh to
> TS/JS projects and this is Go."

That sentence never appeared once in arm A's six runs. So on Go the *current*
wording is too weak to suppress, while a stronger one at the same two lines
suppresses completely — 6/6 vs 6/6 is a measured null, not an unmeasurable
one.

Worth naming because it cuts against a tidy story: **all 18 gin runs passed
the oracle.** Arm C was not wrong, only more expensive — 3.6x the searches,
2.5x the turns, 1.4x the cost. And arm B was not cheaper than arm A
($0.2587 vs $0.2364 on identical tool sequences); that is output-token noise,
not an effect, and nothing in it should be read as "de-scoping costs money".

## 4. psf/requests (Python): the scope line suppresses the tool

The confound arose on Python, so the A/B was repeated there on exactly the two
tasks whose GMB-168 dry runs recorded `mcpToolCalls: 0` —
`py-references-httpbasicauth` and `py-find-impl-supportsread-protocol`. Run at
3 reps, then extended to 5 more, and pooled: 8 runs per task per arm, 16 per
arm.

| arm | runs calling g-mesh | g-mesh calls | greps/reads | turns | oracle | cost |
|---|---|---|---|---|---|---|
| **A** scoped | **5 / 16** | 5 | **39** | 60 | 16/16 pass | $0.4957 |
| **B** de-scoped | **16 / 16** | 24 | **16** | 56 | 16/16 pass | $0.4462 |

Per task, g-mesh calls per run:

    py-find-impl-supportsread-protocol   A: 1 0 0 0 0 0 0 0    (1/8)
                                         B: 2 2 2 2 2 2 2 2    (8/8)
    py-references-httpbasicauth          A: 1 0 1 0 1 1 0 0    (4/8)
                                         B: 1 1 1 1 1 1 1 1    (8/8)

Fisher exact, one-sided, on 5/16 vs 16/16: **p = 3e-05**.

Two things beyond the count. The de-scoped arm is **deterministic** — the same
tool count in all eight runs of each task — where the scoped arm is erratic;
that is the shape of an instruction being followed versus an instruction being
weighed. And one scoped-arm run stated the language as its *only* reason, with
no simple-lookup clause attached:

> "I used a text search because this is a Python project."

That is the de-confounding this task existed to produce. Arm B removes **only**
the language clause — the simple-lookup licence is present, unchanged, in both
arms — and usage goes from 5/16 to 16/16 on the very tasks that raised the
question. The simple-lookup clause is therefore not what was driving those
zeros.

## 5. What this settles, and what it does not

**Settles.** The scope line is a cause, not a description. On psf/requests it
suppressed the tool under test in 11 of 16 runs. Option 3 ("leave it and say
so in every write-up") is ruled out by measurement: it does not merely
document a language it excludes, it changes what the arm does.

**Does not settle, and should not be rounded up.**

- **The effect is not uniform across languages.** On gin it is zero. Two
  languages, four tasks, is not a law; the Go null is as real as the Python
  effect, and the difference between them is unexplained. The plausible
  reading — a stronger prefer-the-tool cue (an explicit signature-change
  impact question) outweighs the scope cue, while a weaker one does not — is a
  hypothesis this data suggests and does not test.
- **Rust is unmeasured.** ripgrep's cold index is 552s isolated and 804s under
  load. Nothing in the Go and Python results suggested the answer turns on the
  language rather than on the task, so the spend was not made.
- **Correctness never moved.** 34 of 34 runs across all arms passed their
  oracle. What the scope line costs is tool usage and turns, not answers — on
  these tasks, which have grep-tractable ground truth. It says nothing about a
  task where grep would get it wrong.
- **Nothing here is a claim about g-mesh's value.** Both arms of every pair
  are `gmesh-configured`; baseline was not run. These numbers are about the
  document, not the tool.

## 6. The decision: option 2 — per-language selection, TypeScript bytes untouched

`gmeshConfiguredClaudeMd(language)` / `gmeshMapConfiguredClaudeMd(language)`
in `harness/lib/armConfig.ts` now hand a `ts`/`js` corpus
`GMESH_CONFIGURED_CLAUDE_MD` by identity, and every other language the same
document with its two scoping spans replaced and nothing else touched. All
five call sites (four in `token-economy.ts`, one in `session-economy.ts`) pass
their own corpus's `language`.

**Why option 1 (rewrite language-neutral, sync the copies) lost.** It is not
an edit in this repo. `armConfig.test.ts`'s drift guard pins this constant
byte-for-byte to g-mesh's shipped `AGENTS_MD_SNIPPET`, so changing it here
turns the suite red until `g-mesh/core/src/cli/agent_instructions.rs`, its two
tests and `README.md:425` change too — a product decision about what
`g-mesh init --agent claude` writes into real users' repositories, belonging
to the GM project and not to this task. It would also end byte-identity with
every historical TypeScript comparison, and break
`GMESH_MAP_CONFIGURED_CLAUDE_MD`'s "the configured doc plus one `@AGENTS.md`
line" property, which is the only reason the `gmesh-configured`/`-map` pair
measures the repo map and nothing else. Option 2 keeps all three.

**What option 2 costs, stated rather than absorbed.** On a non-TypeScript
corpus the arm is no longer literally the document `g-mesh init` ships, which
is the claim that makes `gmesh-configured` a measurement of a real delivery
path instead of a benchmark invention. Three things keep that cost bounded,
and none of them erases it:

- The variant is **derived, not maintained** — computed from the one constant
  by a two-span substitution, so the drift guard still covers every word.
- The substitution **refuses to guess**: `descopeGuidance` throws unless each
  span appears exactly once, so a reworded upstream snippet fails loudly
  instead of silently handing a Go corpus the scoped text again.
- It is what a real Go user pasting g-mesh's README snippet into their
  `CLAUDE.md` would plausibly do — drop the language gate, keep the rest.

**Every write-up of a non-TypeScript run must say the arm ran a de-scoped
derivative rather than g-mesh's shipped text.** That is the standing cost of
this choice, and it replaces the (heavier) obligation option 3 would have
carried.

### Verification

- `npm run typecheck` clean; all 19 test files pass, 0 skipped — so the drift
  guard ran rather than skipping for a missing g-mesh checkout.
- **Control on the new tests:** with `descopeGuidance` short-circuited to
  return the document unchanged, `armConfig.test.ts` goes 24 pass / 1 fail
  ("de-scopes go/rust/python in exactly two lines and no others"); restored,
  25/25. The test tells the arms apart.
- **End-to-end**, through the committed harness rather than a worktree: see §7.

## 7. End-to-end check of the shipped change

Run from the committed harness (not a worktree), `gmesh-configured`, 3 reps,
`G_MESH_BENCH_WARM_CACHE=no`, g-mesh 3.7.0 —
`docs/results/gmb165-raw/verify-shipped-harness-ts-and-py.json`:

| corpus | task | runs calling g-mesh | oracle |
|---|---|---|---|
| task-tracker-mcp (ts) | `tt-references-requiretask` | 3 / 3 | 3/3 pass |
| psf/requests (python) | `py-find-impl-supportsread-protocol` | 3 / 3 | 3/3 pass |
| psf/requests (python) | `py-references-httpbasicauth` | 3 / 3 | 3/3 pass |

The Python half reproduces arm B (6/6 here, 16/16 in the experiment) against
arm A's 5/16, so the change that shipped is the change that was measured. The
TypeScript half is the answer to "did anything a TypeScript arm sees change":
it ran unaffected, and nothing could have changed — `gmeshConfiguredClaudeMd`
returns `GMESH_CONFIGURED_CLAUDE_MD` by identity for `ts`/`js`, asserted in
`armConfig.test.ts`.

**And the effect was read off disk, not off a return code.** The `CLAUDE.md`
each throwaway clone actually received during that run, diffed against each
other:

    1c1
    < # Code search (TypeScript/JavaScript projects)      <- task-tracker-mcp clone
    ---
    > # Code search                                       <- py-requests clone
    3c3
    < - In TS/JS projects, prefer g-mesh (`mcp__g-mesh__*`) for cross-file i...
    ---
    > - Prefer g-mesh (`mcp__g-mesh__*`) for cross-file impact analysis, amb...

Two lines, and the TypeScript clone's file is byte-identical to
`GMESH_CONFIGURED_CLAUDE_MD`.

One caveat on that run's timings, not its counts: the machine's load average
was 115 by the end of it (an unrelated workload), so nothing in it should be
read as a duration measurement. `mcpToolCalls` and the oracle verdicts are
unaffected by load.

## 8. Left for someone else

- **`~/.claude/CLAUDE.md`** — deliberately untouched. It is the operator's
  personal global config, not a file of this repo (the same call GMB-148 made
  about it). Under option 2 it needs **no** change: the shared constant did not
  move, so that copy is still in sync.
- **`g-mesh/README.md`** — also untouched, for the same reason. The snippet it
  publishes is `AGENTS_MD_SNIPPET`, which did not change.
- **Upstream, in the GM project — the hazard this choice makes worse.**
  GMB-163 §5 measured that this document's `get_dependencies` bullet ("an
  `Incoming` walk already answers every file that imports this") is true
  *only* on TypeScript: elsewhere a module is not a file, and a file-anchored
  `Incoming` walk returns a confident `results: []`. The TS/JS heading was an
  accidental warning about that, and the de-scoped variant removes it. The
  derivation was deliberately **not** widened to patch the bullet: correcting
  it is a change to g-mesh's shipped guidance, it has no A/B behind it, and
  making it only in the benchmark's derived copy would leave two documents
  nobody could reconcile. It needs a GM task.
- **`g-mesh/README.md:4`** still reads "MVP scope: JavaScript/TypeScript
  only", while `g-mesh 3.7.0` ships bundled go, python and rust plugins. If
  the TS/JS scoping is ever dropped upstream, this repo's derivation should be
  deleted and every corpus share one document again — `descopeGuidance`'s own
  error message says so.
- **`reportData.ts`'s `computeSilentMcpArms`** catches an arm that never calls
  MCP, but aggregates over *all* of that arm's runs — so in a mixed
  TypeScript + Go report a silent Go half is averaged away by a busy
  TypeScript half and nothing is raised. Making it per (arm, corpus) belongs
  to GMB-169, the task that will first publish such a table.
