# v0.6.0 realistic dev-scenario tasks: what was added and a first cheap look

Date: 2026-07-31. Validation run:
`results/token-economy/2026-07-31T21-09-46-299Z.json` (the 5 new tasks below
only, `G_MESH_BENCH_REPS=low` → 1 repetition, `gmesh`/`baseline` arms only,
`G_MESH_BENCH_WARM_CACHE=no`, `G_MESH_BENCH_HTML_NARRATIVE=no`,
`claude-sonnet-5` under test, `claude-haiku-4-5` as judge). Real spend: **arm
$0.9496 + judge (grading) $0.0804 + narrative $0 = $1.0300 total**, 10 arm
calls + 3 judge calls. See `docs/architecture/g-mesh-bench-v2-realistic-tasks.md`
for the pool/judge grading modes and category conventions this batch builds
on.

## Why this batch exists

Every task added in the v2 redesign (`docs/architecture/g-mesh-bench-v2-realistic-tasks.md`)
is still framed as abstract "find every X" — a real query shape, but not the
reason a developer actually runs it. This batch adds tasks framed around an
actual pending action (about to change a signature, chasing a bug back to its
source, deciding whether something is safe to delete), to see whether that
framing changes anything measurable versus dressing the same query in
different words.

## Tasks added

All 5 use `category: "scenario"` (new — see below) and `revealsLocation:
false`. Ground truth for every pool/dead-code claim was computed with
`scripts/computeCandidatePool.ts` (ts-morph, independent of g-mesh); the
bug-trace task's ground truth was confirmed by hand-reading the actual call
chain, since no `computeCandidatePool` mode answers "which caller passes a
bad value."

| id | corpus | shape | ground truth |
|---|---|---|---|
| `ex-scenario-impact-getelementabsolutecoords` | excalidraw | 1: pre-change impact | `getElementAbsoluteCoords` (`packages/element/src/bounds.ts`) has 22 real callers outside its own file (`computeCandidatePool --mode references`); pool of 22, `minMatches: 10` |
| `ex-scenario-deletesafe-getrectangleboxabsolutecoords` | excalidraw | 3: blast-radius / safe-to-delete | `getRectangleBoxAbsoluteCoords` (same file) has **zero** references anywhere in the repo, tests included (`computeCandidatePool --mode references --include-tests` → `files=0`) — genuinely dead code, confirmed independently of g-mesh |
| `tt-scenario-impact-requireproject` | task-tracker-mcp | 1: pre-change impact | `requireProject` (`src/domain/projects.ts`) has 6 callers (`board.ts`, `epics.ts`, `lifecycle.ts`, `releases.ts`, `status.ts`, `tasks.ts`); pool of 6, `minMatches: 4` |
| `tt-scenario-deletesafe-taskcode` | task-tracker-mcp | 3: blast-radius / safe-to-delete | `taskCode` (`src/domain/tasks.ts`) has exactly **one** reference anywhere — `tests/tasks.test.ts` — and zero references from any file under `src/`; despite its own doc comment claiming it's "the one place... every surface... renders identically," nothing in production code actually calls it yet |
| `tt-scenario-bugtrace-createtasks-selfdep` | task-tracker-mcp | 2: bug tracing from a symptom | `addDependency` throws `"A task cannot depend on itself"` when `taskId === dependsOnTaskId`. Traced by hand: `createTasks` (`src/domain/tasks.ts:294-337`, behind the `create_tasks` MCP tool) creates every task in a batch first, building a `temp_id → real task_id` map, then resolves each spec's `depends_on` entries through that map. A spec whose `depends_on` includes **its own `temp_id`** resolves back to its own freshly-created id, so `addDependency(db, id, id)` fires — even though no spec in the raw input ever repeats a literal real id. Verified by reading the two-pass structure directly; no existing test exercises this exact case |

Why each is a good instance of its shape:
- **Shape 1** (`ex-…impact…`, `tt-…impact…`): both symbols have genuine,
  independently-verified fan-out (22 and 6 files respectively) — a real
  signature change would break real call sites, not a contrived list.
- **Shape 3** (`ex-…deletesafe…`, `tt-…deletesafe…`): deliberately picked one
  *clean* case (`getRectangleBoxAbsoluteCoords`, truly zero references
  anywhere) and one *nuanced* case (`taskCode`, referenced only by a test,
  not by any production path) rather than forcing both into the same "yes,
  totally dead" shape — the nuanced case is a better test of whether an arm
  actually checks rather than pattern-matching "looks like dead code plus low
  usage → say yes."
- **Shape 2** (`tt-…bugtrace…`): this is the one the design doc calls hardest
  to author honestly. It's grounded in a real code path — a batch API design
  (client-chosen `temp_id`s resolved post-creation) that genuinely does admit
  a self-reference bug, confirmed by reading the actual two-pass
  implementation, not invented. No test in the repo currently exercises this
  case, so it's an authentic "walk the call graph backward to find who could
  pass the bad input" question with a real, non-obvious answer — not "list
  everything downstream," which is the shape the existing multi-hop tasks
  already cover.

## New category: `scenario`

Added `"scenario"` to `TaskCategory` in `harness/lib/types.ts` (additive —
the type was already a plain union with two consumers, `token-economy.ts`'s
passthrough field and the type declaration itself, neither with switch-style
logic on the value). Checked `harness/lib/reportData.ts` and
`harness/lib/htmlReport.ts`: every category-keyed table/chart derives its
category set dynamically via `[...new Set(runs.map(r => r.category ?? ...))]`
— nothing enumerates a fixed category list, so no report code needed
changing.

Why one shared category for all three scenario shapes rather than three:
`kind` already carries per-shape texture (`find_references` for shapes 1/3,
a new `bug_trace` value for shape 2), and a single `scenario` category lets
`report.ts`'s per-category correctness/token tables produce one row directly
comparable against `lookup`/`multi-hop` — which is what the investigation
question below actually needs.

One deliberate side-effect worth flagging: `search-latency.ts` (out of scope
for this change, not touched) picks one task per `kind` from each corpus's
`tasks.json`, first-match-wins by array order, as its latency-probe targets.
All 5 new tasks are appended after the existing entries, so for every `kind`
that already had an earlier task in the same corpus, the existing target is
still picked first — unaffected. The one exception:
`tt-scenario-bugtrace-createtasks-selfdep` deliberately uses `kind:
"bug_trace"`, not `"find_callers"`, specifically so it doesn't become the
task-tracker-mcp corpus's `find_callers` latency-probe target (that corpus
previously had none, so introducing one under a real tool-name `kind` would
have silently changed `search-latency.ts`'s behavior for that corpus).

## Did the scenario framing change anything, or is it narrative dressing?

**Honest answer: at n=1 per task, mostly no — the numbers land in the same
range and same direction as the existing "abstract find-X" tasks, with one
task-level exception worth a follow-up look, not a conclusion.**

- **Shapes 1 and 3 (`impact`, `deletesafe`) behaved like ordinary lookup
  tasks.** Turn counts stayed low (3-5) on all 4 of these tasks, on both
  arms — none showed the self-verification blowup (`ex-find-callers-mutateelement`,
  13 turns; the 57-74 turn multi-hop cases) that the existing findings docs
  flag as gmesh's worst-case pattern. That's consistent with the design
  doc's own framing: these two shapes are the *same underlying
  references-style query* as the existing `lookup` category, just narrated
  around a pending action — and they measured like it. The token-reduction
  number for these 4 tasks alone (gmesh: 81,422 mean; baseline: 51,981 mean
  → gmesh costs 56.6% more) sits in the same range as the existing corpus's
  reported `lookup`-adjacent numbers (`-36.7%` unconditional / `-43.3%`
  paired, v0.2.0-realistic-tasks-findings.md) — higher in this small sample,
  but not a different phenomenon; both say "gmesh spends meaningfully more
  tokens on single-hop lookups here," which was already the established
  finding before this batch.
- **Both arms answered every scenario-framed prompt correctly and directly**
  — the "I'm about to change X" / "is it safe to delete" / "trace this bug"
  narrative didn't visibly confuse either arm into answering a different,
  easier question than the one actually asked (e.g. the `deletesafe` answers
  explicitly stated "safe to delete" / named the one test reference, not
  just "here are the references" with no verdict) — a real, if small, sign
  that the scenario framing is eliciting the intended *conclusion*-shaped
  answer, not just the same file list with extra words around it. Whether
  that generalizes needs the same task re-run at `G_MESH_BENCH_REPS=normal`
  or more distinct scenario tasks, not claimed here from n=1.
- **The one task that looks structurally different is the bug-trace task**
  (shape 2): gmesh took 9 turns / 188,701 tokens versus baseline's 5 turns /
  71,522 tokens — the largest gmesh/baseline gap of the 5 tasks (+164% tokens,
  vs. +30-73% on the other four). Both arms still answered correctly and
  fairly concisely (`resultText` on both is a direct, complete explanation of
  the `temp_id` self-reference mechanism), so this isn't the self-verification
  pattern from other docs (no re-checking language in the text) — more likely
  gmesh explored more of the call graph before settling (this task genuinely
  requires reading two functions and reasoning about their interaction, not
  one references list). **This is one data point on one task with no
  repetition** — it's plausible that shape 2 (the only genuinely new query
  pattern here, not a reframed lookup) costs more than the other two shapes,
  but n=1 cannot distinguish "shape 2 is inherently more expensive" from
  "this particular task happened to need more exploration." Worth a targeted
  re-run (`G_MESH_BENCH_REPS=normal`, this task alone, maybe 1-2 more
  bug-trace tasks) before drawing any conclusion.

**Overall**: this validation run found no evidence that scenario framing by
itself changes tool-call behavior for the reframed-lookup shapes (1 and 3) —
they measure like the lookup tasks they structurally are. The bug-trace shape
(2) shows a bigger gap in one sample, consistent with it being a genuinely
different (harder, more exploratory) query rather than dressing — but that
reading rests on a single repetition of a single task and should not be
treated as established.
