# GMB-143: the disclosure defends against a mistake the agent does not make

**Date:** 2026-08-25
**Outcome:** the task was built, measured, and **reverted**. It does not discriminate, and the reason
generalises: no phrasing of a caller-listing task can make GM-256's disclosure load-bearing, because
the agent reaches for `find_references` on its own whenever the answer needs test files.
**Cost:** $0.55 for the run that settled it, plus a free index query that chose the anchor.

## What was built

GM-256 discloses `excludedReferences` when a `CALLS` walk skips `REFERENCES`-kind edges. Its A/B
could not be run because no registry task penalises the omission
(`v0.22.0-gm256-excluded-references-ab.md`). This task was meant to supply one.

Anchor chosen from the index, not from grep — a first attempt on `mutateElement` failed a check and
is worth recording. Grep found 11 test files calling it; the index returned 2. **The index was
right:** the other nine call `h.scene.mutateElement(...)`, which is `Scene`'s *method*, a different
symbol, reached through a variable receiver, which produces no edge by design.

`pointFrom` (`packages/math/src/point.ts`) is the real anchor:

| edge kind | edges | files | from test files |
|---|---|---|---|
| `CALLS` | 193 | 58 | 8 |
| `REFERENCES` | 27 | 26 | **27 of 27** |

**23 test files are reachable only through `REFERENCES`** — invisible to `find_callers`, returned by
`find_references`. Those 23 became the pool, `minMatches: 8`, with a prompt asking for at least ten
test files that call it. On paper the discrimination is total: a `CALLS`-only answer scores 0 of 23.

## What happened instead

| arm | runs | oracle | turns | CV | mean tokens |
|---|---|---|---|---|---|
| `gmesh-configured` | 5 | **5/5** | 2–2 | 0% | 52,859 |
| `serena-configured` | 5 | 5/5 | 2–3 | 18% | 34,684 |
| `baseline` | 5 | **5/5** | 2–2 | 0% | **27,192** |

`gmesh-configured` used **`find_references` in all five reps and `find_callers` in none.** From the
transcript, before its single call:

> **say:** I'll find all references to `pointFrom` and filter for test files.

One call, 18,826 characters back, answer complete. The disclosure cannot appear on a tool that is
never invoked.

## Why this is general, not another underpowered attempt

The three attempts at measuring GM-256 have converged on one explanation, and it is not sample size.

The guidance document already tells the agent that `find_callers` walks `CALLS` edges only and that
`find_references` is the exhaustive answer when test-file call sites matter. **The agent follows
it.** That closes the trap by tool choice, upstream of any disclosure in the payload.

And the trap cannot be reopened by rewording the task:

- Phrase the prompt so the answer clearly needs test files, and the agent reads that and picks
  `find_references` — what happened here.
- Phrase it generically as "who calls X", and the agent picks `find_callers` — but then the expected
  answer is source files, where a `CALLS` walk is complete and sufficient. That is
  `ex-find-callers-mutateelement`, which the arm passes 3/3 in 2 turns with zero greps.

Steering the prompt until the agent picks the tool that will fail is not a measurement of the
disclosure; it is a measurement of the steering.

## Why the task was reverted rather than kept

GMB-143's own acceptance criteria said a task the arm already passes without help "repeats the
mistake this task exists to fix". This one is passed 5/5 by every arm in two turns, so it supplies
no signal about the disclosure — and as a benchmark task in its own right it is worse than neutral:
`gmesh-configured` spends 52,859 tokens where `baseline` spends 27,192 for the same 5/5, so adding
it would tax every future sweep to restate that a one-call lookup is a one-call lookup.

Registry restored to 34 excalidraw tasks. The measurement is kept here; the task is not kept there.

## What this leaves

**GM-256 stays shipped, on correctness.** `find_callers` was returning pages that said
`hasMore: false` while omitting usages; now it says so, at zero cost when nothing is omitted. One
measured agent — mid edit-and-verify loop on `tt-implement-release-cancelled-task-bug` — did fall
into exactly that gap and grepped its way out. The disclosure is for that case.

**Its benefit is not measurable on this benchmark, and now for a stated reason.** Not "we lacked
repetitions" but "the benchmarked agent takes the other path". Anyone revisiting this should start
from that sentence rather than from another A/B.

**The open question it leaves is sharper than the one it closed.** The gap only bites an agent whose
tool choice has already gone wrong — and the one observed instance was an agent that had started
editing, which is the same boundary GMB-141 found the post-edit collapse at. If there is a real cost
hiding here, it is in the edit-and-verify loop, not in navigation, and it wants a task built around
that phase rather than around a lookup.
