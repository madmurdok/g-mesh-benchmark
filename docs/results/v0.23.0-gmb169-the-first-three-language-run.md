## What one repetition can and cannot support

One rep per (task, arm). That is enough for the question this run exists to answer — does the chain hold, and does the arm use the tool — and it is **not** enough for any statement of the form "X costs more than Y". A cost table reads as comparable whether or not it is, so the numbers below are reported with what they are for, and the comparisons this data cannot carry are named rather than left for a reader to attempt.

Nothing here compares a number across corpora. Different repositories, different tasks, different ground truth; the three columns sit side by side because they were run the same way, not because they are commensurable.

## The second headline, and it is a measured change rather than an observation

**The `gmesh-configured` arm called g-mesh on all 23 tasks**, between one and three times each.

Yesterday, on this same Python corpus, it called g-mesh in **5 of 16 runs** and said why in its own answer text: *"I used grep because this is a Python repo and the lookup was a single, unambiguous name."* That was GMB-165's subject — the arm's project doc opened `# Code search (TypeScript/JavaScript projects)`, and an arm handed a document that excludes the repository in front of it is not measuring the tool.

GMB-165 removed the scope line for non-TypeScript corpora. This run is the first measurement of that change beyond the two tasks that motivated it: 23 of 23, on three languages. The simple-lookup clause is still present in both arms and is still a legitimate reason to skip the tool — so this is not "the arm now always uses g-mesh", it is "the arm no longer declines because of the language".

## Per plugin, anchored to specific tasks

**Go.** `gin-deps-render-incoming` passed with one g-mesh call. That task was written against GM-356's defect — a file-path anchor on a module-graph language returning `results: []` with `truncated: false` — and its oracle is the three real importers of gin's `render` package. It is the fix working through the whole chain rather than in a unit test.

**Rust.** Three tasks written against 3.8.0's own fixes all passed: `rs-deps-sink-module-incoming` (GM-356 from the other side), `rs-find-impl-sink-trait` (GM-361's blanket impls, which were absent from a page reporting `hasMore: false`), and `rs-ambiguous-regexmatcher` (GM-360, where a bare name used to resolve, unflagged, to a `pub(crate)` test fixture). The two Rust failures are corpus defects, not tool defects — see below.

**Python.** `py-scenario-callers-httpadapter-send` is the one task where the two arms genuinely disagreed about the code: **g-mesh passed, baseline failed.** The question is whether `Session.send` is a caller of `HTTPAdapter.send`. It is not, statically: `get_adapter` is annotated `-> BaseAdapter`, so the call binds to the interface declaration even though `Session.__init__` only ever mounts concrete `HTTPAdapter` instances. The grep arm answered "Yes ... through dynamic dispatch" and the judge rejected it for conflating static analysis with runtime behaviour. That distinction is exactly what the index knows and a text search does not.

## The three oracle failures, and none of them is "g-mesh did worse"

**`py-scenario-callers-httpadapter-send` (baseline failed)** — above. A real difference in the answers.

**`rs-deps-json-printer-workspace-crates` (gmesh failed)** — a corpus defect, in two parts. The `candidatePool` spells the crates as module identifiers (`grep_searcher`) while the task's own prompt spells them as Cargo does (`grep-searcher`); the answer followed the prompt and missed two entries on spelling alone. The third entry, `grep_regex`, is present in the answer but was correctly refused by the harness's own negation guard, because the answer argues it is a test-module-only import and gives the line. That leaves a real question the oracle settled by fiat — whether an import inside `#[cfg(test)]` is the file's dependency — which the fix has to decide rather than re-spell. Filed as **GMB-174**.

**`rs-outline-sink-vs-lines` (gmesh failed)** — the oracle requires the answer to contain the literal strings `crates/searcher/src/sink.rs` and `crates/searcher/src/lines.rs`, both of which the **prompt itself supplies**. The agent, having been given them, wrote `sink.rs` thereafter. Baseline happened to repeat the full paths and passed. Both arms listed the right public items; `SinkMatch` and `LineStep` matched in both. This grades transcription. Also **GMB-174**.

Both of these make the arms differ on wording where the knowledge is identical, which is noise in a benchmark whose entire output is a comparison between arms. **Rust's 6/8 should be read as 8/8 on knowledge**, and the Rust column's oracle figure is not usable until GMB-174 lands.

## What the cost column is, and what it is not

The `gmesh-configured` arm spent roughly twice the tokens on gin and py-requests and about 2.8x on ripgrep, while taking **fewer turns on two of three** (20 against 30 on gin, 29 against 34 on py-requests, 30 against 32 on ripgrep) and issuing fewer greps and reads everywhere.

Fewer turns and more tokens together point at the per-turn cost of the guidance document the arm carries, which GMB-150 measured at about 9,100 tokens per turn — the baseline arm carries no such document. That is a *consistent reading*, not a measurement: one repetition cannot separate it from task-level variance, and this run was not designed to. GM-352 in 4.0.0 owns that measurement and has been amended with what it must cover.

What can be said without a second repetition: the tool was used, it did not cost turns, and it did not cost correctness.

## One finding filed against g-mesh

**GM-369** (3.9.0). On the outline task the agent wrote, unprompted, that g-mesh "flags trait methods and impl items as `exported: true` even when they aren't independently `pub`", and spent a grep checking. The field is correct — a method of a `pub trait` is reachable — and it does discriminate, which was checked rather than assumed: `sink.rs` is 59 of 60 true, `lines.rs` 7 of 31, `searcher/core.rs` 0 of 34. But a real consumer read "exported" as "has its own `pub`", disbelieved a correct answer, and paid a round trip to confirm it. Nothing in the response says the field is about reachability.
