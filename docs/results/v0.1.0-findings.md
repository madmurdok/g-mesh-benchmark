# v0.1.0 token-economy findings

Date: 2026-07-28. Run: `results/token-economy/2026-07-28T20-44-53-497Z.json`
(5 seed tasks × 2 arms, `task-tracker-mcp` corpus, `claude-sonnet-5`, single run
per task/arm — no repetitions yet).

## Headline number, with its caveat

Aggregate token reduction (gmesh vs. baseline): **+1.0%** — effectively a wash.

This number is **not a reliable signal at n=5, one run each**. Per-call cost
ranged $0.02–$0.13 and turn counts swung 2–7; a single-digit aggregate
percentage on a sample this small and this noisy could flip sign on a rerun.
Treat this release as "the harness works and produces real, honest data," not
"g-mesh does/doesn't save tokens" — that question needs more samples (see Open
Questions).

## The pattern inside the sample (more informative than the aggregate)

| Task | Result |
|---|---|
| `tt-deps-incoming-db-connection` (fan-in across 37 files) | g-mesh clearly cheaper (1681 vs. 3717 tokens) |
| `tt-outline-lifecycle-vs-small` (outline + contrast, 2 files) | g-mesh clearly cheaper (4173 vs. 7635 tokens) |
| `tt-find-impl-completionverifier` (single implementation) | g-mesh more expensive (2640 vs. 894 tokens) |
| `tt-find-impl-budgetestimator` (single implementation) | g-mesh more expensive (2562 vs. 2126 tokens) |
| `tt-references-requiretask` (find_references) | g-mesh more expensive (4785 vs. 1632 tokens); oracle false-negative, see below |

**Hypothesis**: g-mesh's advantage should track corpus size/complexity, not be
a constant. The two wins are exactly the cases where a structural graph beats
grep (searching *across* many files). The two losses are trivial single-file
lookups on a small (~7k LOC) corpus, where g-mesh's fixed tool-schema overhead
(extra `cache_creation` tokens for the tool definitions) isn't amortized by
enough search volume to pay for itself. `task-tracker-mcp` may simply be too
small to show g-mesh's advantage clearly — a bigger corpus is the natural next
test of this hypothesis (deferred: tier-2 external OSS corpora).

## Oracle false-negative (grading artifact, not a real failure)

`tt-references-requiretask`'s gmesh-arm answer correctly listed
`src/domain/tasks.ts` as a caller but never literally repeated the word
"requireTask" in its final sentence (implied by context), so the
substring-based oracle marked it failed. The design doc's architecture flagged
this exact class of false-negative as a known v1 limitation — confirmed on
the very first real run.

## Bug found and fixed during this run

The first attempt (now deleted, superseded) showed 2/5 gmesh-arm tasks
returning a permission-prompt message instead of a real answer — g-mesh's
tools were blocked on an unapprovable interactive confirmation in headless
mode. Fixed by adding `--permission-mode bypassPermissions` to
`harness/lib/runClaude.ts`'s spawn args. Confirmed fixed before this run.

## Open questions for future work

- **Sample size**: repeat each task 2-3x before trusting any aggregate
  percentage (already flagged as a v1 risk in the architecture doc).
- **Corpus-size scaling**: test the fan-in/outline-win hypothesis against a
  larger corpus once tier-2 (external OSS repos) is added.
- **Turn-count anomaly**: gmesh arm took 5-7 turns on 3/5 tasks vs. baseline's
  3-4 — under separate investigation, see `turn-count-investigation.md`.
