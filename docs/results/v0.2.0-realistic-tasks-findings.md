# v0.2.0 realistic-tasks findings

Date: 2026-07-30. Run: `results/token-economy/2026-07-30T13-36-32-111Z.json`
(full v2 corpus, 20 tasks × 2 arms, `G_MESH_BENCH_REPS=low`, one rep each,
`claude-sonnet-5`), read together with the accumulated history in
`results/token-economy/*.json` via `npm run report`. See
`docs/architecture/g-mesh-bench-v2-realistic-tasks.md` for the redesign this
run validates.

## What v2 set out to fix, and whether it did

1. **Oracle false-negatives** — fixed and confirmed. The two tasks that
   motivated the whole redesign (`ex-references-pointfrom-highfanout`,
   `ex-deps-package-math-incoming`) now grade against a ts-morph-computed
   candidate pool instead of a hand-picked subset, and both pass on both arms
   in this run (`oraclePassed: true` for gmesh and baseline alike).
2. **Location-revealing prompts** — fixed; every non-outline v2 task
   (`revealsLocation: false`) makes the agent locate the symbol itself.
3. **Missing multi-hop / ambiguous-name / control coverage** — fixed; all
   three categories are now populated (3 multi-hop, 2 ambiguous-name, 2
   control tasks in the corpus) and ran clean.
4. **Correctness vs. token-economy conflation** — fixed; `report.ts` now
   prints a separate correctness-by-category table before the token table,
   and the aggregate is reported both PAIRED (only oraclePassed-true pairs)
   and UNCONDITIONAL.

No crashes, no `budget_exceeded` runs, all three oracle modes (substring /
pool / judge) exercised successfully in this run.

## Correctness (v2-categorized tasks only, cumulative history)

| Category | gmesh | baseline |
|---|---|---|
| lookup | 17/17 | 15/17 |
| ambiguous-name | 3/3 | 3/3 |
| multi-hop | 4/5 | 5/5 |
| control | 2/2 | 2/2 |

Now that the oracle isn't the thing being measured, correctness reads as a
real signal: gmesh matches or slightly beats baseline everywhere except
multi-hop (4/5 vs 5/5 — one judge-graded compound task failed on the gmesh
arm; worth a follow-up look but n=5 is too small to call a pattern). This is
a meaningfully different picture from v1, where the two arms' pass rates
(34/53 gmesh, 38/53 baseline) were mostly measuring which arm got lucky with
the hand-picked `mustMentionFiles` subset, not which arm was actually right.

## Token economy — the honest number is worse for gmesh than v1 suggested, not better

| Scope | Paired reduction | Unconditional reduction |
|---|---|---|
| v2-categorized tasks only | **-43.3%** (n=24 pairs) | -36.7% |
| Whole history incl. legacy v1 tasks | -27.3% (n=37 pairs) | -36.6% |

Read literally: gmesh spends roughly 30-45% *more* tokens than baseline on
the v2 task set. This is not the oracle-bug artifact v1 had — these are
paired numbers, restricted to runs where **both** arms produced a
provably-correct answer, so there's no "gmesh looked bad because its correct
answer got marked wrong" effect left to blame.

### Splitting by corpus surfaces a real, distinct signal

| Corpus | Paired/mean reduction | gmesh pass | baseline pass |
|---|---|---|---|
| `task-tracker-mcp` (small, ~7k LOC, single package) | -24.9% | 6/6 | 6/6 |
| `excalidraw` (large pnpm monorepo) | -38.4% | 20/21 | 19/21 |

gmesh costs more tokens on **both** corpora, but the gap is worse on
excalidraw. Two candidate explanations, not distinguished by this run:

- **Fixed overhead not amortized.** The two `control` tasks
  (`expectedWinner: "parity"`, where gmesh's tools shouldn't matter at all)
  show gmesh costing ~10,500 more tokens than baseline on *both* tasks
  (57.2-57.4k vs 46.8-46.9k) — a near-constant ~22% tax that looks like pure
  MCP tool-schema/config overhead, independent of task content. This alone
  would explain a chunk of the gap on both corpora.
- **g-mesh's own cross-file resolution bugs on the excalidraw monorepo**
  (tracked separately, task #22 in this project's tracker — **still open,
  not fixed by this redesign**). If g-mesh's structural tools return
  incomplete or wrong results on excalidraw's multi-package pnpm layout, the
  agent has to fall back to grep/Read to double-check or correct them,
  paying for both the g-mesh call *and* the manual verification —
  exactly the self-verification pattern already documented in
  `find-impl-token-increase-investigation.md`. This would explain why the
  gap is specifically worse on the corpus where that bug lives, not on
  `task-tracker-mcp` where it doesn't.

**This run cannot separate the two.** Task #22 is explicitly out of scope
for the v2 redesign (it's a g-mesh bug, not a benchmark-methodology bug) and
remains open. Until it's fixed, the excalidraw-specific portion of gmesh's
token disadvantage should be read as "at least partly a known, fixable
tooling bug," not as an inherent property of structural search on large
repos. The `task-tracker-mcp` number (-24.9%, no known resolution bugs) is
the cleaner read of gmesh's overhead on a corpus where it "just works."

## Bottom line

The redesign did its job: the benchmark's correctness signal is now
trustworthy (paired, pool/judge-graded, location-hidden), and it says gmesh
is at least as correct as grep/Read/Glob, sometimes more so. But the token
picture is now *more* unfavorable to gmesh than v1's near-wash number, not
less — v1's flattering aggregate was itself partly an artifact of
location-revealing prompts removing gmesh's main opportunity to win *and*
partly the oracle bug inflating both arms' apparent failure rate similarly.
With realistic tasks, gmesh's fixed per-call overhead (~10-11k tokens,
visible cleanly in the control tasks) and, on excalidraw specifically, its
own open resolution bugs, add up to a real net token cost today. The
multi-hop category was supposed to be gmesh's best case (chained structural
lookups vs. several grep round-trips) and it did not show a token win in
this small sample either.

## Open questions for future work

- **Fix task #22** (g-mesh cross-file resolution on pnpm monorepos), then
  re-run the excalidraw split to see how much of its -38.4% gap closes.
- **Multi-hop sample size** (n=5) is too small to trust the 4/5 correctness
  dip or the lack of a token win — worth more tasks/reps once #22 is fixed,
  so a rerun isn't measuring the same confound twice.
- **Fixed overhead**: the ~10-11k token control-task tax is now measured
  directly; worth checking whether it's dominated by MCP tool-schema
  definitions (fixed, one-time per call) vs. something scaling with
  conversation length, since that changes whether it's amortizable on
  longer real-world sessions.
